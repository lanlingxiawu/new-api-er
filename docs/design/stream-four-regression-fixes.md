# 流式异常流程四项修复与延迟验证

## 目标与已确认范围

按本次确认修复四项：AWS 原生 Claude 的 message_delta 被过滤、多候选完成状态提前锁定、预读错误影响此前有效尾帧、完整 JSON 仅凭语法合法被判成功。保留入口流式及成功 HTTP 200/WS 101 门控，非流式和关闭开关的路径不变。PaLM 空结果虽有历史行为，本次也纳入修复。

## 数据流与边界

1. HTTP 原始响应采集仍位于解析之前；不新增读取、不采集请求。采集上限、超级管理员查询和异常才保存的条件沿用现状。
2. 受管 SSE/NDJSON 的读协程只做分帧；所有者按帧顺序观察协议、转换、写出。EOF/读错误排在已读帧后处理。独立旧扫描器使用一帧一批的响应观察，避免同一次 Read 提前处理后续错误。
3. Claude message_delta 使用独立结束粒度：有真实 stop_reason 证据或全流完成时放行；message_stop 仍要求完整协议结束。原生 Claude 专用解析器维持原流程。
4. 多候选按 index 累计完成状态，每次重算；透传使用入口 n/candidateCount，转换路径在发送前用实际出站 JSON 覆盖（包含字段被删除）。新增未完成候选撤销暂时完成，未全部完成时 [DONE] 不替代候选结束。后续兼容性修复见 `stream-protocol-compatibility-fixes.md`。
5. 完整 JSON 必须满足具体响应结构，而非只通过 JSON 语法检查。PaLM 空候选/空内容进入上游协议异常；保留有效 PaLM/Nova 和已有标准完整响应。原生 error 仍保存原帧。
6. 受管 OpenAI 转换取消延后一帧写出的行为，在当前帧已验证且尚未处理下一帧前写出；避免尾帧留到 EOF 后才交付。保留 usage 选择、协议转换以及本地假成功尾帧拦截。

## 计费与错误处理

不修改结算矩阵：用户断开按确认用量；上游异常且已有有效交付时采用确认用量或交付估算；无有效交付零计费并由既有结算退款。新增识别出的异常复用现有公开错误、私有证据和诊断流程。首个错误保持不被覆盖，不将后续排队用量当作已处理用量。

## API、存储、配置

无新增接口、字段、表、迁移、索引或配置；诊断沿用仅超级管理员的现有接口。复用 stream_error_setting.enabled/capture_response。无前端改动。

## Main Chain Impact

同步：有界分帧、JSON 验证、候选状态更新、原转换、Write/Flush、已交付内容估算。读协程仍为既有单读者，不新增网络等待、凑批定时器或后台任务。日志仍在既有异步路径。当前完整事件到达即可处理，不等下一事件或 EOF；完整 JSON 协议本身需等 body 完成。

## Shared Resource Audit

仅请求局部会话锁、候选 map（最多 128 项）、响应帧缓存（8 MiB 上限）及已有单元素读队列；无新共享 map、Redis key、数据库访问、连接池或文件句柄。下游写锁不与读者协议状态锁跨网络共享。原始采集缓冲仍为头尾固定窗口。

## Concurrency Analysis

30k/100k RPM 分别约 500/1667 请求每秒；本修复新增 DB/Redis 调用为 0，新增工作协程为 0。候选状态每帧 O(候选数)，上限 128；JSON 和帧处理 O(当前帧字节数)。实际 CPU 成本随每请求事件数量变化，使用本地基准量化，而不把微基准当作生产压测。重点检查新流程每帧同步 token 估算及帧复制的成本。

## 实施顺序与验证

先加回归夹具并确认失败，再修复生产代码，补中文注释并对照实现复核。覆盖正常/异常、单/多候选、同批读取/分片、SSE/NDJSON/SDK、原始 error、非流式和开关关闭、PaLM/Nova 完整 JSON。增加首帧到达后上游停住的延迟测试，检查下游无需等待下一帧；运行开关/采集开关基准。最后运行相关 Go 测试、根模块构建；数据库不可达时单独说明数据库测试边界，不操作真实余额。

## 风险与取舍

未知厂商完整 JSON 不推断为成功，应由明确协议结构确认。候选数量未声明时按已出现候选判断，未来出现新候选时重新判断；上游连候选存在的证据都未提供时，没有事实依据推断隐藏候选。基准只代表本机本地写入，实际下游延迟还受网络、反向代理刷新及上游分帧影响。

## 实施与验证结果

已完成四项修复。生产文件涉及 `relay/common/stream_session.go`、`relay/common/stream_writer.go`、`relay/helper/managed_stream.go`、`relay/channel/openai/relay-openai.go`、`relay/channel/openai/helper.go`、`relay/channel/palm/relay-palm.go` 和 `service/stream_lifecycle.go`。

- AWS SDK 原生 Claude 在 message_stop 前即可交付真实 message_delta；缺 message_stop 仍报异常。
- OpenAI/Gemini/腾讯按候选索引累计并重新判断完成；候选数在透传和重试时按本次实际请求确定，DONE 不替代未完成候选。
- 受管读者只分帧，写入所有者按顺序推进协议状态；独立扫描器一次最多接收一个已观察帧。采集器可保存已读入但尚未消费的字节，不据此提前改变协议状态或确认用量。
- 完整 JSON 检查具体响应结构。空对象、仅用量、缺内容/候选/必要终态在适配器写出前失败；PaLM 再校验自身内容。有效 PaLM/Nova 保留原成功和计费路径。完整 JSON 的读取错误不因 finish 字段被忽略。
- 受管 OpenAI 取消一帧滞后；Claude 转换的真实 finish 帧没有 usage 时先交付正文，确认完成后仅关闭协议块，不重放正文、不在异常时猜测 end_turn。覆盖首帧即结束、独立 usage 和未预建转换状态。
- 独立读取复用 4 KiB 缓冲，分隔符仅扫描新增数据与最多三个边界字节；受管扫描器、SDK、裸媒体不分配此缓冲。

- service/model/controller/middleware 的选定流式结算、诊断权限及退款日志测试通过。沿用外部 overlay 跳过依赖本机数据库的 TestMain，未修改仓库 TestMain 或操作真实余额。
- 根模块 `go build ./...` 通过。未修改 relaykit、前端、依赖或数据库结构。
- Go 格式、差异空白、UTF-8 无 BOM 及本轮中文注释与实现复核。

### 下游延迟结论

完整当前 SSE 事件到达即处理，无新增等待下一帧或 EOF 的条件。管道测试让上游在第一帧后暂停，OpenAI/Claude/Gemini 下游均先收到正文。修复前快照运行同一测试，三种路径均被旧的一帧滞后阻塞超过测试的 1 秒上限；修复后重复 30 次通过。1 秒是测试阈值，不是生产固定延迟。完整 JSON 协议本身仍需等 body 完成。

本机 Windows amd64 / i9-14900HX，基准每组 `-benchtime=1s -count=3`，不含真实网络、DB 或日志落库：

| 基准 | 本次修复前 | 本次修复后 |
| --- | --- | --- |
| 103 字节帧的协议观察、写出/刷新和交付估算 | 5.63–5.89 μs | 5.56–5.68 μs |
| 上述流程加上下游有界采集 | 5.70–5.91 μs | 5.70–5.80 μs |
| 独立 HTTP 观察，100 个内容帧及结束 | 0.272–0.281 ms | 0.271–0.295 ms |

单帧约 0.006 ms 的同步成本，18 次分配/1448 字节与修复前一致。独立 HTTP 观察每请求分配约 62.8 KiB → 66.8 KiB，增加固定读取缓冲；耗时同量级、有波动。开关关闭的直接内存写出约 0.01 μs，但它不含协议检查，不代表网络端到端基线。

结论：新流程相对关闭开关有微秒级 CPU/内存开销，不是零成本；本次修复没有增加跨事件等待，并移除了受管 OpenAI 的一帧等待。真实 RTT、p95/p99、慢客户端及高负载影响仍需部署环境压测。
