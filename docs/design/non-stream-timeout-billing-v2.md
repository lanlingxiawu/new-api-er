# 非流式超时计费与内部转流优化方案

状态：用户已确认，P0 已实现；P1/P2/P3 为后续路线，未开放新增厂商或原生协议。
日期：2026-10-17

## 1. 目标与范围

本功能是管理员针对单个用户设置的超时收费策略。目标是让现有三个选项的实际行为与说明一致，并补齐该用户选择 charge 时的内部转流兼容性。不增加全局转流开关、容量参数、资源准入系统或新的用户配置项。

本方案结合现有代码、Codex/Qwen/Kimi 交叉审查，以上游实际协议及代码证据为准。相关历史设计：

- [非流式超时成本回收](non-stream-timeout-loss-prevention.md)
- [超时成本承担](relay-timeout-cost-bearing.md)
- [单用户双超时](per-user-relay-timeout.md)

当前事实：

1. `shouldAdaptUpstreamStream` 同时要求 OpenAI ApiType、StreamOptions、Chat Completions、charge 策略和有效截止时间。结合渠道映射和能力名单，生产路径实际仅允许 OpenAI/Azure 渠道类型的部分请求。
2. 专用 DeepSeek、xAI、NewAPI、Sub2API 等渠道类型有独立 ApiType；不能因其支持 OpenAI 协议就认为已进入转流聚合。
3. 能转流不等于拿到最终 usage；超时通常需要根据已收到的内容估算。
4. 未转流的 charge 超时走估算输入结算；按次模型、请求未完整发出等场景继续遵循现有退款规则。
5. 转流资格检查在参数覆盖之前，最终正文可以引入不支持的音频、logprobs、legacy functions 等字段。
6. 聚合器未记录输出报告的新鲜度；早期 usage 后继续输出再超时，可能按过期输出数量少收。这里只确认代码可接受此事件序列，未证明真实厂商会发送。
7. OpenAI adaptor 清除非 OpenAI/Azure 渠道 StreamOptions 的分支，在当前转流范围内不可达，不能作为当前缺陷；未来扩围时必须重新核查。

不在本轮范围：平台级开关和容量治理、后台继续读取以追讨输出成本、真实上游账单对账、修改价格表达式、重新设计钱包事务、修改客户端断开合同、把所有 API 强制变为 Chat 聚合。现有内存和连接使用只做影响检查与测试，不借此扩建一套管理配置。

## 2. 实施阶段与交付边界

| 阶段 | 工作 | 交付标准 |
|---|---|---|
| P0：先修用户策略的现有行为 | 最终正文校验、usage 新鲜度、复用现有日志说明确认/估算依据、明确三档说明 | OpenAI/Azure 范围内不再因参数覆盖静默丢字段；异常结束不直接采用过期输出计数；无新增配置 |
| P1：兼容渠道 | 按实际协议和请求特性判定；分批评估 NewAPI、DeepSeek、xAI、Sub2API | 每个新增组合有完整 fixture 和回退测试，仍只在该用户选择 charge 且有有效超时时进入 |
| P2：原生协议 | 分别接入 Responses、Claude Messages、Gemini | 各自完整重建目标非流响应、用量与终止状态，逐协议单独发布 |
| P3：特殊能力 | 多 choice、logprobs、音频等分别评估 | 按已验证能力判定，未达标继续使用普通非流路径 |

建议先批准并实施 P0；P1/P2/P3 是完整演进路线，不与 P0 捆绑上线。各后续阶段在实施前补齐具体协议合同和测试清单，再确认其实施范围。

## 3. 用户计费与返回合同

保留数据库和 API 的 `refund`、`input`、`charge` 三个值，不自动修改存量用户选择。

| 我方超时场景 | refund | input | charge |
|---|---|---|---|
| 未内部转流，尚无完整响应 | 按现有规则退款 | 按估算输入；输出 0 | 同 input，明确标记未取得输出证据 |
| 已内部转流，但无有效输出 | 不启用此转换 | 不启用此转换 | 确认输入优先，否则估算输入；特殊退款条件沿用现有合同 |
| 已内部转流，有有效输出 | 不启用此转换 | 不启用此转换 | 返回部分结果，按确认/补估用量结算 |

以上只讨论非流式客户端。普通流式请求已有交付后的收费、客户端主动断开、上游错误和任务豁免规则不改变。

补充合同：

- 正常完整完成优先保留上游 usage，不用本地估算覆盖新鲜的最终报告。
- 异常结束且输出报告早于最后一段计费内容时，采用 `max(确认输出, 已接收输出估算)`，与普通受管流保持一致。不得把未知缓存/隐藏推理 token 按猜测补入。
- usage 是否存在、字段是否缺失、显式零是否有效必须分开；新鲜且明确的零不能仅因等于 0 被覆盖。缺输入字段的回退与当前兼容合同不同时，先以回归测试固定差异，不在本轮顺带改变所有正常请求的零值行为。
- 输入、缓存、输出可来自不同证据，不能只用一个“真实用量”标签概括。
- 按次价格不能拆成输入价格；免费、未完整发送上游、结算失败等边界复用当前规则。
- 超时有输出保留当前普通 JSON 和 `finish_reason: length` 合同。工具 arguments/结构化内容可能截断，不伪造闭合 JSON，不自动执行工具。
- 无输出继续使用现有 504 超时错误及请求 ID；HTTP 200 的部分结果不能被 UI 解释为完整成功。
- 资源预算截断与我方超时分开记录，不能伪装 `relay_timeout` 或擅自套用 input 超时规则。

界面建议保留三档结构，说明为“超时退还额度”“超时按收到的用量计费”“超时仅收输入费用”。第二档附说明：优先上游确认，缺失时本地估算；不支持内部转流时仅按输入结算。最终文案实施时按前端 i18n skill 完成七种语言，不在本设计中新增翻译键。

## 4. 数据流：请求 → 处理 → 存储 → 响应

1. 从现有用户上下文读取收费策略、超时及渠道设置；冻结本次请求的配置快照，不新增 DB/Redis 回源。
2. 对候选请求完成现有模型映射、适配器转换、禁用字段处理和管理员参数覆盖，得到最终业务正文。是否可聚合依据此正文与实际目标协议判断。
3. 实际实现将 stream/stream_options 注入与计时器 hold 延后到适配器转换、禁用字段处理和管理员参数覆盖全部结束之后。最终正文不兼容时不注入、不 hold，直接保留原普通路径，无需先改写再撤销。
4. 参数覆盖只执行一次，因为其可能含条件、审计或请求相关逻辑。将改写前 stream/stream_options 的原始 JSON 小片段保存于本请求上下文；若转流遭拒后普通重发，只撤销本功能的注入，恢复管理员原值，包括显式 false/null 与扩展选项。管理员 stream:true 或 include_usage:false 不接入内部聚合，保持既有处理方式。
5. 根据最终正文和已验证协议能力决定是否转流；不支持则走原普通非流路径，超时后按该用户现有策略处理。不新增资源准入步骤，不增加上游调用。
6. 确认可转流后，保持客户端非流身份和原超时语义，只调整上游请求；首次 SSE 事件不能提前解除“等待完整非流结果”的计时器。
7. 由对应协议聚合器同步读取既有上游响应，积累内容与 usage 证据，识别完成、超时、读取失败、上游错误及资源截断。
8. 用量选择后，由现有 BillingSession 唯一结算，响应写入与错误路径沿用现有终止所有权。记录必须反映资金实际提交结果，失败不得产生虚假收费日志。
9. 复用异步日志管道写消费/错误日志；释放上游 body 和扫描缓冲，沿用现有聚合上限。重试前清空单次尝试状态，保留请求级资金会话和调用预算。

## 5. 协议能力与兼容路线

不要用“厂商名支持流式”或单个 `SupportStreamOptions` 推导可聚合。P1 提供显式静态能力定义，至少区分：上游协议、目标非流协议、usage 获取方式、已支持的响应特性；不按请求探测远程能力，不维护无限增长的自动探测缓存。

| 协议 | 聚合要求 | 首批边界 |
|---|---|---|
| OpenAI Chat | choice/index、正文、推理别名、拒答、tool_calls、annotations、过滤信息和 usage | 先维持单 choice；原生多模态/未知块不能直接吞掉 |
| Responses | output item/content part 生命周期、工具调用、推理及 usage、完成/不完整状态 | 复用现有转换能力，但另补超时结算所有权；不能直接套 Chat finish_reason |
| Claude Messages | content block、tool_use、thinking/signature、缓存读写/TTL、stop reason | 原生事件保留；不能丢思考签名或按 OpenAI 缓存口径重复扣减 |
| Gemini | candidates、parts、多模态数据、函数调用、thought 信息、usageMetadata、安全和完成原因 | 未明确支持的媒体输出不转流，不把媒体只当文本 |

P1 的 NewAPI/DeepSeek/xAI/Sub2API 只是候选，不表示全部接口、模型和设置已获支持。必须核查各 adaptor 的最终路径、字段改写和是否请求 usage，再逐组合纳入。专用渠道的 Claude/Gemini/Responses 路径与 Chat 路径分开判定。

图片生成、音频输出、Realtime、视频及任务提交保留专用生命周期。原有提交即计费的超时豁免不变，不强行纳入本方案。

## 6. 用量证据及日志

P0 已实现的请求本地状态为：最后计费输出序号、最近输出 usage 报告所覆盖的序号、同帧是否携带 usage，以及 completion_tokens 是否存在。输入/缓存仍沿用既有证据处理，不扩大本轮的正常零值语义。正文、推理、拒答、工具名称或参数的实际写入推进输出序号；角色、心跳、空帧、annotations 和工具 id/type 不推进。

若单帧同时包含正文和 usage，应在该帧处理完成后确定覆盖范围，避免把同帧报告误判为过期；尾部新鲜 usage 即使输出显式为零也按相应协议解释。

优先复用普通流的“输出报告新鲜度＋异常补估”规则；抽取确有两处调用的业务逻辑即可，不为机械缩短调用者建立大量 helper，也不把非流请求接入流式 writer。

P0 复用现有 `admin_info.local_count_tokens` 标志：只有实际补估并提高输出计数时设置本地计量标志；确认值已经不小于估算值时不修改。复用既有转流与终止日志，不增加新的诊断对象、页面或报表配置。返回 JSON 中的 usage 与实际选择的计费用量一致，不再把过期的原始 usage 覆盖回去。

逐输入/输出/缓存的独立来源展示留到后续协议扩展确有需要时再设计，本轮不为界面说明而引入一套用量证据平台。日志不保存额外正文、提示词、API key 或完整请求参数。

现有 `timeout_absorbed` 与导出字段保持兼容；它是按现有定价和可观测证据计算的估算，不能宣称等于上游账单或数学意义上可靠的成本下限。P0 不改这一独立展示及历史列名，不批量重写历史记录。

## 7. API 合同、权限及数据模型

不增加业务端点：用户策略继续沿用管理员 `PUT /api/user/`，保持现有 `AdminAuth` 权限；普通用户不能借此修改管理员配置。

请求示意（其余更新字段沿用当前接口）：

```json
{"id":123,"non_stream_timeout_billing":"charge"}
```

策略仍只接受 `refund|input|charge`；失败响应沿用现有 API 形状及鉴权，不能返回原始 Go 错误。不新增系统设置 API 调用或公开接口。

无新增表、列、索引或迁移；复用现有 `users` 字段和日志 `other`，不新增 `options` 配置，不引入新的大表查询、JOIN、聚合或历史回填。日志权限过滤和管理员导出合同保持不变。

若实现阶段更改配置读写、日志 SQL 或其他数据库行为，必须补 SQLite/MySQL/PostgreSQL 真实实例验证；不能把“无需迁移”当成免验证的理由。当前设计未执行该矩阵，不声称已验证。

## 8. 配置范围：只沿用用户现有选项

新增配置参数：无。保留 `users.non_stream_timeout_billing` 和现有用户超时字段，存量用户选择不变。

- 用户为 refund：不因本方案启用内部转流，超时按现有退款规则处理。
- 用户为 input：不为收输入而额外转流，超时按现有输入结算规则处理。
- 用户为 charge 且存在有效超时：只对已验证支持的协议与请求特性进行内部转流；不支持则保留普通请求和现有输入回退结算。
- 用户没有启用超时或明确不限时：不因这个计费选项额外转换上游请求。

现有用户策略已提供逐用户启用边界，符合 relay 改动需可配置控制的要求，不重复增加全局开关。不能为临时停用转流擅自将用户的 charge 改为 input/refund，因为这会改变用户约定的收费策略；代码回退通过对应版本修复或回滚完成。

兼容判断属于实现正确性，不要求管理员再选择厂商/协议开关。只有经过验证的组合进入代码能力判断，不支持的组合自动保留原路径。用户不需要理解 stream_options、缓冲预算或聚合器。

本轮沿用现有 scanner、聚合上限及连接池。扩围前核查其性能影响；若发现阻碍上线的实际容量问题，先暂停对应扩围并单独记录问题，不在用户配置方案里加入新容量管理系统，也不声称现有单请求上限足以保障任意并发。

## 9. 错误处理、重试与生命周期

- 正常成功：聚合并唯一结算，完整返回；释放资源。
- 我方超时：有输出交付部分结果，无输出返回现有超时错误；按用户原策略与本方案证据选择结算。
- 参数不兼容：必须在上游调用之前恢复普通路径；不额外发送试探请求。
- 转流被上游拒绝：保留现有一次普通重发规则，仍受总调用次数和总时长预算约束。不能假定任何 HTTP 500 都未产生费用；本轮不扩大可重发状态码。
- 已收到内容后坏帧/断流：保留当前部分交付合同，记录真实异常；显式上游错误仍按既有错误/重试策略，P0 不私自改变这一产品取舍。
- 结算失败：复用 FundingCommitted 与 BillingSession 的资金提交判定。未提交时走现有退款；提交后不可再次退款/扣款，必须记录失败供排查。
- 客户端断开：维持既有读取/结算及截止时间合同，不新增无限期后台工作。
- 解析异常：有界处理并记录英文内部日志，用户看到可理解的本地化错误；不把未识别的协议数据静默当成空 Chat chunk。
- 资源和计时器：body close、池归还须在所有退出路径恰好一次；重试只重置尝试级状态，不重置请求总调用预算和资金提交状态。

## 10. Main Chain Impact

同步执行：现有请求转换、最终字段校验、一次静态能力判断、请求本地 usage 序号更新、原本就需要的上游读流与聚合。资金结算沿用现有路径，不在本方案中引入第二套资金事务。

异步执行：诊断日志、消费日志复用现有通道；不在 relay goroutine 上增加日志 DB 写入、网络能力探测或后台对账等待。

不新增每请求 goroutine、全局互斥等待、同步 DB/Redis 调用、HTTP Client 或连接池；不接管普通客户端流式 writer。任何新增观察性失败只记日志，不能改变 relay 响应；必要的聚合解析/终止按明确协议合同处理。

可回退边界是发往上游之前。发送后不能以“安全降级”为由重跑一次有成本请求。仅现有用户 charge 策略且有超时时可能转流，未知能力不进入已验证名单。

## 12. Concurrency Analysis

100k RPM 约为 1667 请求/秒，30k RPM 约为 500 请求/秒。转换并发估算为 `RPS × 平均上游时长 × 转换比例`：例如平均 30 秒、全部转换，分别约 50,000 和 15,000 个在途请求。因此不能把单请求 200 MiB 上限理解成可承受该并发。

- 新增 DB 调用/请求：0；新增 Redis 调用/请求：0。
- 新增上游调用：正常及兼容检查回退均为 0；拒绝转流的普通重发保留原预算，不扩大发送范围。
- 锁：新增状态仅在请求内维护，无新增共享锁；沿用现有用户配置读取方式。
- goroutine：0 个新增每请求 goroutine；已有传输、超时控制和结算成本另计。
- CPU：复用现有 JSON/聚合扫描；最终兼容检查仅解析必需字段，不能额外完整反序列化整个大正文。补估仅异常结束触发一次，避免逐帧 token 化和重复拼接全部输出。
- 内存：沿用现有有界载荷，仅增加少量用量序号/存在性元信息；编码/快照的临时副本必须纳入实测。64 KiB scanner × 50,000 已约 3.05 GiB，尚未包含正文、HTTP 和业务数据，因此扩围必须评估真实容量，不能直接全量放开。

上述为设计估算，不是压测结果。P1 必须同时报告转换成功率、普通路径降级率、峰值堆、GC、连接数、延迟与错误率，不能只证明“请求没报错”。
