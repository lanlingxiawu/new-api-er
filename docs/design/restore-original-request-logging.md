# 恢复原有请求日志逻辑

用户确认以 9 月 10 日前的 `ccb9e01bc^` 为采集/投递逻辑基准，仅撤销新增的私有流及 `/messages` 排除。使用日志与计费不在本次范围内。

## 数据流与范围
沿用 RequestResponseLogger → recordRequestLogEntry → 原非阻塞队列 → model.RecordRequestLog。删除私有标记触发的响应正文清空和投递跳过，以及 `/messages` 路径排除。开关、用户名过滤、正文/头预算、字段、时间、原始头处理、存储、队列满丢弃及历史日志不变。原请求日志按原设计保留请求头，未新增脱敏规则。

## API / 数据模型 / 配置 / 错误
不新增接口、表、迁移或配置；详情 Root 权限和 no-store 保持当前状态。私有诊断与普通应用日志的隐私处理不变，只恢复独立的请求日志采集。保留 responseBodyWriter.Unwrap 这一透明接口，使新流的 FlushError/写入期限仍可传到底层；它不修改日志字段、采集或投递规则。

## Main Chain Impact
恢复原有受预算限制的请求/响应采集，同步仅执行原采集和非阻塞入队；正文落盘及内存索引登记仍由既有后台工作者完成，不新增主链同步磁盘/DB/Redis 操作、等待或协程。异常与用户断开不因日志恢复改变原结算结果。

## Shared Resource Audit / Concurrency Analysis
复用既有请求日志队列、文件写入工作者、正文文件及进程内索引，不增加命名空间、共享缓存或锁。当前 RequestLog 不写数据库；Redis 仅沿用进程首尾索引快照，不新增逐请求 Redis 操作。恢复后流式请求入队量增加，100k RPM 若全部命中过滤器则约 1667 条/秒，需关注既有队列、磁盘吞吐和文件句柄；不为避免丢弃而在主链等待。最大采集仍由 RequestLogMaxBodyKB 控制，与 200 MiB 流式帧限额无关。沿用旧队列满丢弃策略，因此不承诺零丢失的可靠投递。

## 验证
先更新原排除测试并补回归：私有/普通请求、Messages 流式/非流式、正常/异常/断开/非 200、关闭开关、用户名过滤、截取、原请求头、单次入队、刷新失败与诊断独立。与基准对比，生产文件除保留透明 Unwrap 外恢复原版本；其余数据写入模块保持原样。测试使用本地队列和 t.TempDir 隔离的真实文件存储，不访问生产日志目录。
