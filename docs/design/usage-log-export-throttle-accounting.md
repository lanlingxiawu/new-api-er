# 使用日志导出：限速按实际读到的行数计费

> 基线文档：`docs/design/usage-log-export.md`（§10 资源治理、§8 配置参数）。
> 本文是一处**性能缺陷的定位与修复设计**，不新增功能、不改变任何导出结果。

---

## 1. 结论先行

导出慢的主因不是查询、不是渲染、也不是压缩，而是**限速闸门按「请求的批大小」收费，
而不是按「实际读到的行数」收费**。

在本机开发库上实测一次 7 天范围的导出：

| 项目 | 耗时 |
|---|---|
| 真实工作（查询 3 ms + 渲染 1 ms，共 595 行） | **4 ms** |
| 闸门休眠（168 个 1 小时窗口 × 150 ms） | **25,200 ms** |

**99.98% 的时间花在睡觉上。** 31 天范围则是 744 × 150 ms = **111.6 秒**，
与这段时间里有多少行日志完全无关——哪怕一行都没有，也要跑将近两分钟。

## 2. 定位过程与实测数据

### 2.1 渲染路径不是瓶颈（先排除）

`go test -bench`，12600KF：

| 场景 | ns/op | allocs/op |
|---|---|---|
| 默认模板 22 列渲染（`other` ≈ 700 B） | 10,323 | 144 |
| 同上，但列集不依赖 `other` | **226.9** | 6 |
| 单独的 `other` JSON 解析 | 9,209 | 128 |
| `other` 膨胀到 8 KB | 32,761 | 148 |

`other` 的 JSON 解析占了整个渲染成本的 **89%**。但即便如此，10.3 µs/行 换算成
97,000 行/秒，仍是配置上限 `max_rows_per_sec=20000` 的近 5 倍——**渲染不是瓶颈**。

> 顺带否掉一个想当然的优化：把 `other` 改成「先切成 `map[string]json.RawMessage`，
> 用到哪个 key 再解哪个」。实测**反而更慢**（11,986 ns vs 9,209 ns）——`encoding/json`
> 切 RawMessage 一样要扫完整个文档并逐片复制，省下的解码还不够抵掉两次扫描。
> 只有在 `other` 很宽（8 KB）时才由 32.8 µs 降到 25.5 µs。不值得做。

### 2.2 真实数据上的批次代价

只读探针，跑在本机配置的真实 `LOG_DB` 上：

```
[probe] logs 时间跨度: 2026-07-31 17:25 → 2026-09-20 19:46
[probe] 最近 7 天行数 = 595，平均 4 行/小时
[probe] 7 天 = 168 个 1 小时窗口；非空 14 个，其中不足一个批次(<3000 行) 14 个，空窗口 154 个
[probe] batch=3000 实取 595 行，查询+GORM扫描 3ms（4.38 ms/千行），other 平均 131 字节
[probe] batch=3000 渲染 1ms（1.75 ms/千行）
```

**168 个窗口里 154 个是空的。** 每个空窗口依然要付一次完整的闸门成本。

### 2.3 根因：闸门在查询**之前**按 `batchSize` 收费

`model/log_export_job.go` 的主循环：

```go
batchSize := ...GetBatchSize()        // 3000
gate.Wait(ctx, batchSize)             // ← 先按 3000 行收费
logs, err := scanLogExportBatch(...)  // ← 再去查，可能只回来 0 行
```

`gate.Wait` 里（`model/log_export_throttle.go`）：

```go
// waitRate: need = 3000/20000 * 1s = 150ms；base = 100ms；只补差额 50ms
// Wait 末尾: sleepAndCount(base + extra + penalty) = 100ms
// 合计：每批固定 150ms
```

这个账在**批次读满 3000 行时是准确的**（正好 20,000 行/秒）。问题出在读不满的时候：

- **每个窗口的最后一批**必然读不满（读满就不会退出内层循环）；
- **稀疏或空窗口**整个窗口只有一批，而且几乎是空的。

于是「每窗口至少一次按 3000 行计费的休眠」变成了一笔与数据量无关的固定税：
`窗口数 × 150 ms`。时间范围越宽、数据越稀，这笔税占比越高——
而「拉一个宽时间范围看看」恰恰是导出最常见的用法。

## 3. 修复

### 3.1 改动一：闸门按实际读到的行数计费

把 `gate.Wait(rows)` 拆成两个时机：

| 时机 | 做什么 | 为什么在这儿 |
|---|---|---|
| **查询前** `gate.Before(ctx)` | 低峰窗口等待、CPU 水位软/硬限 | 这两道闸的语义是「系统忙就别开工」，必须在开工前判断 |
| **查询后** `gate.Charge(ctx, rowsRead)` | 基础休眠 + 令牌桶速率 + penalty | 这两项的语义是「为刚做完的工作付费」，只有查完才知道做了多少 |

计费公式：

```go
factor := float64(rowsRead) / float64(batchSize)   // 0.0 ~ 1.0
sleep  := base*factor + rateDebt(rowsRead) + penalty
```

- `base*factor`：批间基础休眠按产出比例缩放。读满 3000 行仍睡满 100 ms，
  **满批行为与今天逐毫秒一致**；读 0 行则不睡。
- `rateDebt(rowsRead) = rowsRead/maxRowsPerSec`，减去已被 `base*factor` 占掉的部分，
  与现在 `waitRate` 的「只补差额」逻辑相同，只是基数从 3000 换成实际行数。
- `penalty` **不缩放**：它由实测查询耗时反馈得出，代表「数据库正在变慢」，
  这个信号与本批读到多少行无关，该退让还是要退让。

**满批场景下的限速强度完全不变**——这是这个改法的关键性质：
`max_rows_per_sec=20000` 依然是 20,000 行/秒的硬上限，
只是不再对没读到的行收费。

微休眠合并：`rowsRead` 很小时算出的 sleep 可能是零点几毫秒，
频繁 `time.NewTimer` 得不偿失。累积到 ≥ 5 ms 才真正睡，不足的记进 `debt` 带到下一批。

### 3.2 改动二：自适应扫描窗口

改动一之后，空窗口不再付休眠，但**仍然各付一次数据库往返**。
31 天 = 744 次往返，在稀疏实例上纯属空转。

让窗口宽度自适应：

```
初始宽度 = window_sec（配置值，默认 3600）
一个窗口扫完后：
  若该窗口总共读到的行数 < batch_size  → 下个窗口宽度 ×2（上限 MaxLogExportWindowSec = 86400）
  若该窗口用了 ≥ 4 批                  → 下个窗口宽度 ÷2（下限回到配置的 window_sec）
```

密集数据下窗口收敛回配置值，「把单次索引区间限死」的原始意图不变；
稀疏数据下窗口迅速扩张到一天，744 次往返收敛到 31 次。

**窗口拼接逻辑一个字都不能动。** 基线文档 §16.3 记过一个坑：窗口是闭区间
`[windowStart, windowEnd]`，下一个窗口必须从 `windowStart - 1` 收尾，否则边界那一秒
会被相邻两个窗口各扫一次、并真的重复写进文件（每个窗口的游标是独立重置的，
重复行不会被自然过滤）。自适应只改**宽度**，不改**拼接**，这条不变式必须由测试锁死。

### 3.3 预期效果

以 §2.2 的真实数据（7 天稀疏）为例：

| | 现在 | 改动一后 | 改动一 + 改动二 |
|---|---|---|---|
| 闸门休眠 | 25,200 ms | ≈ 30 ms | ≈ 5 ms |
| 数据库往返 | 168 次 | 168 次 | ≈ 10 次 |
| 总耗时 | **≈ 25 s** | **≈ 0.5 s** | **≈ 0.1 s** |

**落地后实测**（`TestWriteLogExport_SparseWideRangeDoesNotPayForUnreadRows`，
生产默认的 `window_sec=3600` / `batch_size=3000` / `max_rows_per_sec=20000`，
7 天范围 28 行）：

```
[gain] 7 天范围 / 28 行：耗时 22ms，闸门让出 18 ms，导出 28 行
       旧实现同等条件下仅闸门休眠就是 168 窗口 × 150ms = 25,200 ms
```

**25,200 ms → 22 ms。** 与预估一致。

数据密集的实例（每小时都能读满多个批次）上，两项改动的效果都趋近于 0——
**因为那种情况本来就没有被多收费**。这正是我们想要的：修掉虚耗，不动真实的限速。

## 4. 这会不会让导出变危险（Rule 0 / 资源治理）

不会，逐条对照基线文档 §10 的四道防线：

| 防线 | 改动后 |
|---|---|
| 行速率上限 `max_rows_per_sec` | **不变**，且计费更准确——现在是按真实读取量计，以前是按请求量高估 |
| CPU 软/硬水位闸门 | **不变**，仍在每批查询前判断；硬限以上照样暂停 |
| 低峰模式 | **不变**，仍在查询前判断 |
| `penalty` 反馈退让 | **不变**，且刻意不随行数缩放 |
| 一键刹车 `cpu_hard_limit=0` | **不变** |

真正的变化只有一句话：**以前空转也要付钱，现在不付了。**
单位时间内对数据库的真实压力上限没有提高——每秒最多还是 20,000 行。

唯一新增的压力是「稀疏范围下数据库往返变密」：改动一之后，空窗口之间几乎没有间隔。
改动二正是为此而设——它把空窗口数量本身压下去，比给空查询加休眠更对症。
保守起见，`Charge` 保留一个 **2 ms 的地板**，保证任何情况下都不会退化成忙等。

### 共享资源审计

| 资源 | 关系链路是否也用 | 影响 |
|---|---|---|
| `logs` 表（LOG_DB） | 是（异步批量写入） | 查询语句、索引、扫描顺序**零改动**；同一时间的读取速率上限不变 |
| CPU | 是 | 单位时间处理的行数上限不变，CPU 闸门不变 |
| 数据库连接 | 是 | 仍是单任务单连接，`max_concurrent_jobs` 不变 |
| Redis `logexport:*` | 否 | 不变 |

AI 关系链路代码零改动。

## 5. 配置

**不新增配置项。** `batch_sleep_ms`、`max_rows_per_sec`、`window_sec` 的含义与取值范围全部不变：

- `window_sec` 从「固定窗口宽度」变成「窗口宽度的**起点与下限**」。
  语义变化需要在设置页的说明文案里改一句，并同步基线文档 §8。
- 两个内部常量（微休眠合并阈值 5 ms、忙等地板 2 ms）不做成配置项——
  它们是实现细节，不是运营旋钮。

## 7. 不做的事

| 方案 | 否掉的理由 |
|---|---|
| `other` 改浅解析（`map[string]json.RawMessage`） | 实测更慢（§2.1） |
| 全局换 JSON 引擎（sonic 等） | `common/json.go` 确实预留了单点切换，但它同时是关系链路的 JSON 引擎。为了导出性能去动关系链路的热路径，风险与收益完全不成比例（Rule 0） |
| 查询与渲染流水线化（预取下一批） | 真实数据上查询 4.4 ms/千行、渲染 1.8 ms/千行，重叠最多省 30%；而在闸门修好之前，这 30% 淹没在 150 ms 的休眠里毫无意义。**等前两项落地、且确实需要突破 20,000 行/秒时再考虑**，届时单独设计 |
| `Find(&logs)` 换成 `Rows()` + 手动 Scan | 同上，属于「闸门修好之后才看得见」的量级 |
| 调大 `max_rows_per_sec` | 这是运营旋钮，不是修复。当前的账算错了，先把账算对；算对之后大概率不需要调 |

## 8. 实施顺序

**2026-09-20 已确认实施，且排在异常筛选/模板重整之前。**

1. 改动一（闸门按实际行数计费）+ 其测试 —— 独立可交付，收益最大
2. 改动二（自适应窗口）+ 其测试 —— 独立可交付
3. 同步基线文档 §8/§10 的语义描述与设置页文案（`window_sec` 由「固定宽度」改为「起点与下限」）

两项改动互不依赖，可以分别评审、分别上线。

## 9. 实现记录（2026-09-20）

两项改动均已落地，实测与预估一致。

### 9.1 文件清单

| 文件 | 改动 |
|---|---|
| `model/log_export_throttle.go` | `Wait` 拆成 `Before`（低峰 + CPU 水位）与 `Charge(rowsRead, batchSize)`（基础休眠 + 令牌桶 + penalty）；新增 `debt`/`softExtra` 字段与 `exportGateMinSleep`/`exportGateMinCharge` 两个常量；删除 `waitRate` |
| `model/log_export_scanner.go` | **新增**。把窗口迭代 + 批次 + 闸门 + 游标 + 进度抽成 `logExportScanner`，明细与聚合共用 |
| `model/log_export_job.go` | 主循环改用 scanner；新增 `nextLogExportWindowSec` 与 `logExportWindowShrinkBatches` |

### 9.2 与设计的差异

- **抽出了 `logExportScanner`**（设计里没有）。做聚合汇总时发现，若另写一套循环，
  「窗口边界不重不漏」这条不变式就会出现第二个必须单独维护的副本——而它恰恰是
  基线文档 §16.3 记过一次的、最容易错且后果最隐蔽的地方。
- **`Charge` 放在整批写出之后**，而不是查询之后。这样休眠成为两次数据库查询之间
  真实的间隔，渲染时间落在「活跃期」而不是「休眠期」。
- **窗口自适应只在窗口跑满整个宽度时调整**。被 `exportStart` 截断的最后一个窗口
  行数天然偏少，拿它当「稀疏」的证据会得出错误结论。

### 9.3 测试

| 测试 | 锁住的性质 |
|---|---|
| `waitFullBatch` + 既有 10 个用例 | **满批行为逐毫秒不变**。数值全部继承自旧实现，未改一处 |
| `TestExportGate_ChargeByRowsRead` | 满批 150ms / 半批 75ms / 空批 0（旧实现空批也要付 150ms） |
| `TestExportGate_EmptyBatchesStillPayFloor` | 地板价防止空窗口退化成无间隔连续查询 |
| `TestExportGate_MicroSleepDebtIsNotLost` | 600 行 @20000 行/s 恰好收 30ms，一毫秒不少 |
| `TestExportGate_PressureSignalsNotScaledByRows` | 软限额外休眠与 penalty 不随产出缩放 |
| `TestNextLogExportWindowSec` | 9 个表驱动用例：翻倍、封顶、减半、下限、批大小为 0 |
| `TestWriteLogExport_AdaptiveWindowKeepsRowsExactlyOnce` | 自适应扩张下边界仍不重不漏 |
| `TestWriteLogExport_SparseWideRangeDoesNotPayForUnreadRows` | 回归锁：7 天稀疏导出的闸门计费必须 < 500ms（旧实现 25,200ms） |

### 9.4 实现期的两处修正

- **`TestWriteLogExport_ThrottledTimeDoesNotConsumeTimeout` 的前提被改掉了**：
  它插 1 行却期望按满批（10 行）计费。按实际行数收费后 1 行只付十分之一，
  攒不出超过 `timeout_sec` 的让出时间。已补齐数据喂满一整批，保留它原本要证明的东西。
- **稀疏回归用例一度在全量套件里飘**。原因不是计费退回去了，而是 `penalty`
  （按实测查询耗时反馈的退让）在共享测试库上被其它用例的负载拉了起来。
  把 `batch_sleep_ms` 置 0 同时关掉了 penalty（上限是 8×base），
  断言才只反映「按行计费」这一件事；对照关系不受影响——旧实现在
  `batch_sleep_ms=0` 下令牌桶仍按 3000 行收费，168 个窗口照样是 25,200ms。
