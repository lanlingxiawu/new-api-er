# Dify 确认用量与流式媒体类型识别修复

## 已确认目标与范围

用户已确认按本轮审计建议修复两项问题：Dify 的 message_end.metadata.usage 未进入确认用量；带参数的 application/octet-stream 在观察器与转发器之间分类不一致。仅修改受管流式路径，不扩展协议能力，不改非流式、关闭开关、HTTP 非 200 或未收到响应的旧流程。

## 数据流、业务规则与错误策略

1. 原始上游事件 → 通用会话：仅 Dify 渠道的 message_end 登记 metadata.usage，使用既有数字校验和整批原子更新。该位置与 Dify 适配器一致；不采用节点事件的局部用量，也不把其他渠道的同名 metadata 当作计费证据。累计报告覆盖而非累加，保留显式零；非法报告保留此前有效证据并进入现有上游 JSON 错误路径。
2. 渠道转换 → Write/Flush → 统一结算：正常完成仍使用原适配器用量，但正确标记确认为上游用量；尾帧写入或刷新失败按已确认用量结算。缺失用量和显式零保持不同语义，结算矩阵不变。
3. 原始 Content-Type → 提取并规范化基础 MIME 类型 → 观察器/下游写入器/媒体转发器/终止错误层共用。只处理分号前的类型及大小写、首尾空白，不解析参数值，不修改原始响应头。参数中的 json、eventstream 等字符串不参与协议分类。
4. 裸媒体逐块读取并立即写入刷新，不等待 EOF，不受文本帧 8 MiB 上限影响；正常非空 EOF 完成，真实读取错误仍进入现有异常结算，已发送媒体中不追加 SSE。完整 JSON 与 SSE 保持原有交付确认及终态校验。

## API、数据模型、配置及权限

无新接口、表、列、迁移、索引、日志字段或配置。复用 stream_error_setting.enabled 及当前成功响应门控。原始响应头/body、底层错误和用量证据继续按既有上游异常规则保存，查询仍由 Root 权限保护；不采集请求数据。原 BillingSession、退款、日志队列及诊断字段均不变。

## Main Chain Impact

同步仅增加 Dify 终止事件的一次字段检查，以及基础 MIME 类型字符串提取/归一化；不增加上游读取者、网络/磁盘操作、等待下一帧或 EOF 的条件。媒体仍使用既有 32 KiB 转发缓冲，下游每次成功刷新后才确认有效交付。日志与资金副作用继续复用原路径，不新增同步存储操作。

## Shared Resource Audit

无新增 Redis 键、数据库查询、共享缓存、文件句柄、连接池或工作者。复用当前请求局部会话证据 map 及原有短锁，锁不跨网络操作。基础 MIME 类型不做全局缓存，不引入跨请求同步；不新增资金扣款入口或日志队列。

## Concurrency Analysis

30k/100k RPM（约 500/1667 请求每秒）新增 DB/Redis 调用 0、协程 0。Dify 增量成本为终止帧现有 JSON 查询中的固定字段数检查。MIME 分类只扫描 Content-Type 基础类型，不解析参数 map；已为小写的常见类型无额外归一化分配。修复后裸媒体不再因参数误分类缓存至 EOF 或占用 8 MiB 文本帧缓冲。新增本地首块顺序断言及大媒体夹具，不代替生产容量压测。

## 实施与验证步骤

先写回归测试并确认旧实现失败，再修改生产代码及中文注释：
- Dify 真实本地 HTTP fixture：正常用量、尾帧 Write/Flush 失败、无有效正文但有确认用量、显式零、缺失用量、非法用量有/无有效交付。
- 会话用量边界：重复累计报告不相加、显式零、缺失/null、负数/小数/超限/非数字、整批校验失败不污染此前证据、其他渠道与节点事件隔离。
- 媒体类型：带参数、大小写、参数含 json/eventstream；正常与读取失败、逐块即时交付、超过 8 MiB 的媒体、原头不变。
- 下游 MIME 识别：SSE 半帧继续缓存，JSON/媒体交付不被参数值误导；失败媒体不附加 SSE。门控关闭时包装器仍原样转交。
- 运行相关 Go 测试和根构建，复核格式、注释及差异；数据库独立的 service 回归可沿用现有外部 overlay，单独注明验证范围。

## 风险与取舍

不将 Dify 任意 metadata 或工作流节点用量累加为请求总用量；仅适配器已支持的 message_end 是本次补齐的权威位置。MIME 归一化只用于新流程内部判断，保留原始头及已有未知类型兜底，不因参数格式扩展新错误。无前端、relaykit、依赖或定价表达式修改。

## 实施结果

两项均已实施，未提交或部署。

- 修复前新增测试实际检出 Dify 的确认来源为 none/estimated 而非 upstream，以及媒体等待后续读取、正常响应被记为异常、大小写媒体丢失正文等问题；修复后相同夹具通过。
- Dify 在通用来源列表中加入受渠道及终止事件约束的 metadata.usage，沿用原子校验和既有最终用量构造。正常来源、尾帧写/刷新失败、无正文用户断开、零值、缺失及非法报告均通过真实本地 HTTP fixture 验证，测试不执行资金写入。
- 新增 StreamMediaType / IsStreamBinaryContentType，观察器、StreamWriter、OpenaiTTSHandler、WriteStreamTerminalError 使用同一基础类型规则。原响应头保持原字节；首块与后续每块均在下一次 Read 前写出，8388609 字节媒体正常完成；异常裸媒体正文后未插入 SSE。
- 所有新增方法、测试辅助类型/字段及关键分支均补充中文作用说明；没有修改非流式转换、relaykit、前端、依赖或数据库结构。
