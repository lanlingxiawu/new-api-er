# 错误日志清理优化方案

状态：两阶段代码已在本地实现；尚未部署，完整长稳压力与生产验收未执行。

错误日志清理采用 **2000 条起步、单批 5 秒，自适应升至默认上限 5000 条，可配置上限 10000 条**。起步批量和单批期限为用户明确要求。扩大批量与有效扫描起点、空洞跳过和状态显示已一同实现；同时加入默认关闭的同一范围自动续跑。两阶段均不新增表、列或索引，复用现有主键、维护连接和任务断点。在[既有有界扫描设计](error-log-cleanup-bounded-scan.md)上补齐空洞定位和任务状态恢复。5000 上限已做本地短测，仍不能据此承诺生产容量。

## 开始时间与零进度的关系

目前日期表示清理截止时间 `before`，业务语义是删除 `0 <= created_at < before` 的错误日志，并保留最近至少 24 小时。没有必填的开始日期并不是接口遗漏，也不会让数据库按时间从 1970 年逐秒遍历。

真正需要区分的是**删除范围的开始日期**和**后台扫描的起点**。修复前 `id` 模式从 `cursor_id=0` 开始，每次最多推进 65,536 个 ID；如果第一条现存日志在 ID 10 亿以后，会逐段经过不存在的数据。这与实际只有几千万行还是几亿行是不同维度的问题。`id` 候选查询不使用时间下界，单加一个开始日期控件不会改变这条扫描路径。本次由后台自动定位现存主键，定位失败才保留有界窗口回退。

起点应由后台根据实际存在的数据定位，用户继续只选截止日期。把“70 天前”硬编码成下界会留下更早的导入、回填或未清理记录，改变“清理截止时间以前全部错误日志”的语义。如果未来需要“只清理某个时间段”，可独立增加可选开始日期，并在确认框明确更早数据会保留；不将它作为本次修复的前置条件。

## Goals and Scope

第一阶段解决已复现的空洞耗时、零计数误导及大积压下批量过小：自动定位现存记录，探测失败时保留有界扫描；区分排队、执行、重试与状态读取失败；增加启动计划校验和任务状态写入的有限重试；增加错误日志专用的大批量配置与适配。保持手动继续、原始截止时间、快照上限、删除下界计数及租约隔离。

第二阶段解决任务总期限造成的反复手动继续：允许正常批间按时间片交接到后续任务。每次交接继续同一个清理范围，最终扫描完成后结束；数据库故障、人工禁用或失去租约不触发无限续跑。

不修改消费日志写入、计费、审计保留规则或财务清理，不增加并行删除 worker。ClickHouse 继续返回当前不支持的清理结果。自动定期清理新产生的日志、分表/分区与改变错误日志保留期不属于这次方案。

## 第一阶段的扫描流程

1. worker 正常领取并验证计划，仍使用单连接维护池。`time`、`error_time` 继续按现有索引和二元游标处理。
2. 对 `id` 模式，开始时尝试一次主键定位；以后只有上一窗口实际没有可见候选时才考虑探测。探测使用独立子 context，期限为 1 秒且不超过父 context 剩余期限；不能取消后继续复用一个已经失败的事务。
3. 探测成功得到 ID `n`，只在 `n > cursor_id+1` 时跳到 `n-1`，让下一批仍能读取 `n`。先按现有任务和租约条件保存断点，保存成功后才扫描后面的数据。跳过的 ID 数不计入扫描/删除条数。
4. 探测成功且没有返回行，说明当前快照上界内没有后续可见行；保存 `cursor_id=max_id` 后按原流程完成。超时、连接错误和取消绝不能解释为“没有数据”。
5. 探测超时则保留原游标，回到现有最多 65,536 ID 的有界查询。对失败探测设置 30 秒冷却，不在每个 200 ms 批次重复尝试慢范围查询。父 context 取消、禁用或失租则直接停止。
6. 正常删除使用原来的窄投影和类型/日期/快照二次校验，批量按下文错误日志专用上限执行。多个 DELETE 子语句仍在同一事务、同一个单批期限内；整个事务确认成功后保存绝对进度，再执行下一批。

探测 SQL 沿用已验证的主键访问形状，只取第一条实际存在的记录：

```sql
SELECT id, created_at, type
FROM logs
WHERE id > :cursor_id AND id <= :max_id
ORDER BY id
LIMIT 1;
```

这里不先找“下一个错误类型”：没有合适索引时，类型过滤仍可能让数据库在大范围寻找。该定位仅证明一段主键不存在记录，不决定哪些日志可删除。ID 与创建时间不保证同序，也不能遇到一条新时间日志就跳过后面的旧时间日志。

定位、候选扫描与 DELETE 的查询计划由数据库回归测试检查。大量未回收死元组可能使宽范围主键扫描超时，因此必须保留独立探测期限和有界回退，不能把所有批次改回无界的 `id > cursor LIMIT n`。

## 状态与恢复

启动计划校验、批前状态写入复用已有超时分类与 500 ms、1 s、2 s 退避，最多 4 次。永久 SQL 错误、索引失效、关闭开关、父期限结束和失租立即停止。状态写入重试成功以前不能开始下一个 DELETE。

状态 API 增加可选的 `progress` 对象，来源是现有任务 state JSON、凭据和租约记录。包含 `phase`、`checkpoint_at`、`heartbeat_at`、`lease_valid`，以及 `scan_mode,cursor_id,snapshot_max_id`。按用户要求，页面不提供诊断展开入口，不显示扫描模式、ID 游标或 worker 心跳时间；保留阶段、进度保存时间和状态读取失败提示。接口字段保持兼容。只查询主库的当前任务记录，不在页面每次轮询时访问日志大表。`phase` 使用固定枚举，例如 queued、preparing、scanning、retrying、saving；异常阶段仅返回受控的提示键，不返回 Go 错误或 SQL。

worker 将轻量阶段信息合入现有逐批 task state 更新；只在初始化或进入重试时额外更新，不为每条记录新增写入。`checkpoint_at` 以成功保存的凭据为准，`heartbeat_at` 来自租约，不能把“心跳存活”说成“有删除进度”。旧任务没有阶段信息时，根据已有状态展示通用说明，不猜测具体等待阶段。

前端 pending 显示等待执行，running 显示清理进行中；扫描数为 0 时仍可根据保存的阶段与更新时间说明正在定位记录。轮询失败显示“状态暂时无法更新”和上次成功读取时间，旧计数可以保留，但不把缓存的 running 继续描述为当前实时结果。不能用 ID 比例冒充按记录数量计算的完成百分比。

主库不可写时，不能保证立刻持久化失败终态。终态写入保留有限期限和租约校验，失败记录后台错误；API 如读到过期租约，可以提示任务失去心跳，但只有实际任务已被后台标记 failed 后才提供继续操作。沿用当前过期清理机制，不在 GET 中改状态或凭空恢复数据。无存活 master 时显示等待执行/恢复，不能承诺自动恢复。

删除数继续表达“至少已删除”。不引入跨库分布式事务，也不承诺重启后重建丢失的准确删除数。若将来确实需要精确可审计数量，需要独立设计日志库内与 DELETE 同事务提交的批次凭据；那会新增存储，不混入本轮轻量优化。

## 第一阶段的批量调整

在 `setting/operation_setting/data_cleanup_setting.go` 增加错误日志专用配置，经既有配置管理器和设置 API 持久化，不读取临时环境变量。第一阶段增加批量与单批期限设置，第二阶段增加续跑开关：

| 配置 | 默认与范围 | 作用 |
| --- | --- | --- |
| `error_log_batch_size` | 5000；允许 1～10000 | 错误日志每事务删除上限，未设置时使用 5000，不再继承通用 batch_size=100；保留小值供主动降载 |
| `error_log_batch_timeout_sec` | 5；允许 1～10 秒 | 错误日志每次批次尝试的事务期限，覆盖候选扫描、所有 DELETE 和 COMMIT；通用 batch_timeout_sec 默认仍为 3 秒 |
| `error_log_auto_continue` | false | 开启后，只在正常批间按保存断点交接下一段；故障仍停止 |

在日志维护设置表单中为 Root 提供这三个字段，普通管理员仍可按既有日志维护权限执行清理，但不获得修改清理资源参数的权限。三个新键登记到 `operations.logs` 的选项列表，用现有逐项保存入口；保留 `controller/option.go` 对整个 data_cleanup_setting 模块的 Root 写入限制。同步补齐 operations 默认值、section registry 的 props、表单校验、变更比较和保存后基线更新，非 Root 不渲染或提交这三个字段。

实际实现使用 `ConfigManager.RegisterSnapshot` 发布不可变配置快照，每批读取副本，避免在线修改与后台读取竞争。`ValidateErrorLogCleanupOption` 同时接入 `model.validateOptionValue`，拒绝越界数字和非法布尔值；控制器沿用已有本地化参数错误，不返回内部 Go 错误。历史无效值仍由 getter 的默认值/上限保护。没有新增环境变量或配置专用 API。

通用 `batch_size` 的默认值 100 和上限 500 不变；错误日志使用独立限额。仅提高配置值无效：当前设置 getter 会把值截到 500，`DeleteErrorLogCleanupBatch` 也会拒绝大值，`DeleteDataCleanupBatch` 在分发到计划错误清理前还有一次 500 校验。实现时必须同步修改专用限额，并把已带计划的错误清理分发放在通用 500 校验之前，由专用函数完整校验边界；财务、审计及旧无计划路径继续走原来的校验。

批量控制规则如下：

1. 每段从 `min(2000, 配置上限)` 起步；只有管理员明确设置更低上限时才使用该低值。正常情况下连续 10 批日志事务（包含 COMMIT）低于 `min(250 ms, 单批期限/4)`，且每批包含主库状态和进度保存的工作时间低于 500 ms、没有重试，才倍增。默认升档顺序为 2000 → 4000 → 5000；配置 10000 时按 2000 → 4000 → 8000 → 10000 升档。空窗口不作为增大删除批量的依据。
2. 日志事务超时按已有有限重试规则减半，允许降到 2000 以下；连续 3 批成功事务仍超过单批期限的一半（默认 2.5 秒），也在下一批减半并清空升档计数。状态或进度保存变慢、发生重试时不升档，且保存成功以前不得继续删除。较小批量是故障降载手段，不是亿级积压的默认起点。
3. 每批前重新读取配置快照。降低上限从下一批生效，提高上限仍经升档判定；单批期限更新也从下一批生效，禁用则停止新批次。错误日志默认单批期限改为 5 秒，批间等待仍为 200 ms，总期限仍为 1800 秒，不增加并行 worker。5 秒限制每次日志事务尝试，最多 4 次尝试及退避的总用时可能超过 5 秒；主库状态/进度保存、启动校验和交接保留各自的 3 秒期限，起点探测仍为 1 秒。
4. ID 模式候选预算改为 `min(10 × 当前删除上限, 20000)`，ID 区间上限仍为 65536，超时仍缩小区间。否则保持旧 5000 候选上限时，按均匀 60% 可删比例只能找到约 3000 条，设置 5000/10000 也无法充分利用。未处理的预读尾部不能推进游标或计入扫描数。
5. `time`、`error_time` 维持已有索引访问、时间边界和候选投影，候选上限为当前批量。`time` 模式包含非错误记录，实际删除数可低于上限；不为凑满批量做无界查询。所有模式都按 RowsAffected 计已确认删除数，配置值不是每批必删条数。

区分事务批量与单条 SQL 的参数规模：MySQL/PostgreSQL 每个 DELETE 最多 5000 个 ID；配置 10000 时分两条。SQLite 复用现有预览的每组 400 个 ID 策略，避免把数千个绑定参数直接放入一条语句。默认 5000 条在 SQLite 最多 13 条 DELETE，10000 条最多 25 条；每条都带原来的类型、时间和快照保护条件。候选读取、所有 DELETE 和 COMMIT 共用单批 5 秒期限，不给每条 DELETE 重新计 5 秒。

子语句之间不提交、不保存断点、不等待。任一子语句失败则整批回滚；只有整个事务确认成功才累计删除数和推进断点。提交结果不明确时仍保留原断点，重试不会越过未确认范围。跨库进度失败或提交确认丢失时，一次计数不确定窗口可能增大到当前批量；累计删除数仍只保证下界，不能伪造精确统计。

批量增大减少循环及固定等待开销，但完成时间仍取决于候选密度、SQL/提交、主库保存、重试及降档。默认上限的容量评估须使用真实提交、并发写入与查询；批量设置本身不能解决无 master、锁等待或空 ID 前缀。

## 第二阶段的自动续跑

自动续跑采用**同一清理凭据、不同系统任务 ID**。截止时间、max_id、扫描计划和断点都保持原值。正常批次保存成功后，如果距离本段总期限不足 20 秒且尚未完成，就尝试交接；发生查询/提交/进度错误时不自动交接，以免无限掩盖故障。

交接由主库一个不超过 3 秒的事务完成：校验原 task/runner/有效租约和凭据关联；将原系统任务记录为本段完成并注明 `continued`；释放它的 active_key；创建引用同一凭据和计划的新 pending 系统任务；更新凭据的 task_id/task_sequence/status；释放旧租约。新任务继续占用同一个唯一 active_key，其他清理不能在两个时间片间插队。事务失败整体回滚，不能先释放锁再补建任务。

handler 仅在交接事务确认成功后跳过原来的终态 defer，关闭本段连接并唤醒 runner；下一段按正常领取流程开始。若提交结果不明确，旧 task_id 的写入条件也不能覆盖已经关联新任务的凭据。禁止复用原 task_id 反复设置 pending，以免同一个 runner 身份让晚到写入误通过校验。

人工关闭 Enabled 后停止新批次，关闭 auto_continue 后本段不再自动交接；两者都不会扩大删除范围。错误日志快照已经扫完时最终 succeeded，不自动创建下一次保留期任务。进程重启后依赖现有持久化任务与租约恢复，丢失租约的旧任务继续走明确失败和手动继续。

## API Contracts and Data Flow

- `POST /api/data-cleanup` 仍接收 `{kind:"error_logs",before:<Unix秒>}`，手动继续仍接收 `{preview_id:<凭据ID>,resume:true}`。不增加必填开始日期。
- `POST /api/data-cleanup/preview` 保持旧客户端兼容；财务/佣金预览、类型和时间校验保持现状。
- `GET /api/data-cleanup?kind=error_logs&id=...` 保持 `{success,message,data}` 和既有字段，只为错误日志添加可选 `progress`。持续轮询保持稳定 run ID，不能因系统任务分段更换而丢失页面跟踪。
- 新建、继续、预览均要求 AdminAuth 与 `operations.logs` Edit，查询要求对应 View；金融类别仍按当前 Root 授权。PAT 使用现有 `ops:write`、`ops:read` 映射。
- 阶段 JSON 扩展旧客户端可以忽略；不修改上游维护的 `api.ts`、`http-client.ts` 等认证基础模块。业务错误用现有 helper 和本地化键，底层原因仅写后台日志。

请求创建 → 后台领取 → 校验原计划 → 自动定位或有界回退 → 小事务删除 → 持久化断点 → 完成/失败/正常交接 → 页面读取当前任务和凭据。只有成功持久化的进度能作为下段起点。

## Data Model and Index Design

不新增表、列、唯一约束或索引，不修改 `Log` GORM 标签，不在启动执行大表 DDL。继续使用 `logs` 主键、已有时间复合索引，`data_cleanup_runs` 主键和 task_id 唯一索引，以及 `system_tasks` 的 task_id/active_key 索引。租约查询用既有 type 主键并核对 task_id。

ID 定位与有界候选查询延续已批准的主键访问方式；纯定位不混入缺少索引的时间过滤。实际 DELETE 必须重新验证错误类型、非负时间、截止时间和 max_id。时间模式已经具备索引的，继续使用有时间上下界的二元游标查询。使用 GORM 构造跨 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+ 的查询，并记录各方言 EXPLAIN。

新增阶段信息放入现有 task state JSON，运行时节流/探测冷却仅保留在单 worker 内存；重启丢失冷却最多多一次探测，不影响正确性。三项新设置通过既有配置表持久化。自动分段增加系统任务历史，不增加每批历史记录；仍走既有历史清理规则，当前活跃任务及其凭据不能被历史清理删掉。

## Main Chain Impact

AI relay goroutine 新增同步工作为 0：不增加 DB/Redis 请求、不加锁、不注册新的 relay 中间件或回调。定位、删除、阶段更新与时间片交接全部在已有后台任务中执行。

独立连接无法隔离数据库磁盘、WAL 和索引竞争。方案通过单活跃清理、单连接日志维护池、短事务、批量上限、等待与失败退避限制占用；不把“后台执行”表述为共享资源零影响。Enabled 可立即阻止后续清理批次，自动续跑默认关闭。错误日志批量默认行为会由 100 调整为从 2000 自适应升至 5000，必须经过下述并发验收；财务、审计批量不变。

## Shared Resource Audit and Concurrency Analysis

| 资源 | relay 是否使用 | 处理 |
| --- | --- | --- |
| `logs` 表、主键/时间索引、日志数据库 WAL/磁盘 | 异步日志管道使用 | 维持串行小事务，保护近期写入，不改索引或写入链 |
| 日志维护连接 | 维护池独立，数据库实例仍共享 | 同时最多 1 个活动连接，定位和删除不并行 |
| `data_cleanup_runs`、`system_tasks`、`system_task_locks` | 不在每次 AI 请求路径上 | 点查/单行更新；仍使用现有租约和 active_key；不锁用户、渠道、钱包 |
| 主库连接池 | 与其他业务共用 | 本轮后台只保留一个执行者，重试间释放连接；分段事务限制为 3 秒，不跨日志 DB 调用 |
| 内存与 worker 池 | 共用运行时/任务调度 | ID 模式每批最多 20000 个窄候选、10000 个待删 ID；时间模式候选最多 10000；不读取 content/other，不按 AI 请求或日志条数创建 goroutine |
| Redis | 本方案不访问 | 无新增键、缓存、分布式锁或每请求开销 |

在 100k RPM（约 1667 请求/秒）下，每个 AI 请求新增 DB/Redis 调用、锁与 goroutine 均为 0。清理负载与请求数量独立：按默认 200 ms 等待约至多 5 批/秒；每批 ID 模式一次候选查询、时间模式至多两次游标查询，加日志事务提交及各一次主库状态/断点更新。默认上限 5000 时 MySQL/PostgreSQL 每批最多 1 条 DELETE，配置 10000 时最多 2 条；SQLite 相应为 13/25 条，但每批仍只提交一次，且受同一期限限制。方言设置语句与未变化 UPDATE 的租约确认查询另计。失败的定位探测至多每 30 秒一次、最多 1 秒；成功的空洞定位只在实际空窗口后发生。心跳沿用 20 秒节奏，自动交接每段一次。以上是调用规模分析，不是 100k RPM 实测认证。

## Implementation Files and Acceptance

第一阶段主要修改 `model/error_log_cleanup.go`、`model/data_cleanup.go` 的计划错误清理分发、`service/data_cleanup.go`、`controller/data_cleanup.go`、前端 `data-cleanup-api.ts` 与 `data-cleanup.tsx`；阶段返回使用单独 DTO，避免无关财务模型暴露字段。同阶段增加专用批量、单批期限配置及前端映射。第二阶段增加错误清理专用的主库交接事务和续跑配置；两阶段配置映射均涉及 `setting/operation_setting/data_cleanup_setting.go`、`service/settingsaccess/scopes.go`、前端 operations 的 `index.tsx`、`section-registry.tsx` 和 `maintenance/log-settings-section.tsx`。不改通用任务领取器与财务 handler 的行为。新增 UI 字符串实施时按项目 i18n 技能覆盖七种语言，后端提示同步实际 `i18n/locales/` 语言资源。

验收顺序与门槛：

1. SQLite、真实 MySQL、真实 PostgreSQL 验证新查询 EXPLAIN 为已有主键范围/索引访问，无大范围 Sort、Bitmap 或 Seq Scan；最低支持版本与当前生产架构分别记录。没有 schema 改动仍验证旧库升级和第二次启动不新增 DDL。
2. 复用首 ID=10 亿的 700 万行夹具，要求无故障暖库下 5 秒内开始实际删除，不再依赖空 ID 总跨度；同条件至少重复 3 次。新增中间大洞、空表和尾部消失场景，不能漏删或把 ID 距离累加成扫描数。
3. 重造未回收死元组前缀，探测必须在 1 秒子期限附近返回并退回有界路径；取消、禁用、失租均停止。不能以测试前 VACUUM 消除原失败条件。
4. 保留此前真实表锁、行锁、COMMIT SyncRep 等待、主库进度锁、真实租约到期例，验证范围正确、计数下界、状态诚实，旧 worker 不能覆盖新任务。
5. 分段交接覆盖正常、创建冲突、每一步回滚、提交确认丢失、崩溃、旧 worker 晚到写入、配置关闭和历史清理。全过程最多一个 active_key，原 before/max_id 不变，未成功保存的断点不前移。
6. 前端覆盖 pending/running、零计数但已更新断点、轮询失败恢复、旧版本缺少 progress 字段、自动换 task ID、手动继续；浏览器通过真实后端确认最终日期、状态与删除范围。
7. 用 100 条作旧版对照，实测 2000/4000/5000/10000 批量，并覆盖故障降档到 1000 的恢复；在约 81 条新日志/秒的日均量、500 条/秒及约 1667 条/秒压力档并发写入和查询。每档至少持续 10 分钟并使用真实提交，分别记录纯日志事务耗时和包含主库保存、休眠的端到端吞吐，不能用外层回滚微基准宣称清理速度。数据覆盖约 60% 错误、稀疏错误、突发集中错误及受保护消费/近期记录。
8. 新默认 5000 的并发门槛：保护记录与消费对账不变，无新增请求或日志写入失败、无持续增长的日志队列积压；相同写入压力下日志插入及近期读取的 P95/P99 相对不清理基线增幅各不超过 10%，日志清理事务 P99 低于单批期限的一半（默认 2.5 秒）。同时报告绝对毫秒值、清理吞吐、WAL 等待、CPU 和连接数；若不达标，依据结果选择更低的可用上限，不能在验收中继续延长 5 秒期限宣布通过。完整 relay 验收还需独立报告响应延迟和错误率，SQL 压测不替代完整链路压测。
9. 多语句批次验证 SQLite 的 400/401/5000/10000 边界、MySQL/PostgreSQL 的 5000/5001/10000 边界：后一个 DELETE 注入错误或超时，之前子语句必须整体回滚，主库断点不变；真实 COMMIT 确认丢失和主库保存失败仍保证删除数下界。测试不得误把每个 SQL 分块当作一次提交，或在分块之间休眠。
10. 验证默认从 2000 起步、专用设置默认上限 5000、可配置上限 10000、单批默认 5 秒，以及在线降档/升档、超时缩批和连续慢批缩批；多语句共用同一个期限，不能每条语句重置。批量放大后候选预读尾部仍留在断点以后，候选不足时不能漏扫或提前完成。原财务/审计默认值及 500 上限保持，通用单批默认仍为 3 秒，旧无计划错误路径也不因通用校验放宽而绕过限额。

## 实际实现

- `model/error_log_cleanup.go`：主键定位、最多 20000 个 ID 候选、最大 10000 条事务批量；MySQL/PostgreSQL 每条 DELETE 最多 5000 个 ID，SQLite 每条最多 400 个，仍共用事务和期限。
- `service/data_cleanup.go`、`service/error_log_cleanup_progress.go`：2000 起步、快速升档、超时/连续慢批缩批、在线配置快照、定位冷却、有限状态/计划重试。进度保存重试不会重复发起 DELETE；初始化计划提交确认丢失后，仅接受同一租约下完全一致的已保存计划。
- `model/error_log_cleanup_continuation.go`：原任务结束、新任务创建、凭据关联及租约释放在一个主库事务中完成。检查已保存的 before/max_id/cursor/计数，旧任务无法写入新凭据关联。
- `controller/error_log_cleanup_progress.go`：在一条主库 JOIN 查询中读取凭据、当前任务及租约，避免分段交接被误报成整体完成。心跳时间和断点时间分别返回，不访问日志库。
- 日志维护页面增加 Root 专用配置、阶段展示、状态读取失败提示；初始查询失败时阻止再次提交。诊断信息展示已按用户要求移除。七个语言文件各增加相同的 15 个键，原有翻译未改动。受保护的五个认证/HTTP 前端文件没有修改。

## 验证与发布边界

保留模型、服务、控制器、配置及页面回归，覆盖定位回退、慢批降档、在线配置、进度写入失败、提交确认丢失、分块事务回滚、租约替换、自动交接与旧 worker 拒写。独立主库/日志库不能提供跨库精确删除计数，接口继续只承诺删除数下界。
