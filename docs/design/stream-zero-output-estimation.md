# 新流程零输出用量补估

最新确认：本文件历史 100 MiB 大小预算已统一提升为 **200 MiB**，其余规则保持，见 [大小上限记录](stream-size-limit-100mib.md)。

2026-09-15 用户确认：已有输出内容且上游输出用量为零时补充本地估算，包括最终显式零。输出大于零保持上游值，无内容保留零。输入、缓存等确认字段保持不变，混合用量标记 mixed。

## 生命周期与范围
通用、Claude 专用及 Realtime 在唯一结算前应用补估。正常完成与上游异常采用成功交付内容，用户断开采用已收到内容（包含失败写出分片）。上游异常无有效交付的原免收费资格不变。接收估算继续累计，不因提前收到输入/零输出证据而停止。原始证据保持零，估算独立记录。裸媒体不按字节估算，Realtime 使用已有音频计量。

## API / 模型 / 配置 / 错误
没有新增 API、表、迁移或配置；沿用新流程开关、一次结算、资金和成本队列。需同时更新嵌套 BillingUsage，防止实际计费再次采用内部零输出；保留缓存和输入细分。异常及超时分类不变。

## Main Chain Impact / Shared Resource Audit
无新增网络、DB、Redis、工作协程或跨请求锁。请求局部接收计数器持续工作，边界仍为 100 MiB/128 个工具；补估只在终止阶段执行。资金、令牌和日志/成本资源沿用现有调用次数与异步队列。

## Concurrency Analysis
100k RPM 下增加的 DB/Redis 调用与协程均为零。此前已有确认字段后的接收计量不再提前结束，因此该类流每帧增加既有增量估算的 CPU/分配成本。估算状态随尝试/轮次清理，无整段正文新增缓存；需部署环境补测 p99/GC。

## 测试
先写用例：中间与最终零、显式全零、非零、无内容、写失败、正常/异常/超时、Claude/Gemini/OpenAI 嵌套计费与缓存、Realtime 音频以及重复结算。测试采用本地帧和资金接口夹具，不调用真实上游。历史“显式零永不补估”断言按此次合同更新。

## 实现结果
- `SupplementStreamZeroOutput` 在唯一结算前执行；以真正参与计费的 effective BillingUsage 判断零/非零，而非可能已经被适配器估算过的外层字段。确认输入与缓存保留，输出补估后原始证据仍为零。
- OpenAI、Claude、Gemini 嵌套计费对象均复制后更新输出及合计；原对象不被修改。正常流程保留原始嵌套输入模态；没有嵌套对象时复用确认字段构造。Claude 全零确认对象在补估后建立对应计费载体。
- 通用接收估算在提前出现确认字段后继续累计。断开采用接收文本，其他结算采用成功交付文本；Realtime 同时保留原音频计量，并逐轮标记/汇总 mixed。
- 正的输出确认值保持原值；Claude 原“正常但非最终正用量取估算最大值”分支也按此次约定停止覆盖非零输出。上游异常无有效交付继续不收费。
- 新增截图场景回归：Gemini 首帧输入 15、输出 0、缓存 4，后续正文到达后写出失败；最终输入仍为 15、缓存仍为 4，输出为收到正文的本地估算，来源 mixed。
- 新增嵌套计费回归：外层输出已有估算 99、内部真实计费输出仍为 0 时，补估正确落到内部对象，不再被外层非零值提前跳过。
