## 2. A：PostgreSQL 统计写入

### 实现边界

仅修改 `model/business_stats_buffer.go` 中四个 `upsert*DailyStatTx` 的更新表达式：

- 所有“读取当前目标行”的列都使用能够按方言引用目标表的 GORM 表达式，包括金额、计数、成本比例、渠道名称和最后时间。
- 参数继续绑定；不拼接未经验证的表名或值，不硬编码测试表名或 PostgreSQL 引号。
- 保留当前原子增量更新，不改为先 SELECT 再 UPDATE，不增加锁或事务往返。
- 保留 `tx.Table(...)` 的测试与调用语义；验证普通表名、动态表名及实际使用的命名策略。
- 保留渠道名仅为空时补入、最后时间取最大值，以及正负增量的现有业务语义。

### 数据流与一致性

消费/冲销 → 现有缓冲与去重 → 后台批量明细写入和统计 upsert → 同一事务提交 → 管理报表读取。

修复 SQL 引用，不改变入队、批量大小、冲销、幂等键或失败重排逻辑。必须逐一核对四个函数的调用点，确认没有把后台处理搬到 relay goroutine。

已证实的是成本明细/统计事务失败，不能据此推断用户钱包退款失败。钱包余额、成本明细、佣金明细和汇总要分别核对。

### 模型、索引与历史数据

不修改模型或索引，核实以下既有冲突键确实有对应唯一约束：

- 平台统计：`(stat_date, channel_id)`。
- 员工佣金：`(stat_date, employee_user_id)`。
- 客户佣金：`(stat_date, employee_user_id, customer_user_id)`。
- 重置周期佣金：`(reset_started_at, stat_date, employee_user_id)`。

不增加扫描查询。若真实 schema 缺少约束，作为独立迁移问题处理，先做重复数据检查和 schema 演练，不能夹带自动建索引上线。

发布前只读核对：失败时间段、队列/回退记录、明细缺口、汇总差额、重试积压。修复后观察既有重试是否恢复。`log_id` 为空或非正数的成本记录没有相同去重保证；不能盲目重放，不重复执行钱包退款。不承诺修复代码后历史数据自动完整。

### 验收

真实 SQLite、MySQL、PostgreSQL 均验证四类函数首次插入、冲突更新、零增量、正向加负向冲销、空/非空渠道名、乱序时间、不同聚合键和同键并发累加。固定输入必须得到精确预期金额与计数。

用故障注入检查明细插入后统计失败时整笔事务回滚；恢复后重试应只产生一份有效明细及正确汇总。重复有效 `log_id`、无去重键记录、批内重复分别测试，不能混用预期。原 PostgreSQL 退款链路重复失败用例应恢复通过，并另核钱包与台账。

## 3. C/D：请求体校验

参考现有[请求体治理方案](relay-body-memory-governance.md)。这次修复校验语义，不改变存储预算、落盘阈值或容量不足处理。

### 单文档 JSON

在 `common/json.go` 的 codec 实现边界增加请求体专用的严格解码能力，由 `common/gin.go` 的磁盘 JSON 路径调用。保留通用 `DecodeJson` 的既有语义，避免影响上游响应和其他控制器调用；不扩展 relaykit 的公共 Codec 接口。

一次解码后，检查同一个 decoder 的已缓冲内容及底层 reader 的剩余内容：只允许 JSON 空白字符和 EOF。遇到第一个非空白字节立即拒绝，不通过解析第二个大型对象来验证结束，也不把磁盘请求体整体 ReadAll 回内存。必须保留读取错误，不将 `n > 0` 同时返回错误的 reader 当作成功 EOF。

该检查使用固定大小扫描缓冲，额外空间与尾部长度无关；尾部全为空白时仍需扫描，额外 CPU/I/O 是 O(尾部长度)，受现有请求体总大小限制。JSON decoder 自身仍可能缓冲首个值，不能声称完整 DTO 解码是恒定内存。

成功后按现有约定 Seek 到起点并恢复 `Request.Body`，保证渠道重试重放一致；失败沿既有清理路径释放存储，不能新增泄漏或重复扣减。

### 空值与媒体类型

`relay/helper/valid_request.go` 的 embeddings/rerank 在解码前构造 DTO，或在解引用前检查 nil，复用既有必填字段错误。有效请求及显式零值语义不变。

`null` 和未实际解析出必填字段的请求必须返回受控校验失败；不能进入上游调用。空指针保护始终保留，不提供重新启用 panic 的开关。

本轮不在共享 `UnmarshalBodyReusable` 中全局拒绝所有未知 Content-Type，因为该函数还服务表单、多部分和其他兼容路径。若要统一媒体类型策略，须先完成调用点清单和兼容性设计。相较审计记录中的初步建议，本方案收窄了该改动边界。

### 配置与回滚

新增 `performance_setting.strict_request_json_enabled`，默认 `false`，控制磁盘请求体新增的尾部校验。默认关闭是发布兼容策略，并不代表缺陷已经在运行环境消除；验收必须覆盖打开状态，灰度后显式开启才算部署修复完成。

配置通过现有 ConfigManager 快照发布、设置 API 和 `operations.performance` 白名单保存，不使用环境变量或请求级 DB 读取。`common` 不能反向导入 `setting`，沿用现有“setting 发布到 common 的只读配置快照”模式，不新增临时可变全局 bool。非法配置不部分发布，单键/分组保存均验证。

每次校验只读取一次快照；配置变更影响后续校验，不在同一次解码中途切换。关闭时恢复旧磁盘尾部行为；内存路径已有严格校验和空指针保护继续存在。该开关仅作为兼容回滚手段，不用于宣称旧行为安全。

不新增配置 UI；通过既有受保护设置接口操作。新增内部解析错误须经过现有 relay 错误映射；如确需新增用户可见消息键，同时补齐后端中英文。

### 接口与错误契约

不新增或改名 API。有效 JSON 请求的结构、字段、状态码、流式输出、usage 与计费保持不变。

新增严格校验只拒绝本来就不是单个完整 JSON 文档的输入。对客户端返回既有 relay 参数校验错误（400），不得转换成上游 5xx、触发渠道惩罚或额外上游重试；校验失败的路由应验证预扣前拒绝或既有退款收口，而不是直接假设所有入口顺序相同。

完整路由分别验证普通 OpenAI 分发和 Gemini URL 取模型入口。前者通常已经提前校验 JSON，后者不能只靠前者的测试证明安全。返回原始解码错误、请求内容或凭据到日志/响应均不在方案内。

## 4. E：分组重试状态接口授权声明

接口：`GET /api/option/group-retry/status?scope=system-tuning.group-retry-times`，返回结构沿用[原设计](group-retry-auto-protection.md)。

源码 `middleware/access_token_routes.go` 明确规定 fork 扩展接口使用后台会话；相邻的熔断、连接池和错误显示状态接口也声明为 `accessTokenSessionRule`。因此本次给该路径补同样声明，保留路由的 `AdminAuth()` 与 `RequireSystemSettingsScope(authz.ActionView)`。

这修复的是“路由策略未声明”，不是默认赋予 PAT 读取能力。带 `option:read` 的 scoped PAT 和 legacy PAT 都按 session-only 规则拒绝；后台会话仍须通过角色和系统设置权限。legacy PAT 从遗漏声明时的兼容放行变为明确拒绝，是需要在发布说明中记录的授权收紧。若将来要求 PAT 调用，应单独批准权限契约。

覆盖匿名、普通用户会话、管理员缺少设置权限、获准管理员、root、有/无 option:read 的 scoped PAT、legacy PAT；校验实际中间件链及响应码，不能只断言 map 中多了一个 key。

### 实施中补充：构建工具链

固定 `GOTOOLCHAIN=go1.26.0` 后复扫发现 34 条标准库符号可达告警。先前通过 `go run govulncheck@...` 启动扫描时，工具自动切换了 Go，不能用该结果证明 Go 1.26.0 制品安全。

## 8. Concurrency Analysis

30k RPM 约 500 RPS；100k RPM 约 1667 RPS。上述修复新增 DB/Redis 调用均为 0 次/relay 请求，新增 goroutine 为 0；这不代表系统原来没有这些调用。

C 最坏增加一次尾部顺序扫描。每秒增量读取约为“进入该路径的 RPS × 平均剩余尾部字节”，不能只按固定一次分支估算成本。内存请求不新增尾部扫描；磁盘模式需要分别测正常小尾部和接近请求上限的空白尾部。

A 恢复写入后，积压重试会重新消耗 DB 容量；即使 SQL 往返数量没增加，恢复期负载也可能上升。观察批量耗时、排队、锁等待、连接池及 relay p95/p99，保留现有限速/熔断，不自动放大 worker 数。

本机几秒组件结果不能证明完整主链可承受 100k RPM。F 的复测采用独立客户端、Linux 网关和可控上游，使用真实代表性的内存/磁盘阈值、请求尺寸和并发长流，记录从发送计划起包含客户端排队的端到端延迟，并同时报告实际发送率及服务完成率。
