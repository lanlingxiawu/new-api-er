# 使用日志后台导出压测记录

日期：2026-10-16。范围：当前工作区 CSV.GZ 后台扫描与写入、共享日志连接池、Redis 并发名额。未修改生产逻辑。

## 环境与方法

- 主机：AMD Ryzen 7 8700G，8 核 16 线程；Go 1.26.0，Windows。Docker 可用 16 个逻辑 CPU、约 23 GiB 内存。
- 数据库：独立 MySQL 8.0.46 与 PostgreSQL 15.19 容器，另设 Redis 7。容器仅绑定本机地址，不访问现有开发数据库。
- 每种数据库插入 20 万条、单条约 1 KB 的合成日志，时间分布约 14 小时。正文有大量重复文本，不能用本次压缩比预测真实业务文件大小。
- 并发查询：4 个固定工作协程，每个每 20 ms 发起一次查询，目标合计约 200 次/秒。按用户与时间索引倒序取 20 条 ID、时间，不执行完整日志列表、鉴权、中继或计费。每次查询限时 1 秒；协程忙时不会无限排队，所以目标速率不是保证达到的开放式负载。
- 每种数据库依次运行：5 秒查询基线；单任务按默认批大小 3000、批间等待 100 ms、行速率上限 20000 导出；4 任务关闭主动休眠并放宽行速率上限；单连接池下按默认节流导出。
- 压测直接调用真实扫描、脱敏与 CSV.GZ 写入逻辑。4 任务场景故意绕过任务创建入口的并发名额，以观察放宽限制后的资源开销；它不代表默认配置允许 4 个任务。
- 另用 32 个并发请求调用真实 Redis 名额获取逻辑，名额上限设为 1；验证只有一个请求成功。
- 每个文件在计时结束后实际解压、解析 CSV，并核对 20 万条记录与表头。计时包含查询、渲染、压缩和节流，不包含造数及验证解压。
- 每 20 ms 采样 Go 堆和连接池占用。堆内存不是进程 RSS，也不包含数据库内存；短于采样间隔的峰值可能遗漏。

|---|---:|---:|---:|---:|---:|---:|

四组并发查询分别完成 969、2704、984、3018 次，错误数均为零。前 3 组无连接池等待；单连接组累计发生 2412 次等待、总等待时间 15.648 秒（各协程等待时间累加，不能当成墙钟时间）。每份压缩文件约 1.75 MB，全部通过解压与行数检查。

32 个并发名额请求：成功 1 个、拒绝 31 个。

四组并发查询分别完成 999、4960、1372、8563 次，错误数均为零。前 3 组无连接池等待；单连接组累计发生 6525 次等待、总等待时间 20.032 秒。每份压缩文件约 1.75 MB，全部通过解压与行数检查。32 个并发名额请求同样只成功 1 个。

两种数据库所有压测断言通过：每份导出文件包含预期的 20 万条记录，无并发查询错误，并发名额没有超发。总计验证 12 份导出文件、240 万条导出记录及 23569 次并发索引查询。

## 结果解释与边界

单连接场景仍能完成导出和并发查询，没有因持有数据库游标跨越压缩或节流而锁死。4 任务会占满 8 条连接，堆内存也明显增加，不能据此建议直接提高生产并发上限。

PostgreSQL 在 4 任务放开限速时，查询 P95 从基线 12.293 ms 增至 31.673 ms；单连接池下导出耗时由 24.818 秒增至 43.028 秒。资源竞争确实存在，因此保留默认单任务并发和节流更稳妥，“后台导出不阻塞下载连接”不等于“完全不影响数据库”。本次不据此改动生产配置。

这是单机、单轮、固定合成数据的核心作业压测，数据库缓存逐步变热，没有在每组之间清空缓存。后续场景查询延迟低于首组基线不能解释为导出改善了数据库性能。

测试进程没有启动生产 CPU 采样服务，CPU 软硬阈值设为 99% / 100%；因此本次验证了批间节流与行速率控制，未验证真实 CPU 压力触发的自动退让。没有真实上游 AI、中继流式连接、异步日志写入混合负载、HTTP 下载慢客户端或浏览器负载，不能据此宣称达到 3 万或 10 万 RPM 中继容量。SQLite、ClickHouse 未参与本轮压测。

本地复现材料：`.git/export-load-harness.go`、`.git/export-load-mysql.log`、`.git/export-load-postgres.log`。测试代码临时放入 `model/zz_export_load_local_test.go`，通过 `EXPORT_LOAD_TEST=1` 启用，且强制要求 DSN 指向命名为 `export_load` 的独立数据库。测试完成后移除临时测试文件并清理专用容器。
