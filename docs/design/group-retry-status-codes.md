# 分组重试状态码

状态：用户已确认；已实现并部署测试服，功能与 mock 压测验证通过。

## 目标和范围

在现有“分组重试”页面中，为每个分组增加状态码规则。
重试次数继续使用 GroupRetryTimes，用户次数 > 分组次数 > 全局次数的优先级不变。
状态码决定“什么错误允许重试”，次数和时间预算决定“还能重试多少次”。
不新增按用户状态码配置、不改渠道自动禁用配置、不改变计费及超时退款策略。

每行展示：分组、重试次数、状态码模式、状态码输入框、删除按钮。
状态码模式为“继承默认”“自定义”“不按状态码重试”：

- 继承默认：普通中继使用全局 AutomaticRetryStatusCodes；任务提交保留其原有规则。
- 自定义：如 `429,500-503`，替换该分组默认的状态码集合，不与默认集合合并。
- 不按状态码重试：状态码集合为空。仅针对 HTTP 状态码分支，
  不改变已有的内部渠道错误特殊处理；如需禁用整个分组重试，仍使用次数 `-1`。
- 删除行恢复继承，新增行默认继承，避免误改现有行为。

## 配置与数据模型

新增配置模块 `group_retry_status_setting`，使用 ConfigManager.RegisterSnapshot：

| 字段 | 类型/默认值 | 作用 |
|---|---|---|
| enabled | bool / false | 启用分组状态码覆盖，关闭立即回到原逻辑 |
| rules | string / `"{}"` | JSON 对象，分组名 → 状态码范围字符串 |

例：`{"vip":"429,500-503","batch":""}`。
字段缺失表示继承；显式空字符串表示不匹配任何状态码。禁止 null、数字、数组及非对象根节点。
持久化键为 `group_retry_status_setting.enabled`、`group_retry_status_setting.rules`。
GroupRetryTimes 结构和持久化键不改，无新表、无列迁移。

启用开关默认关闭，用于回滚该中继行为变更；关闭不删除规则。
规则在配置写入或热同步时解析、规范化、编译，不在中继请求中解析 JSON。
发布包含 enabled 与编译规则的单份不可变快照，发布后不得修改 map 或状态码集合。

## API 契约与权限

复用已有 GET /api/option/、PUT /api/option/、PUT /api/option/group，不新增路由。
使用现有 AdminAuth 与 `system-tuning.group-retry-times` 的查看/编辑权限；
扩展该 scope 的键和模块字段白名单，其他设置权限不得写入新配置。
根管理员沿用现有权限逻辑。

分组保存示例：

```json
{
  "scope": "system-tuning.group-retry-times",
  "module": "group_retry_status_setting",
  "values": {
    "enabled": "true",
    "rules": "{\"vip\":\"429,500-503\",\"batch\":\"\"}"
  }
}
```

返回沿用已有 `success/message/data` 结构。单键和模块保存使用同一校验逻辑，
都必须先验证整份候选规则再写库/发布，不接受部分有效、部分失效的更新。
次数与新规则属于两个已有/新增配置模块：界面分别提供保存状态，
不得用一个“保存成功”掩盖另一个模块保存失败。保留未保存草稿并允许重试。

## 数据流及核心规则

管理员编辑 → 前端校验 → 权限/后端校验 → options 持久化 →
发布编译快照 → 中继错误发生 → 读取失败尝试的实际分组 → 状态码判断 →
原有次数、请求总时限、重试最小预算及总调用上限约束 → 重试或返回原错误。

状态码按现有错误对象的 StatusCode 判断，包括已有渠道状态码映射结果，
不额外解析原始上游正文。自动分组使用“刚刚失败的那次尝试”的实际分组，
不能使用用户注册分组、字面量 auto 或预先准备的下一分组索引。
下一次实际切换分组后重新取对应规则。
无实际分组或规则缺失时回退现有逻辑。

自定义规则不应绕过已有安全边界：

- SkipRetry、指定渠道/探测约束、亲和性禁止重试等现有提前返回分支保留。
- 客户端已断开、流已交付且由流式生命周期接管、时间预算耗尽，不因配置而重试。
- 2xx 不重试；504、524 仍是不可重试状态码，`bad_response_body` 禁止规则保留。
- 配置 `500-599` 时明确提示 504、524 被系统排除；不偷偷重试超时。
- 内部 ChannelError、非 HTTP 状态码等特殊路径保持原处理，不受此功能扩大或缩小。
- 任务自定义状态码仅处理可重试的上游错误，不将本地参数错误、SkipRetry 变为可重试。
  缺省规则不改变任务现有的 429、307、5xx 等处理顺序与结果。

校验复用 ParseHTTPStatusCodeRanges：100–599，逗号/中文逗号、
空格、单码、闭区间；排序合并重复和相邻区间。
99/600、逆序、字母、多重横线拒绝。空白字符串等价空集合，
只有分组键缺失才表示继承。限制 rules 为 64 KiB、最多 256 个分组、
每组最多 128 个输入片段，以约束配置解析和快照内存。
分组删除后孤立规则不应用于其他分组；界面保留显示并允许删除，避免静默丢配置。

## 错误处理及交互

无效输入定位到行；保存中禁用该模块保存按钮；失败保留草稿。
系统级解析/写库错误记录具体内部原因，客户端返回 i18n 的可操作说明，
不返回 Go 原始错误。业务错误使用 ApiErrorI18n，按项目约定处理不可恢复 DB 故障。
热同步遇到非法数据时保留上次有效快照并限频记录系统错误；首次启动无有效快照
则关闭覆盖、回退既有策略。配置失败不得向 relay 传播错误。

界面复用 group-retry-section.tsx 的现有 Input/Select/按钮区域。
前端文案覆盖七个 locale，后端覆盖实际使用的 en/zh-CN/zh-TW YAML 与 Msg 常量；
不改已有认证文件或增加依赖。

## Main Chain Impact

仅错误后的重试判断同步读取不可变快照、查实际分组和状态码。
可将每组编译成固定 HTTP 状态码位图：判断为 O(1)，不分配切片，
不查询 DB/Redis、不启动 goroutine、不增加网络调用。
持久化、校验和编译发生在管理请求/现有配置同步任务。
enabled=false 或无覆盖时沿用现有策略。

## Concurrency Analysis

30k RPM 约 500 请求/秒，100k RPM 约 1667 请求/秒。
每个错误判断增加一次快照读、一次 map 查找和一次位图查询，额外 DB/Redis 调用 0，
跨请求锁 0、goroutine 0；正常成功请求不进入新增状态码判断。
快照编译开销受配置大小限制，仅配置变化时产生。现有请求总预算和尝试上限继续生效，
不允许状态码配置造成无上限重试。

## 测试计划（实现前先写）

1. 解析边界：99/100/599/600、单码、范围、逆序、空白/中文逗号、重复、
   null/错误类型、空对象、显式空规则、大小/条目上限。
2. 开关关闭和无规则时，普通中继及任务入口与原实现逐项一致。
3. 分组 A 仅 429、分组 B 仅 500：同码不同分组行为不同；未命中不重试。
4. 自动分组切换用失败尝试的实际分组；用户重试次数优先级保持原样。
5. 504/524、2xx、SkipRetry、本地参数错误、断开、指定渠道、流已交付、
   预算耗尽均不能由自定义范围绕过。
6. 配置热更新并发读取，非法保存/同步保留有效快照；可运行环境执行 race。
7. 管理员权限矩阵、单键/模块接口同等校验，默认配置和旧数据无需迁移。
8. httptest 上游计数：429→200、500→200、永远失败、禁止码；
   核对实际调用次数及只结算一次，无错误扣费/重复退款。
9. Go 相关包与全量测试、vet；前端 typecheck/lint 与七语言检查。
10. 测试服隔离分组 mock 功能及固定速率回归，记录开关恢复与夹具清理。
