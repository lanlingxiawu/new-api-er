#### IP 监控实际覆盖

`service/auditsecurity/ip_risk.go` 关联五类规则：

* 新登录来源：账号存在至少一天前建立且近 30 天活跃的来源基线，成功登录使用未见过的 IP；没有成熟基线时不触发。
* 连续登录失败：同账号标识（无法识别账号时可能退化为来源）5 分钟内错误凭据/验证码达到配置阈值，默认 5；不是全局恶意 IP 名单。
* 密码喷洒：同 IP 5 分钟至少 20 次有效失败且涉及至少 5 个账号标识。
* 连续失败后成功登录：同账号前 15 分钟失败达到配置阈值后成功登录，默认阈值 5；当前存在上表的失败证据保存缺陷。
* 会话刷新凭据重放：会话系统明确判定 refresh reuse。不是仅凭 IP 变化推断会话被盗。

这些认证关联在 `Normalize` 中整体限定为 Root 可见。检测与额外认证采集是独立开关，默认均关闭；失败登录和重放等新增采集依赖 capture_enabled，suspended 会停止采集/检测。实际运行实例是否开启本轮未核验。

普通审计已提供“IP 风险”筛选与风险标记。标记按 event_id/IP/事件时间关联已保存证据，不会把某 IP 的全部正常操作统一标红；误报不作为活动风险，已解决显示中性状态。历史回填只能恢复保留下来的证据，未标记不代表安全。

`audit/lib/ip-location.ts` 仅在交互时查询国家/地区/城市供查看，监控规则未使用归属地。当前没有异地/跨国跳变、不可能旅行、VPN/Tor/代理识别或 IP 信誉库规则。新 IP 来源不等同于异地登录。截图中的 127.0.0.1 若不是本机测试，应先核验反向代理真实 IP 传递与 `TRUSTED_PROXIES`；采集使用 c.ClientIP()，不能据截图认定线上代理配置已经错误。

渠道多密钥操作改为提交后记录结果，审计执行在既有轮询锁释放之后。渠道更新、用户更新记录已提交的修改，即使后续缓存/权限/会话清理失败。密码重置提供内部 committed 结果，保留旧调用方的错误返回合同。

元数据仅保留固定动作、ID、角色、字段名、明确布尔值、数量和额度前后值。密码、密钥、请求/响应正文、UA、配置/URL 原文不会复制入告警库。账户关联使用 `SessionSecret` 加独立用途前缀的 HMAC；多节点需要相同稳定的部署密钥。

来源数据库先只投影检测使用的 `op` 和 `admin_info`，排除 `changes` 等展示成员，再按字节检查 16 KiB 上限；检测元数据本身超限时替换为 evidence_incomplete 标记。大体积展示差异不占检测预算、不进入监控内存，也不改变变更字段、目标、数量或操作者归因。普通无关事件不查询历史、不写监控回执。相关历史按操作者、账户或非空 IP 分别查询，窗口为对应规则的 5/10/15 分钟，每个索引范围最多取 1,001 条并保留 1,000 条。登录失败有两个范围，合并后按 event_id 去重；其他规则最多一个范围，session reuse 不需历史。超限继续检测独立高危操作，计数为有界样本下界，并置健康状态 history_truncated。不会静默将有缺口的覆盖说成完整覆盖。

## 权限与接口合同

入口：审计日志 → 安全监控。普通管理员需要同时具备 `audit:read` 与 `audit_security:read`；处理告警另需 `audit_security:manage`，并使用浏览器登录身份。Root 隐式授权。普通用户没有管理端监控入口。

Root/未知操作者、Root/未知目标角色的用户管理证据只允许 Root 查看。认证关联可能包含匿名尝试，整组关联保持 Root 可见。列表、详情、统计和处理使用同一可见性过滤；Root/未知角色的人工处理历史也不向普通管理员展示。指定通知联系人仅收到告警 ID、级别、版本，查看证据仍需控制台权限。

## 通知

与告警同事务创建 outbox，单 worker 每轮最多发送 3 条；单次 8 秒上限，失败最多 5 次，间隔为 60×尝试次数² 秒。目的地变更后旧目的地待发任务取消。超过 5 分钟的历史回填不发送通知。发送结果可在告警详情查看。

邮件读取现有 SMTP/Resend 配置，使用独立、有超时和取消能力的连接，不改变原有邮件发送代码。Webhook/Resend 使用独立 HTTP transport，实际拨号 IP 使用现有 SSRF 网段规则校验；Webhook 不跟随重定向。SMTP 允许既有管理员配置的内部邮件服务器。

网络投递与数据库提交不是原子操作：响应丢失或投递后进程退出可能重发。Webhook 带稳定 Idempotency-Key，接收端应去重；不承诺邮件恰好一次送达。重试耗尽明确标记 failed，不把缺少配置当送达。

## 数据模型、索引与迁移

新增主库表：`audit_security_events`、`audit_security_alerts`、`audit_security_actions`、`audit_security_deliveries`、`audit_security_states`、`audit_security_baselines`。文本结构用 TEXT，业务布尔值在代码中赋值；不依赖 MySQL TEXT 默认值或数据库特有 JSON 运算。现有 audit_logs 不新增列。

| --- | --- |
| audit_logs 时间游标 | 复用 `(created_at,event_id)`；ClickHouse 同排序键 |

### Shared Resource Audit

* Redis：不使用，不增加命名空间或连接，不占用 relay 的缓存/限流键。
* DB：检测写独立监控表，读既有 audit_logs；不查询/锁定 users、channels、tokens 来做检测。配置保存沿用管理端 options 写入。独立池不修改 DB/LOG_DB 的容量。
* 物理数据库：仍共享服务器 CPU、I/O；SQLite 同文件还共享文件写锁。独立池不能证明物理资源零影响，因此批次、队列、超时和暂停开关均有上限。
* 内存/协程：固定队列、单执行 worker、固定证据/历史上限；不使用 relay worker pool。健康计数和数据库句柄仅供监控访问。
* 网络：Webhook、Resend、SMTP 均使用独立连接，不占用转发 HTTP transport。

### Concurrency Analysis

30k / 100k RPM AI 请求的新增每请求成本仍是零；监控负载取决于管理和认证审计量。每轮最多读取 500 条来源；无关事件零历史 SQL、零回执写入，相关事件使用有界索引范围历史并事务写入监控表；需要按实际认证攻击量检查后台数据库负载。默认 10 秒间隔最多读取 50 条来源/秒，重叠/补扫占用同一预算；它是后台限流上限，不是处理能力保证。积压时分轮续扫，不能宣称所有事件都在 10 秒内报警。本地没有执行生产规格 30k/100k RPM 混合负载压测，不能据此宣称生产性能验收通过。
