# 原生图片协议与渠道总用量归一化修复

## 目标与已确认范围

修复本轮审计确认的两项回归：流式入口收到 MiniMax / Ali 原生图片 JSON 时被 OpenAI 图片结构误判；Baidu / xAI 异常结算遗漏适配器原有的 `total_tokens - prompt_tokens` 输出量。沿用统一流式异常功能开关、响应门控和结算矩阵，不改变非流式行为，不扩展语音等其他功能。

## 数据流与关键边界

1. 原始响应在解析、转换之前按现有有界采集器记录；正常请求不持久化原始诊断。
2. 图片完整 JSON 按渠道验证：MiniMax 检查 `data.image_urls/image_base64`，Ali 检查 `output.results` 或 `output.choices[].message.content[].image`；其他渠道保留 OpenAI `data[]` 校验。字段非空、项完整且数量达到请求值才登记 `image_count` 并确认完成，不解码图片。
3. Ali 异步图片由适配器在读取前显式标记任务响应。`PENDING/RUNNING` 且有任务 ID 只结束本次 HTTP 读取，不结束生成会话，不登记完成图片。只有 `SUCCEEDED` 且有效图片足量才完成。同步图片不接受任务中间态替代结果。
4. 后续 Ali 轮询属于同一已接收 HTTP 200 的任务，不作为渠道重试，不重置门控、首因或证据；在原有轮询请求上接入采集和观察。读取/JSON/任务失败停止受管轮询并交给现有异常结算；初始连接失败和非 200 仍走旧流程。轮询网络/HTTP 失败发生在已创建任务之后，归为该任务上游异常。受管等待和轮询使用当前请求上下文，即使未启用旧超时控制器也响应用户取消；非受管轮询保留原有处理。
5. 仅 Baidu / xAI 顶层 `usage` 同帧同时提供合法 `prompt_tokens`、`total_tokens` 时，按原适配器语义覆盖规范输出量，并记录总量证据。总量必须为非负有界整数且不小于输入；显式零保留，缺字段不借用上一帧拼接或推造数值。全部用量校验完成后原子提交；其他渠道不采用该总量语义。
6. 正常完成仍用原适配器结算；异常与用户断开由已有确认用量/有效交付矩阵处理。无有效交付的上游异常仍不收费。原始上游 error 事件维持原样传递。

## 接口、数据与配置

- 不新增路由、权限、数据库表/列/索引、配置项。继续使用 `stream_error_setting` 和 Root 诊断查询权限。
- `image_count`、`input_tokens`、`output_tokens` 使用已有证据字段；`total_tokens` 仅为上述两渠道合法同帧组合的附加证据。
- Ali 任务阶段标记仅为本响应读取器的状态，非用户参数。原始响应继续首尾各 1 KiB、响应头 16 KiB、最多四次交换；下游采集规则不变。
- 实际修改 `relay/common/stream_session.go`，增加图片 JSON 校验模块，调整 `relay/channel/ali/image.go` 的受管轮询接入，以及 `relay/channel/minimax/image.go` 的解码错误登记；增加 common / Ali / MiniMax / Baidu / xAI 回归测试，复用现有规范证据构建与结算方法。
- MiniMax/Ali 结构观察通过后，原适配器 DTO 解码仍可能因字段类型报错；该错误在两个图片处理器中登记为 `upstream_json_error`，不误归类成本地错误。服务结算层没有新增代码。

## Main Chain Impact

- 同步：现有已读 JSON 上的有限字段检查和用量整数运算、请求内证据更新；Ali 现有网络请求的响应包装。不增加网络请求、等待、响应缓存预算或额外图片解码。任务中间态在自身 EOF 立即返回，仍由原有轮询间隔推进。
- 异步：沿用既有日志与计费持久化机制；不新增后台工作或写入。

## Shared Resource Audit

- Redis、数据库、连接池、worker pool：无新增访问。Ali 仍用原有 HTTP 默认传输连接池，没有第二次读取或重试请求。
- 内存：每个响应增加两个布尔状态，Baidu/xAI 最多增加一个总量证据键；原生图片遍历在当前 8 MiB 帧上进行，不复制图片。Ali 轮询现在也使用既有最近四响应预算，原文最多 8 KiB、响应头最多 64 KiB（另有容器开销），超过上限淘汰旧响应；关闭采集不保留这些原文。会话及采集器已有请求内短锁，不跨网络 I/O。
- 计费与日志继续访问原有异步通路，没有新共享锁、表扫描或缓存命名空间。

## Concurrency Analysis

30k / 100k RPM 下每次请求新增 DB / Redis 调用均为 0，新增 goroutine 为 0；非目标渠道只有常数分支。目标图片 JSON 线性检查现有结果项，最多现有帧预算；Baidu/xAI 每批用量为常数次检查。未执行线上负载测试，验证采用本地固定夹具。

## 测试先行与验证

先添加可重现旧错误的测试并确认失败，再实施：

- MiniMax URL/base64、Ali results/choices 的正常转换；空/缺损/不足图片仍异常；正常日志不保存原始诊断。
- Ali 初始中间态、轮询中间态、成功、失败、畸形 JSON、非 200、读取错误；验证证据不重置、任务未完成不伪装成功，采集在转换前。
- Baidu/xAI 总量推导、显式零、缺失字段、总量类型/范围/差值错误、整批回滚、非目标渠道隔离；实际适配器输出后异常和客户端断开结算。
- 开关关闭、非流式、初始非 200 保持旧路径。测试仅使用本地 HTTP/内存夹具，不调用真实 AI、数据库或真实扣款。
- 执行相关 Go 包测试、构建、格式与差异检查；实施完成后补充结果并核对中文注释。

## 实施结果

两项修复已实施，未提交或部署。

- 修复前测试复现了有效 MiniMax/Ali 图片被拦截，以及 Baidu 输出 4 被结算为 0、xAI 输出 4 被结算为原始 completion=1；修复后相同夹具通过。
- 图片校验按实际渠道识别原生结果；Ali 任务阶段标记仅存在本次读取器，PENDING/RUNNING 的正常 EOF 保持会话未完成。任务 ID 类型、空/缺损/不足图片、读取错误、任务失败和最终 DTO 类型错误均保留异常语义。
- 轮询采集沿用已开放的门控和既有上限，响应包装后登记幂等关闭；不调用会重置证据的 ObserveTransport。原先已确认用量跨任务阶段保留。
- 原适配器实际写出后异常、首个写入即用户断开，均按确认的总量归一化证据选取结算。零值/缺失/非法总量/整批回滚/其他渠道隔离均有测试。
- 实施复核还用夹具检出并修正了本次原生路径的两个衔接细节：DTO 类型失败要登记上游 JSON 原因；旧轮询后台 context 不适合受管任务，受管分支改用请求 context。真实 Ali 图片入口的取消测试不等待生产定时器、不访问外部网络。

### 验证记录

- 新增图片、任务阶段、总量及适配器结算选择夹具重复 20 次通过，全部使用内存或本地 HTTP；不实际扣款。
- 全部 relay 包、logger/common/router/operation_setting/i18n 回归以及根模块构建通过。
- service/model/controller/middleware 的 Stream/Diagnostic/RejectReason/Private 选定回归使用已有外部 overlay 跳过数据库 TestMain 后通过；此结果不代表数据库集成验证。
- 本轮 Go 文件 gofmt、差异空白、UTF-8 无 BOM/替换字符检查通过；新增方法、参数和状态字段已添加中文功能说明并对照实现核对。
- CGO_ENABLED=0，未执行 race、真实 AI 请求或生产容量压测；不涉及前端、relaykit、依赖、数据库结构及计费表达式。

### 主链复核

没有新增 DB/Redis 访问、goroutine、请求次数或轮询等待；图片结果仅在原有完整 JSON 读取后按原生结构校验，Baidu/xAI 仅增加常数次整数检查。正常 SSE 的逐帧转发时机不变；Ali 原有 5 秒首次等待、10 秒轮询间隔不增加，用户取消和受管任务异常则更早退出。
