# Relay 请求体内存治理：最小必要修复方案

更新：2026-10-18。根据用户“不要做不必要的修改”的要求收缩范围，并按随后“进行修复”的授权完成本地实现。**本文是当前实施范围，替代上一版广泛治理计划；尚未部署生产。**

[本地验证记录](relay-body-memory-validation.md)保存事实；[多模型讨论记录](relay-body-memory-model-review.md)保存建议与分歧。模型建议不等于必须实现，历史记录中的 P0 标签也不自动成为当前范围。

## 重新确认的结论

有必要修改，但没有必要把所有潜在风险一次性改造。

生产日志证明 new-api 被 global OOM 杀死；本地证明大量同时未完成请求会增加存活工作集。尚无事故堆快照，不能声称每个风险都是事故原因，也不能声称改完缓存就彻底杜绝 OOM。

原先把以下内容全部纳入首批过宽：多厂商响应限制、SDK Retryer 改造、新增三套时限、用户并发隔离、自动孤儿回收和大量配置。本次全部从首批移出。

## 必要性逐项裁定

| 项目 | 证据与判断 | 本次决定 |
|---|---|---|
| panic 跳过 BodyStorage/FileSource 清理 | 实际中间件测试复现，外层 Recovery 不会补执行 c.Next 后的清理 | A：修复 |
| Close 后仍持有内存数组 | 源码和测试确认；内部引用可安全解除，但外部别名仍可能存活，不是永久泄漏证据 | A：随 Close 修正，不扩大所有权体系 |
| 年龄清理误删活跃文件、二次减计数 | Linux 复现；手动清理接口可调用到，不能假设十分钟以上即不活跃 | A：修复清理条件与一次释放 |
| 请求体总缓存无上限，磁盘不足回退内存 | 长请求测试复现；降低落盘阈值后仍可退回原内存水平 | B：加有界缓存保护 |
| 磁盘 check-then-act 并发超发 | 2MiB 限额下写入 16MiB | B：原子预留实际字节 |
| 解压后按压缩长度判断容量 | 实际 gzip 中间件 3087 字节解压 3MiB，通过 2MiB 磁盘预算 | B：实际字节预留，不信任声明长度 |
| 非流式 ReadAll / SDK 完整 Body | 确认有完整缓冲；4MiB 响应本身可能合法，未证明本次事故由大响应造成 | 暂不改厂商处理器 |
| AWS 一次调用内部重试三次 503 | 已复现，但属于正常重试机制，不能直接认定缺陷 | 不改 SDK Retryer |
| 256KiB 截断后错误 JSON 失效 | 是上一版拟议截断方案的兼容性问题，不是已存在的截断 bug | 不引入截断，保留现有错误语义 |
| 新增上游总超时 | 已有 relay_timeout_setting.TotalTimeoutSeconds 等机制 | 不另建时限体系，不改变断连/超时行为 |
| 用户/全局并发准入、慢下游隔离 | 有价值但属于容量/公平性策略，无本次实测故障闭环 | 单独评估，不夹带实施 |
| SyncDiskCacheStats 与写入交错 | 测试复现，但尚未发现生产调用 | 不单独修未使用路径；新账本不得依赖它 |
| 自动抓 heap、后台孤儿任务、UI 重做 | 不是修复上述缺陷的前提 | 不做 |

## 目标、边界与分批

**A：小范围正确性修复。** 只保证异常结束也清理资源、关闭后解除自身引用、在线清理不删除活跃文件且不重复记账。这一批单独可审查，但**不能解决正常长请求的大工作集问题**。

**B：请求体缓存容量保护。** 限制 BodyStorage 持有的入站/出站缓存，修复现有共享磁盘预算的预留与释放。容量不足时受控失败，而不是无界回退内存。属于可见行为变化，需开关与批准；不能以“避免不必要修改”为由只修 A，却宣称已解决 OOM。

首批不重写 DTO、不改厂商协议转换、不变更响应限制、计费算法、SDK 重试、断连执行策略或既有超时。缓存预算不是进程 Heap/RSS 上限；DTO、编码临时数组、响应、下载文件等仍需后续实测定位。

## A：最小清理修复

1. `middleware/body_cleanup.go` 在 `c.Next()` 前注册清理 defer，分别保证 BodyStorage 与 FileSource 清理得到执行；不吞原 panic，继续交给现有 Recovery。
2. `memoryStorage.Close` 在现有锁内幂等解除内部 data/reader 引用；Read/Seek/Bytes 关闭后继续返回现有 ErrStorageClosed。不改变 Bytes 的外部别名约定，不提前关闭在用对象。
3. 活跃文件必须能被清理器识别。仅为服务创建的缓存文件增加最小活跃登记，覆盖 BodyStorage 和 FileSource，登记/注销与实际创建/关闭绑定；不能只保护 BodyStorage 而漏掉共用目录的文件。
4. 在线清理只删除已确认不活跃且归属本进程的文件，不根据 mtime 自动删除无法确认归属的文件。跨重启/跨实例未知文件保留并交由运维确认，不新增跨进程租约/自动回收服务。单进程登记不能证明其他进程的文件不活跃。
5. Close/清理器不得分别扣同一文件两次；删除失败不能先谎报已释放磁盘容量。保留失败状态，允许现有人工清理再次处理，不为此新建常驻任务。文件路径只来自服务自己的登记，不接受任意路径递归删除。

## B：最小缓存预算

复用现有存储抽象和磁盘配置，不建立覆盖所有 SDK/DTO 的通用资源调度框架。

### 数据流与生命周期

1. **读前预留**：已知长度只作为提示；读取、内存扩容或磁盘写入之前申请对应预算。未知长度/解压后的内容逐块申请，必须同时执行现有单请求大小限制。
2. **内存转磁盘**：仍由现有 disk_cache_enabled/threshold/path 控制。内存预算不够时，只有现有落盘已启用且磁盘预算可用才转存；不自动打开磁盘缓存。转换期间同时占用的部分都计入预算。
3. **预算不足**：内存、磁盘均不足则结束当前请求，不排队、不无限内存兜底。首次迁移的原数组及当前读取块全部写入成功前，磁盘创建/写入失败允许在原内存预算内继续；失败后不逐块重复尝试落盘。成功迁移并释放原数组后，后续磁盘错误直接失败，不能从剩余输入重新读取伪装为成功。
4. **入站与出站**：两者 BodyStorage 都计入预算；重试保持现有重放语义。已有完整 `[]byte` 再交给存储时，预算不能撤销此前分配，不得声称覆盖了编码瞬态。
5. **关闭/失败**：每次预留返回一个持有额，成功调整到实际容量，异常回滚，最终仅释放一次。内存按持有容量而非仅 len 计量；缓冲扩容时必须计入旧/新数组短暂共驻。
6. **配置变化**：每次存储读取与每个文件租约固定创建时的配置、预留额和路径，共享同一全局计数。下调预算不杀在途，新操作执行新限额，已开始的操作仍受原限额约束，不能承诺下调瞬间全局占用已低于新值。关闭开关只使新操作恢复兼容策略；已开启治理的操作不会中途变成无界读取，旧对象继续记账和释放。

### 共享磁盘范围不可省略

源码确认 `service/file_service.go` 也写同一缓存目录，并调用同一 IncrementDiskFiles/DecrementDiskFiles。**磁盘预留必须接入这些共享写入/关闭点**，否则只修 BodyStorage 仍可超发。这是必要的共享资源配套，不是扩展成下载/图片处理重构。

保持 FileSource 转换、下载、base64 和计费逻辑不变；其在落盘失败后返回内存的既有行为不能被宣称纳入 BodyStorage 内存上限。暴露的指标要明确范围，后续若证实这部分占比大，再单独治理。

### 配置与 API

最多新增两项 `setting/performance_setting` 配置：

| 键 | 默认 | 含义 |
|---|---|---|
| `body_governance_enabled` | false | 开启新的容量预留/耗尽处理；默认保持资源决策兼容 |
| `body_memory_budget_mb` | 0 | 未配置；开启治理时必须为正，不能解释为无限内存 |

磁盘继续使用已有 disk_cache_max_size_mb、disk_cache_enabled、disk_cache_threshold_mb、disk_cache_path，不新增重复磁盘预算、协议映射、用户并发或超时键。

沿用 `SaveConfigGroup` 的校验→事务持久化→发布及现有配置快照机制，只为这组有关字段补齐一致性；不重构全项目配置管理器。单键、分组和同步入口必须避免发布混合配置，失败不部分生效，业务热路径不读 DB。

不新增端点、表、迁移、Redis key。沿用 `/api/option/` 与 `/api/option/group` 的 AdminAuth/系统设置权限，并补齐 operations.performance 配置白名单；`/api/performance/stats` 保留已有权限和响应格式，仅增加 BodyMemoryReservedBytes、DiskReservedBytes、BodyCapacityRejects 对应指标。拒绝指标统计失败的预留尝试，不等于最终失败请求数；未新增清理失败计数。不新增面板或 pprof 自动化。

`DELETE /api/performance/disk_cache` 保留现有权限，响应说明实际清理结果；无法确认归属的文件跳过，不再宣称按年龄即可安全删除。新增用户可见消息通过现有 API/relay 错误体系及中英文翻译处理。

## 错误处理与计费

A 不改变成功/失败响应协议。B 的本地缓存容量耗尽通过现有 relay 错误路径返回 503，明确本地资源分类、SkipRetry，不自动禁用上游渠道；分发阶段也保留该分类，在选渠道/预扣前直接拒绝。单请求过大的既有错误映射不在本次统一改造。不是改写所有上游错误，更不涉及 SDK 内部错误。

缓存失败可能发生在预扣之后，必须验证现有退款/结算收口，不得直接绕开账务返回。新本地错误不应被渠道错误策略误判；成功请求的 usage、退款、重复重试和部分响应处理保持原规则。客户端仍可能重试 503，这个开关不能被宣传为阻止所有外部重试。

## Main Chain Impact

同步新增的是存储分配前短时预留/检查及必要释放；不增加 DB/Redis 调用，不增加请求级 goroutine、不等待队列，不持锁跨上游调用。

如果已启用落盘，内存预算压力可能让更多请求落盘，因此会增加已有同步磁盘 I/O，必须单独测量。不能声称开关本身消除了性能风险。不开落盘时，预算耗尽直接失败，不暗中切换存储介质。

不新增后台子系统；统计使用轻量计数，错误日志限频。资源决策用配置开关回滚，A 的正确清理仍应保留。已有对象直到实际不再使用才释放，不用“收到响应头”作为提前回收信号。

## Shared Resource Audit

- **内存**：BodyStorage 与出站体共享预算；外部 Bytes 别名、DTO、JSON 临时分配不在精确账本内。文件登记表只保存当前持有或删除失败的租约元数据，随成功清理移除；不保存请求内容，本轮没有新增文件数上限。
- **磁盘/文件**：BodyStorage 与 FileSource 共用目录/计数，必须一起接入预留和一次释放。活跃登记只保存必要元数据，不保存请求内容；磁盘可能与 DB/日志共盘，需观察 I/O 竞争。
- **配置**：仅相关快照和现有 options 管理写入，主链读取不新开连接；无新增 Redis 命名空间。
- **连接池/worker**：不改 HTTP/SDK/DB/Redis 池，不新增 goroutine 池，也不改 SDK Retryer。
- **账务表**：不新增查询/写入或改索引，错误继续走已有计费生命周期并做回归。

## Concurrency Analysis

100k RPM 约 1667 请求/秒；60 秒平均耗时意味着约十万在途，不能靠每请求尺寸阈值控制总工作集。B 仅使受管缓存容量有界，不能承诺十万个大请求全部接纳。

新增 DB/Redis 次数为零，新增每请求 goroutine 为零。预留操作随读取块数增加，需要对并发竞争和存储路径 P99 做对照。30k/100k RPM 下两份 4MiB 入站/出站落盘约需 3.9/13GiB/s 写吞吐，不能假设现有 NVMe 必定承受。生产预算根据现有负载测量设定，不拍脑袋写死 4GiB。

## 必需验证与停止条件

实施前写修复后断言；当前诊断测试部分断言的是现有错误行为，不能直接拿“全绿”宣称修复成功。

**A 验收**：正常、Abort、畸形输入、取消后返回、超时后返回、panic；内存引用释放、重复 Close、FileSource 同步清理；活跃文件不误删、删除失败不虚减、关闭与清理并发不重复扣账。无需因此改所有厂商处理器。

**B 验收**：内存/磁盘上限边界，未知/虚假长度和 gzip/br/zstd 解压；并发预留不超发；磁盘创建/写入失败；中途取消；入站/出站重试重放；配置下调/关闭和目录变更；共享 FileSource 磁盘写入不能绕过预算。完整读取保留内容正确性，不能只检查计数。

重复已有大量短请求、8/32/64 长请求、磁盘充足/不足测试，比较自然 GC 与结束后残留。补充 B 失败时的退款/重试回归、有限本地负载开关对照；主链正常路径新增检查 P99 目标 <1ms，实际磁盘 I/O 单独报告。

已运行相关包测试、Windows race 及 Linux 本地并发长请求测试，详见验证记录。Linux race 尚未运行；staging 30k/100k RPM 的小请求容量及长请求混合验证仍待进行，需记录拒绝率、RSS、HeapAlloc、FD、磁盘延迟和 GC CPU。未完成前不能宣布线上容量已验证。

若受管缓存下降后进程内存仍高，**停止扩大这一补丁的范围**，先以堆采样/对象统计定位 DTO、响应或其他来源，另行提出有证据的修复；不默认启动整套厂商响应/超时改造。

## 明确不做的改动与重新评估条件

| 不做 | 何时才重新评估 |
|---|---|
| 多厂商响应截断/协议限额/SDK Retryer 包装 | 堆或线上样本证明响应占用失控，且能定义合法响应上限与错误/计费兼容性 |
| 新的全局/用户并发调度和三种时限 | 既有超时/限流配置不足，实际出现长期占坑或用户饥饿，并单独批准业务策略 |
| 流开始后提前释放、改断连结算 | 明确上传、重试、计费所有者后有针对性证据和回归 |
| 全局 DTO 工作预算、JSON 重构 | 确认相关分配占比和持有点后另议 |
| 文件格式/目录大迁移、跨进程自动孤儿回收 | 有明确多实例需求并完成所有权设计 |
| 自动 heap 采集、前端重做、强制 GC/重启 | 非本次修复前提，不随补丁加入 |

## 发布与批准

先 A 后 B，分开评审；B 默认关闭，确认生产版本、测量并配置预算后再灰度。回滚 B 停止新资源决策，旧对象仍正确释放；回滚后无界缓存风险会恢复，不把它当作永久止血。

本地实现包含 A/B 及复审发现的错误分类、配置快照、首次落盘失败回退修正。A 是有复现的正确性缺陷，B 是应对长请求缓存放大的容量保护；二者都不是对事故所有因素的最终归因。

运维限制：跨重启、跨实例的未知缓存文件既不自动删除，也不纳入本进程租约账本。磁盘指标不能代表物理剩余空间；灰度时必须同时监控文件系统可用容量。残留文件只在确认没有运行实例持有后由运维处理，不使用按 mtime 删除活跃目录的脚本。磁盘耗尽仍可能导致本地容量拒绝；有限内存回退不能消除物理容量不足。

复审明确的剩余风险：`diskStorage.Bytes()` 为 JSON 分发/解析物化完整字节数组，这个返回给调用者的副本没有纳入缓存持有预算，多次调用和并发解析仍可能放大堆。文件预算按有效内容字节计算，不约束文件数、inode 或元数据；阈值为 0 时空/极小文件尤其需要观察。两者不能由本补丁宣称解决，若灰度仍见高内存/FD，应先定位并单独设计 Bytes 所有权或文件数保护，不直接扩大当前改动。
