# Veridrop Monitor 检测接口接入设计

## 背景

当前项目负责渠道、模型、权限、任务调度和管理前端。`E:\code\veridrop-monitor` 只作为外部检测能力接口使用，不接入它的前端，也不把渠道控制权交给 Veridrop。

已实现的接入原则：

- 批量检测默认覆盖所有已启用渠道。
- 每个渠道检测其配置中的已启用模型。
- 检测目标是渠道上游 `base_url`，不是当前项目的中转入口。
- 检测结果只用于记录、筛选、评分和报告，不自动修改渠道状态。
- 前端在当前项目中提供独立检测页面 `/channels/detection`。

## 目标和范围

目标：

- 在当前项目中新增 Veridrop 检测后台任务。
- 读取当前项目的渠道、模型、上游地址和密钥，提交给 Veridrop 后端检测。
- 保存检测历史，供后台页面查看。
- 保持渠道启停控制由当前项目负责。
- 支持批量检测、手动测试、任务状态和结果查看。
- 不影响 AI 请求主链路。

范围内：

- Veridrop 后端地址与检测参数配置。
- 单渠道检测接口。
- 手动填写上游地址、API Key、模型和协议进行一次性检测。
- 批量检测已启用渠道和模型。
- 检测结果表和查询接口。
- 后台系统任务接入。
- 前端独立检测页面 `/channels/detection`。

范围外：

- 不接入 Veridrop 自带前端。
- 不把 Veridrop 作为渠道状态的唯一事实来源。
- 不在 AI relay 请求过程中同步调用 Veridrop。
- 不做检测成功后的自动启用。
- 不修改模型能力表 `abilities`。

## 数据流

### 批量检测

1. 管理员在 `/channels/detection` 查看“批量检测”页签。
2. 前端先请求 `GET /api/channel/veridrop/targets`，展示本次会检测的渠道、模型、上游 Base URL，以及因协议不支持或没有模型而不会纳入检测的渠道。
3. 管理员点击“运行检测”后，前端请求 `POST /api/channel/veridrop/detect_enabled`。
4. Controller 校验管理员渠道操作权限，并创建 `veridrop_detection` 系统任务。
5. 系统任务读取 `veridrop_monitor_setting` 配置。
6. 服务层按 `id > last_id` keyset 分页读取已启用渠道。
7. 每个渠道使用 `channel.GetModels()` 展开已启用模型。
8. 每个渠道/模型组合创建一条 `channel_veridrop_detections` 记录，初始状态为 `queued`。
9. 后台 worker 按 `MaxConcurrent` 限制并发提交检测。
10. 服务层调用 Veridrop：
    - `POST {veridrop_base_url}/api/detect/{protocol}`
    - `GET {veridrop_base_url}/api/status/{job_id}`
    - `GET {veridrop_base_url}/api/result/{job_id}.json`
11. 检测完成后保存分数、结论、摘要、错误和脱敏后的原始 JSON。
12. 检测完成后只写入检测记录；无论结论或评分如何，都不调用渠道禁用逻辑。
13. 前端轮询系统任务和检测结果，展示最新状态。

### 单渠道检测

1. 调用 `POST /api/channel/veridrop/detect`，传入 `channel_id`。
2. 服务层读取指定渠道。
3. 请求明确传入非空白 `model` 时只检测该模型，用于保留 API 的定向检测能力；渠道列表和真伪检测工作台的普通单渠道入口均只传 `channel_id`，不传 `model`。
4. 请求未传入 `model` 或只传空白时，通过 `channel.GetModels()` 读取并规范化渠道当前配置的全部模型，去除空值和重复项，不再回退到 `TestModel` 或只取模型列表第一项。
5. 每个渠道/模型组合创建一条独立检测记录，单渠道任务的 `Channels` 固定为 1，`Models`、进度总数和完成进度按实际模型数统计。
6. 所有模型继续复用现有有界并发执行器、超时、失败策略和结果写入逻辑；记录不写入批次标识，仍与批量、定时检测结果区分。
7. 渠道没有有效模型时只创建一条跳过记录；协议不支持时按实际模型分别记录跳过结果；任务取消时把已经创建但尚未派发的模型记录统一改为 `cancelled`。
8. 只要成功读取到目标渠道，汇总中的 `Channels` 就记为 1，包括无模型或协议不支持等跳过场景；渠道不存在或数据库读取失败时保持 0。模型任务构建失败也必须推进已处理数，避免系统任务进度停在非 100%。

本次修正不改变接口路径和请求/响应结构，不新增数据库字段、索引或配置项。只调整单渠道任务在未指定 `model` 时的模型展开语义；显式指定模型的调用保持兼容。

测试先覆盖以下路径，再修改服务实现：

1. 单渠道包含三个有效模型时创建三条任务并将 `Models` 统计为 3。
2. 模型列表包含空白和重复值时只检测规范化后的唯一模型。
3. 请求显式指定 `model` 时仍只检测指定模型。
4. 渠道无模型时产生一条跳过记录，不进入上游调用。
5. 多模型执行时进度总数、取消后未派发记录状态和最终汇总保持正确。
6. 渠道列表行操作与真伪检测工作台行操作都只提交 `channel_id`，两处入口均覆盖全部模型。
7. 无模型和协议不支持时的渠道数、模型数、跳过数及最终 100% 进度一致。

实现记录：单渠道分支现在把目标限制为当前 `channel_id` 后复用批量检测的模型展开与有界并发执行流程，并显式允许读取已禁用渠道，保持原单渠道入口能力。`model` 在应用默认值前统一去除首尾空白；空值展开渠道全部模型，非空值只检测指定模型。回归测试已覆盖三个唯一模型、重复与空白模型、`TestModel` 不抢占、显式模型覆盖、空白覆盖、无模型、协议不支持、批次标识为空以及最终进度。香港测试服务器已部署 SHA-256 为 `eed118203a10b7aedf46270de1aa9504417b9b36a4e5ad7e43fc05a346d0858d` 的构建，`/api/status` 与 `/channels/detection` 健康检查均返回 200。

### 手动检测

1. 管理员在“手动测试”页签填写临时上游 `base_url`、`api_key`、`model`、`protocol` 和检测模式。
2. 前端请求 `POST /api/channel/veridrop/detect_manual`。
3. Controller 校验渠道操作权限和必填字段。
4. 服务层创建一条 `channel_veridrop_detections` 记录，`channel_id = 0`，`channel_name = "Manual Test"`。
5. 后端异步调用 Veridrop，不创建系统任务，不把手动填写的 API Key 写入任务或响应。
6. 检测结果进入现有检测结果列表；手动、单渠道、批量和定时检测都不会改变渠道状态。

### 存储和响应

- 任务状态存在现有 `system_tasks`。
- 每个渠道/模型检测结果存在新表 `channel_veridrop_detections`。
- API 只返回任务和结果元数据，不返回 API Key。
- Veridrop 返回内容入库前进行密钥脱敏。

## API 合约

所有接口都挂在已有渠道管理路由下，使用后台权限控制，无公开接口。

### 启动单渠道检测

`POST /api/channel/veridrop/detect`

权限：渠道操作权限。

请求：

```json
{
  "channel_id": 1,
  "model": "claude-haiku-4-5",
  "protocol": "anthropic",
  "mode": "quick",
  "include_long_context": false,
  "include_long_context_extreme": false,
  "openai_wire_api": "chat_completions"
}
```

响应：

```json
{
  "success": true,
  "message": "",
  "data": {
    "task": {},
    "created": true
  }
}
```

### 启动已启用渠道批量检测

`POST /api/channel/veridrop/detect_enabled`

权限：渠道操作权限。

请求：

```json
{
  "mode": "quick",
  "include_long_context": false,
  "include_long_context_extreme": false,
  "openai_wire_api": "chat_completions"
}
```

可选调试字段：

- `channel_ids`：限制到指定渠道集合。
- `model`：覆盖模型选择。
- `protocol`：覆盖协议推断。
- `max_channels`：限制本次最多处理的渠道数。

响应同单渠道检测。

### 启动手动检测

`POST /api/channel/veridrop/detect_manual`

权限：渠道操作权限。

请求：

```json
{
  "base_url": "https://api.example.com/v1",
  "api_key": "sk-...",
  "model": "gpt-5",
  "protocol": "openai",
  "mode": "quick",
  "include_long_context": false,
  "include_long_context_extreme": false,
  "openai_wire_api": "chat_completions"
}
```

响应：

```json
{
  "success": true,
  "message": "",
  "data": {
    "id": 123,
    "channel_id": 0,
    "channel_name": "Manual Test",
    "protocol": "openai",
    "model": "gpt-5",
    "status": "queued"
  }
}
```

### 查询本次批量检测范围

`GET /api/channel/veridrop/targets`

权限：渠道读取权限。

查询参数：

- `mode`：可选，检测模式。
- `model`：可选，覆盖模型选择。
- `protocol`：可选，覆盖协议推断。
- `max_channels`：可选，限制预览渠道数；默认不限制。
- `include_long_context`：可选，是否启用长上下文探针。
- `include_long_context_extreme`：可选，是否启用极限长上下文探针。
- `openai_wire_api`：可选，OpenAI 兼容检测协议。

响应：

```json
{
  "success": true,
  "message": "",
  "data": {
    "items": [
      {
        "channel_id": 1,
        "channel_name": "主站 OpenAI",
        "channel_type": 1,
        "channel_type_name": "OpenAI",
        "protocol": "openai",
        "base_url": "https://api.openai.com/v1",
        "models": ["gpt-5", "gpt-4o"],
        "model_count": 2
      }
    ],
    "channel_count": 1,
    "model_count": 2,
    "skipped_channel_count": 0
  }
}
```

该接口只读取当前已启用渠道和模型，不创建系统任务，不读取或返回 API Key。前端用它在“运行检测”前展示会检测哪些渠道、哪些模型，并在确认弹窗里给出准确数量。

### 查询检测结果列表

`GET /api/channel/veridrop/results`

权限：渠道读取权限。

查询参数：

- `channel_id`：可选，按渠道过滤。
- `channel_name`：可选，按渠道名称模糊过滤。
- `model`：可选，按模型名称模糊过滤。
- `mode`：可选，按检测模式过滤。
- `verdict`：可选，按检测结论模糊过滤。
- `keyword`：可选，在结论、摘要和错误信息中检索。
- `status`：可选，按状态过滤。
- `protocol`：可选，按协议过滤。
- `min_score` / `max_score`：可选，按检测分数范围过滤。
- `updated_after`：可选，只返回该 Unix 秒之后更新的结果。
- `error_only`：可选，只返回带有错误信息的结果。
- `before_id`：可选，keyset 翻页游标。
- `limit`：可选，最大 100。

响应：

```json
{
  "success": true,
  "message": "",
  "data": {
    "items": [],
    "next_before_id": 123
  }
}
```

### 查询单条检测结果

`GET /api/channel/veridrop/results/:id`

权限：渠道读取权限。

响应：

```json
{
  "success": true,
  "message": "",
  "data": {}
}
```

## Veridrop 后端接口

当前项目调用 `E:\code\veridrop-monitor` 已有接口：

- Claude/Anthropic：`POST /api/detect/claude`
- OpenAI 兼容：`POST /api/detect/openai`
- Gemini：`POST /api/detect/gemini`
- 任务状态：`GET /api/status/{job_id}`
- JSON 结果：`GET /api/result/{job_id}.json`

提交表单字段：

- `base_url`：渠道上游地址，来自 `channel.GetBaseURL()`。
- `api_key`：渠道密钥，来自当前项目渠道密钥选择逻辑。
- `model`：本次检测模型。
- `mode`：检测模式。
- `include_long_context`：是否启用长上下文检测。
- `include_long_context_extreme`：是否启用极限长上下文检测。
- `wire_api`：仅 OpenAI 协议使用，默认 `chat_completions`。

鉴权：

- 如果配置了 `admin_api_key`，请求 Veridrop 时附带 `Authorization: Bearer <admin_api_key>`。
- 当前实现不要求 Veridrop 必须开启鉴权。

## 数据模型

新增表：`channel_veridrop_detections`

主要字段：

- `id`
- `channel_id`
- `channel_name`
- `channel_type`
- `protocol`
- `model`
- `mode`
- `status`
- `veridrop_job_id`
- `score`
- `verdict`
- `summary`
- `run_error`
- `error`
- `result_json`
- `created_at`
- `started_at`
- `finished_at`
- `updated_at`

状态枚举：

- `queued`
- `running`
- `done`
- `error`
- `timeout`
- `cancelled`
- `skipped`

索引设计：

- `channel_id`：支持按渠道查看历史。
- `protocol, id`：支持按协议过滤和倒序列表。
- `status, id`：支持按状态过滤和倒序列表。
- `finished_at, id`：支持后续按完成时间清理或统计。
- `veridrop_job_id`：支持从 Veridrop job 反查。
- `created_at`：支持时间相关排序和清理。

兼容性：

- 使用 GORM AutoMigrate。
- JSON 结果以 `TEXT` 保存，避免数据库特定 JSON 类型。
- 时间字段使用 Unix 秒级整数。
- 兼容 SQLite、MySQL 和 PostgreSQL。

## 配置参数

新增配置模块：`veridrop_monitor_setting`

结构：

```go
type VeridropMonitorSetting struct {
    Enabled bool `json:"enabled"`
    BaseURL string `json:"base_url"`
    AdminToken string `json:"admin_api_key"`
    DefaultMode string `json:"default_mode"`
    DefaultOpenAIWireAPI string `json:"default_openai_wire_api"`
    IncludeLongContext bool `json:"include_long_context"`
    IncludeLongContextExtreme bool `json:"include_long_context_extreme"`
    MaxConcurrent int `json:"max_concurrent"`
}
```

配置通过 `setting/operation_setting` 注册，由现有设置系统持久化。前端配置入口放在检测页右上角“检测设置”弹窗内，不直接铺在页面首屏，避免挤压批量检测、手动测试和结果查看区域。

## 关键业务逻辑和边界

- 批量检测只处理启用状态的渠道。
- 渠道模型为空时跳过该渠道，并在检测范围里展示原因。
- 协议只支持 OpenAI 兼容、Anthropic/Claude、Gemini；其他协议跳过。
- 手动检测不复用渠道密钥，不写入 API Key。
- 所有检测模式只记录结果，永远不触发渠道禁用。
- Veridrop 调用失败时只更新检测记录和任务状态，不影响其它渠道继续检测。
- 页面下拉框显示本地化文案，例如“快速”“标准”“完整”“OpenAI 兼容”，不直接显示内部值。

## 前端交互设计

- 检测页面使用三个页签：“批量检测”“手动检测”“检测记录”。页签已经表达当前区域语义，页签内容不再重复同名标题和说明。
- 页签栏使用内容区完整宽度，避免宽屏下右侧出现没有用途的大片留白。
- 页面右上角只保留“检测设置”按钮。失败策略移入批量检测工具栏并只显示一次，不再同时出现在页头和运行卡片中。
- 检测设置通过弹窗编辑，保存成功后关闭弹窗；保存失败时弹出用户可理解的错误提示。
- 批量检测页签改成单列、全宽布局：顶部是紧凑操作栏，下面直接接检测范围表格。操作栏集中显示“立即检测”、刷新、渠道/模型数量、失败策略和当前任务状态，不再保留固定宽度的左侧运行卡片。
- 当前没有任务时，在操作栏内显示一行“当前无运行任务”，不渲染带最小高度的大型空状态。任务运行时在相同位置显示状态、进度和更新时间，避免布局跳动。
- 检测范围只展示一次渠道数和模型数；表格标题区不再重复“检测范围”说明和相同统计。模型默认显示前 3 个，其余合并成“另有 N 个”，减少单行高度。
- 手动检测页签提供协议、检测模式、Base URL、API Key、模型、OpenAI Wire API 和长上下文开关；标题统一使用“手动检测”，结果中的 `channel_id = 0` 显示为“手动检测”且隐藏无意义的 `#0`。
- 检测记录页签直接展示筛选工具栏和结果表，不再额外套一层“检测结果”标题卡片。运行中、失败数和“下载报告”放在筛选工具栏右侧。
- 检测结果筛选会传到后端结果接口，而不是只筛当前前 100 条；支持按状态、协议、模式、更新时间、渠道名称/ID、模型名称、结论、是否有错误、最低分、最高分和关键字筛选；下载报告按钮导出当前筛选后的 CSV，便于排查和留档。
- 结果筛选区域使用明确标签而不是只靠占位符，避免多语言文案或窄屏下被挤压后无法判断字段含义。
- 结果筛选使用一行紧凑工具栏；匹配数量并入工具栏，不再单独占一整行。窄屏时按“关键字 → 状态/时间 → 操作”顺序自然换行。
- 结果表把“状态、分数、原始结论”收敛成一个“结果”字段：
  - `done + passed` 显示“通过”，不再同时显示“完成”和原始 `passed`；
  - 有有效分数时格式化为最多 1 位小数并追加“分”，例如 `93.3 分`，不显示长浮点数；
  - `error`、`timeout`、`cancelled`、`skipped` 使用本地化状态，不直接暴露内部英文枚举；
  - 原始结论只有在补充了状态没有表达的新信息时才显示，并放入详情列。
- “摘要”列改名为“详情”，按错误信息、运行错误、摘要的优先级只展示一份内容；相同内容不在状态列和详情列重复。
- 技术标识（模型名、协议、Base URL、API 路径）保持原值；操作、状态、帮助和空状态文案全部本地化。普通页面不显示 `Veridrop` 品牌名，只有“检测设置”弹窗中的第三方连接配置保留该名称。
- 所有加载、空状态和错误状态都告诉使用者下一步可做什么，例如刷新、补全设置或保存配置。
- 桌面端表格使用完整内容宽度；移动端保留横向滚动并缩短辅助文案。长列表行使用 `content-visibility: auto` 和合理的固有高度提示，减少屏外行的布局与绘制成本。

### 全渠道检测工作台：筛选批量与单个执行

#### 目标与范围

“批量检测”页不再只是已启用渠道的只读预览，而是列出全部渠道的检测工作台：管理员可以按条件筛选渠道、勾选若干渠道批量执行、对当前全部筛选结果批量执行，或直接执行单个渠道。检测继续复用渠道已保存的地址、密钥、协议和模型，不在页面返回或展示 API Key。

页面结构：

- 顶部保留当前任务状态、刷新和失败策略；原“立即检测全部已启用渠道”主按钮改为与筛选/选择关联的批量操作。
- 筛选条件包括：关键词（渠道名、ID、API 地址或模型）、渠道状态（全部/已启用/已禁用）、协议（全部/OpenAI/Anthropic/Gemini）和可检测性（全部/可检测/不可检测）。筛选在完整目标集合上执行，不只过滤当前可见的几行。
- 表格列为：选择、渠道（同时显示启用状态与 ID）、API 地址、协议、模型、操作。移除独立 ID 列，减少横向占用。
- 可检测行支持复选；表头复选框选择当前筛选结果中的全部可检测渠道。筛选变化后保留仍在结果集合中的选择，移除已不匹配或不可检测的选择。
- 操作区提供“检测已选（N）”和“检测筛选结果（N）”。批量执行前复用现有确认弹窗，明确渠道数和模型数；没有可执行对象时按钮禁用并说明原因。
- 每行提供紧凑的“检测”按钮。单渠道执行不增加确认弹窗；仅当前行显示加载态。不可检测行不发请求，并展示具体原因（不支持的协议、没有模型等）。
- 已禁用渠道仍展示且可以被管理员明确选择或单独检测；不会因为出现在列表中自动执行。默认进入页面时状态为“全部”，但未选择前不触发检测。

#### 数据流与 API 合约

1. 页面请求 `GET /api/channel/veridrop/targets?scope=all`。默认不带 `scope` 时继续保持现有“仅已启用渠道”语义，兼容已有调用。
2. `scope=all` 使用按主键递增的分批查询读取全部渠道，响应项新增：

```json
{
  "channel_id": 15,
  "channel_name": "grok-fra",
  "status": 1,
  "protocol": "openai",
  "base_url": "https://example.com",
  "models": ["grok-4.6"],
  "model_count": 1,
  "skipped_reason": ""
}
```

3. 单渠道继续调用 `POST /api/channel/veridrop/detect`，请求 `{ "channel_id": 15 }`。
4. 新增 `POST /api/channel/veridrop/detect_batch`，仅用于管理员明确选择的渠道，请求为：

```json
{
  "channel_ids": [15, 17],
  "mode": "quick",
  "include_long_context": false,
  "include_long_context_extreme": false,
  "openai_wire_api": "chat_completions"
}
```

5. `channel_ids` 必须非空、去重且全部为正整数；服务端重新读取渠道并重新判断协议和模型，不信任前端展示状态。请求体不接受 API Key。批量任务沿用现有最大并发、超时、失败策略和结果写入流程。
6. 两个执行端点要求 `admin_menu.veridrop_detection + channel.operate`；目标列表要求 `admin_menu.veridrop_detection + channel.read`。业务错误仍使用现有成功 HTTP 状态加 `success=false` 的管理 API 约定。

#### 数据模型、配置与兼容性

- 不新增数据库表、字段、迁移、Redis key 或配置项。
- `channels` 表只读；`system_tasks` 和 `channel_veridrop_detections` 沿用现有写入结构。
- 现有 `POST /detect_enabled` 保持“所有已启用渠道”的原语义，供定时任务和兼容调用继续使用；显式选择（包括已禁用渠道）只走新 `/detect_batch`，避免悄悄改变既有任务范围。
- 页面拿到全部目标后在前端进行即时组合筛选；目标查询仍使用服务端批大小分段读取，避免一次无界 DB 行扫描占用连接。若后续渠道规模超过管理页面可接受范围，再独立升级为游标分页和服务端筛选，本次不引入两套选择语义。

#### 关键逻辑与边界

- “检测筛选结果”只提交当前筛选集合中可检测渠道的 ID；不可检测渠道不计入确认数量。
- 模型数按各渠道当前 `model_count` 求和；提交后服务端重新读取，因此确认数与执行数可能因并发配置变更略有差异，最终以任务结果为准。
- 同一类检测任务已运行时，不重复创建任务，页面提示“检测任务已在运行中”并刷新当前任务。
- 请求失败、权限不足或检测设置缺失时恢复按钮状态，保留筛选和选择，给出可执行的重试提示。
- 单渠道任务和批量任务都只读取渠道配置，不改变渠道启用状态；失败策略是否停用渠道仍由现有检测设置决定并在确认弹窗中显示。

#### Main Chain Impact 与共享资源审计

- AI relay 请求路径不执行任何新增同步或异步逻辑；100k RPM 下每个 relay 请求新增 DB、Redis、锁和协程成本均为 0。
- `channels` 表和主数据库连接池与 relay 共享。全渠道列表只在管理员打开页面或手动刷新时执行，按 `id` 主键顺序、使用既有批大小分段读取，不加锁、不更新渠道；批量任务沿用现有后台任务读取方式，不在 relay goroutine 上执行。
- `system_tasks`、`channel_veridrop_detections` 和 Veridrop worker 并非 relay 主链资源；不新增连接池或无界 goroutine，检测并发继续受 `MaxConcurrent` 限制。
- 不使用 Redis，不新增内存全局缓存。页面筛选和选择状态只存在于当前浏览器组件生命周期。

2. 关键词、状态、协议、可检测性可组合筛选；统计数、全选范围和表格内容一致。
3. “检测已选”只提交勾选 ID；“检测筛选结果”提交全部匹配且可检测 ID；切换筛选不会误带已隐藏选择。

### 检测记录筛选语义修正

部署后的实际操作暴露出“内部任务状态”和“用户可见结果”混用的问题：下拉框使用 `queued/running/done/error/timeout/cancelled/skipped`，表格却根据 `status + verdict` 显示“通过/失败”，导致“已完成”不能对应用户真正想查的结果。

调整方案：

- 状态筛选改为结果筛选，只保留“全部 / 进行中 / 通过 / 失败”四项。
- “进行中”匹配 `queued` 与 `running`。
- “通过”匹配 `status = done` 且 `verdict` 为 `passed/pass/success`。
- “失败”匹配 `status = error/timeout`，或 `status = done` 且 `verdict` 为 `failed/fail/error`。
- `cancelled` 与 `skipped` 仍在“全部”中按各自标签展示，不再作为高频独立筛选项。
- 结果接口增加面向用户语义的 `outcome` 查询参数；继续保留现有 `status`、`verdict` 参数以兼容已有调用。
- 关键词查询同时匹配 `channel_name`、`model`、`verdict`、`summary`、`error` 与 `run_error`，与“搜索渠道、模型或详情”的界面文案一致。
- 所有筛选均在数据库查询中执行，之后再应用 `LIMIT`，不在前端对已返回的 100 条记录做二次假筛选。

验收：选择四个结果选项时，请求参数和返回集合分别符合上述组合；搜索截图中的渠道名 `thinkai` 或模型名 `gpt-5.2` 能返回对应记录；清空筛选恢复全部结果。

实现记录：前端筛选字段已改为 `outcome`，下拉仅显示“全部 / 进行中 / 通过 / 失败”；后端在应用 `LIMIT` 前完成组合条件和关键词过滤。`model/channel_veridrop_detection_test.go` 覆盖四类结果边界、取消/跳过不误归类，以及渠道名和模型名关键词查询。表格结果标签与筛选复用同一套通过/失败判定，避免显示口径不一致。

筛选口径修复（2026-08-15）：页面按上游最终结论和评分边界显示结果。`passed` 显示“通过”；`marginal` 且分数不低于 50 显示“基本合格”（包括因严重问题从 70 分以上下调的记录）；`marginal` 且分数低于 50 显示“未达标”；运行或调用错误显示“失败”。服务端沿用 `completed` 与 `low_score` 查询参数以保持 API 兼容，但页面分别显示为“基本合格”和“未达标”；组合筛选仍在数据库查询和 `LIMIT` 之前执行。

部署后复核进一步调整：关键词输入使用 400ms 防抖，避免每个字符触发一次管理 API 查询；结果数量、重置、手动刷新和下载合并到筛选工具栏，移除仅统计当前返回页且容易被理解为全量统计的“运行中/失败”汇总徽标。时间范围的起点在每次请求时重新计算，长时间停留页面时仍保持“最近 24 小时/7 天/30 天”的滚动语义。终态结果筛选可能停止自动轮询，因此工具栏保留明确的手动刷新入口。

- 手动检测保留必要的用途说明和提交按钮，但移除了与页签重复的卡片标题。
- 检测记录使用“筛选栏 → 结果统计与导出 → 表格”的单层结构；不再渲染重复的结果标题和第三方说明。
- 结果状态根据 `status + verdict` 组合生成人类可读标签；有效分数格式化为最多一位小数，已由状态表达的 `passed`/`failed` 不再重复显示。
- 范围和结果表格行使用 `content-visibility: auto`，模型预览从 6 个收敛为 3 个；接口、查询参数、轮询和 CSV 原始字段保持不变。
- 新增和调整的页面文案已通过脚本同步到七个前端语言包，没有直接手工修改 locale JSON。

侧边栏导航项、菜单管理项、权限资源、页面标题、渠道行操作菜单项和系统任务类型展示名统一使用 `t('Authenticity Detection')`（中文“真伪检测”），避免同一功能在不同入口出现“检测”和“真伪检测”两种名称。管理员菜单中该入口与“价格巡检”等四字菜单集中排列。

内部命名保持不变，不受这次改名影响：路由 `/channels/detection`、前端目录 `features/veridrop-detection`、系统任务类型字符串 `veridrop_detection`、后端 API 路径 `/api/channel/veridrop/*`、配置模块 `veridrop_monitor_setting`。这些是工程内部标识，改动会扩大不必要的 diff 且没有用户可见收益；只有面向管理员展示的文案改了名字。设置弹窗里描述具体对接机制的文案（“Veridrop Base URL”“Enable Veridrop Detection”等）同样不受影响，因为它们准确描述的是正在配置的第三方后端本身。

### 独立菜单权限

“真伪检测”原来挂在 `admin_menu.channels` 权限下，任何能看到“渠道”菜单的管理员都能访问。这次改名的同时把它拆成独立的权限资源 `admin_menu.veridrop_detection`（后端 `service/authz/resources_admin_menu.go`），使 root 能够单独对某个管理员授予或收回这个入口，不再和渠道管理权限绑死：

- 新资源默认对 `admin` 角色开放（`DefaultRoles: []string{BuiltInRoleAdmin}`），与拆分前的可见范围保持一致，避免现有管理员在升级后突然失去入口。
- `service/authz` 的内建角色策略在每次服务启动时都会依据当前资源定义重新生成（`resetBuiltInRolePolicies` + `seedDefaultPolicies`），因此新增资源不需要额外的数据库迁移脚本。
- 后端路由 `/api/channel/veridrop/*` 原来跟随 `/api/channel/*` 分组统一要求 `admin_menu.channels`，现在拆到独立分组，改为要求 `admin_menu.veridrop_detection`（叠加原有的 `channel.read`/`channel.operate` 逐路由权限不变）。仅拆前端导航权限而不改后端会导致“看得见菜单但接口 403”或反过来“菜单被收回但接口仍可直接调用”的不一致，因此前后端一起拆分。
- 前端 `web/src/lib/admin-menu-access.ts` 新增 `ADMIN_MENU_IDS.VERIDROP_DETECTION`，并在 `ADMIN_MENU_BY_URL` 里把 `/channels/detection` 排在通用的 `/channels` 前缀之前（更具体的前缀优先匹配）。

## 错误处理策略

- Controller 使用 `common.ApiErrorMsg` 或现有成功响应结构，不返回原始 Go 错误给前端。
- 服务层记录内部错误，前端只展示可操作文案。
- Veridrop 网络错误、超时、结果解析错误都会落到检测结果记录。
- API Key 和 Bearer token 不写日志、不返回给客户端。

## 与现有系统交互

- 渠道：只读取渠道、base_url、密钥和模型列表，不写入渠道状态。
- 模型：只读取渠道配置中的模型，不修改模型广场或能力表。
- 系统任务：批量检测写入 `system_tasks`，手动检测不创建系统任务。
- 设置：通过现有 `setting` 系统保存 Veridrop 配置。
- 前端路由：新增 `/channels/detection`，在管理员菜单中显示。
- i18n：前端新增文案进入现有 i18next 语言包。

## Main Chain Impact

该功能不挂入 AI relay 主链路。

同步执行：

- 仅后台管理 API 请求中的权限校验、参数校验、配置读取、目标预览和任务创建。
- 检测页面的前端请求只访问管理接口。

异步执行：

- 批量检测由系统任务后台执行。
- 单渠道和手动检测提交 Veridrop 后在后台轮询状态并写入结果。

不会在 relay goroutine 上执行：

- Veridrop HTTP 调用。
- 检测结果写库。
- 检测结论不会触发渠道状态变更。
- 前端轮询。

## Shared Resource Audit

- DB 表 `channels`：检测任务读取启用渠道和模型。relay 链路也会读取渠道信息，但本功能在后台任务中分页读取，不在 relay 请求路径中执行。
- DB 表 `channel_veridrop_detections`：新增独立结果表，relay 链路不访问。
- DB 表 `system_tasks`：后台管理任务表，relay 链路不访问。
- DB 配置表：通过现有 setting 系统读写 `veridrop_monitor_setting`，relay 链路不访问该配置。
- Redis：当前实现不新增 Redis key。
- 内存结构：只使用任务局部变量和有限 worker 并发，不新增全局缓存。
- 连接池：检测任务会占用数据库连接和 Veridrop HTTP 连接；并发由 `MaxConcurrent` 限制，默认值较小，避免后台任务挤占 relay 资源。

## Concurrency Analysis

管理后台路径不要求 100k RPM relay 级别并发，但仍做以下限制：

- 目标预览使用 keyset 分页读取渠道，避免无界全表扫描。
- 批量检测按 `MaxConcurrent` 限制同时提交 Veridrop 的数量，默认 2。
- 每个渠道/模型组合最多产生一条结果记录和一组状态更新。
- 无分布式锁。
- 无 relay 每请求 DB/Redis 调用增量。
- 在 100k RPM relay 流量下，本功能不会随 relay 请求数增长；只随管理员启动的检测任务增长。

## 手动检测参数完整性复核

以 `mxyhi/veridrop-monitor` 当前 `main` 分支的直接检测接口为准，手动检测表单只展示实际参与对应协议请求的参数：

- 三种协议共同参数：`base_url`、`api_key`、`model`、`mode`。
- OpenAI 专属参数：`wire_api`，只允许 `chat_completions` 或 `responses`。
- OpenAI 与 Anthropic 支持：`include_long_context`、`include_long_context_extreme`；Gemini 直接检测接口不接收这两个参数，因此切换到 Gemini 时不显示。
- 三种协议共同支持高级参数 `force`：跳过模型可用性预检并直接进入正式检测。默认关闭，只有管理员明确开启时才向 Veridrop 发送 `force=true`。
- `name`、`enabled`、`interval_minutes` 属于 Veridrop 监控器创建参数，不属于本系统的一次性手动检测，不在此表单展示。

交互调整：`wire_api` 使用固定选项下拉框，避免输入上游不接受的任意值；协议专属参数按当前协议条件渲染，不保留无效占位区域；`force` 作为高风险但必要的兜底开关，文案明确说明它不会绕过正式检测，只跳过前置可用性判断。

数据流不新增端点、表、配置或缓存。`force` 由现有手动检测 JSON 请求传入服务层，仅在值为 `true` 时写入发往 Veridrop 的表单；Gemini 请求不发送长上下文字段，非 OpenAI 请求不发送 `wire_api`。该修正仍完全位于管理员检测路径，对 AI relay 主链每请求新增 DB、Redis、锁和协程成本均为 0。

验证包括：OpenAI 透传合法 `wire_api`、长上下文与 `force=true`；Gemini 不发送协议不支持的字段；前端类型检查、目标目录 lint、多语言同步和生产构建通过。

## 检测记录评分明细

### 目标与范围

- 检测记录列表继续保持单层、紧凑布局，只在存在可解析的完整报告时显示“查看明细”操作。
- 完整报告的分数与“查看明细”合并为明确的描边按钮（例如“82.2 分 · 查看明细”），避免弱化按钮混在状态文字中而被忽略；没有完整报告的记录仍只显示普通分数或错误原因。
- 点击后在独立弹窗中展示总分规则和逐检测项数据，不把数十个检测项直接嵌套到列表行中。
- 明细完全读取现有 `channel_veridrop_detections.result_json`，不新增接口、表、配置或后台请求。

### 数据与展示

完整报告按 Veridrop 当前结构解析：`total_score`、`verdict`、`summary`、`results[]`。每个检测项展示：

- `display_name` / `name`
- `status`
- `score`
- `weight`
- 对总分的加权贡献 `score × weight / 有效权重总和`
- `duration_ms`
- `error`
- `details` 字段级证据（按需展开，格式化 JSON）

评分规则在弹窗顶部明确说明：跳过项不进入分母；错误项保留权重并按报告中的分数参与（上游常规错误项为 0 分）；70 分及以上通过、50–69.9 分基本合格、低于 50 分未达标；严重问题可以把“通过”下调为“基本合格”。页面只解释上游已经执行的规则，不在前端重新决定最终结论。

### 边界与错误处理

- `result_json` 为空、不是合法 JSON 或缺少 `results` 时，不显示误导性的评分明细入口。
- 后端对空 `result_json` 使用 `omitempty`，列表响应可能完全缺少该字段；前端必须将其视为空报告，禁止直接调用字符串方法导致整页进入错误边界。
- 未知检测状态保留原始值；已知 `pass/fail/skip/error` 使用本地化标签。
- `details` 可能包含长响应摘录，默认折叠并限制弹窗内部滚动，不撑高列表和页面。
- 报告数据已在服务端通过现有凭据清理逻辑处理；页面不额外显示 API Key 字段。

### Main Chain Impact

该改动仅在管理员已加载的检测结果上进行前端 JSON 解析；不新增后端调用、DB/Redis 访问、锁、协程或 relay 主链成本。解析只在管理员打开明细时执行，列表渲染阶段仅判断报告字符串是否可能存在。

### 验证

- 有完整报告的通过结果显示“查看明细”，弹窗总分和逐项分数与原始 JSON 一致。
- 跳过项的加权贡献为空；有效项贡献之和与总分一致（允许显示舍入误差）。
- 失败但无完整报告的记录继续只显示错误原因，不出现空明细弹窗。
- 前端通过 typecheck、目标目录 lint、生产构建和七语言同步。

## 下载报告包含逐项检测详情

### 目标与范围

- “下载报告”不再只导出每个渠道/模型的一行总分，而是同时导出该次检测中 `results[]` 的每一个检测项。
- CSV 使用长表结构：一条检测记录有多少个检测项，就输出多少行；父级渠道、模型、总分和结论字段在各明细行重复，便于 Excel 筛选、排序和透视统计。
- 没有完整 `result_json` 的失败、排队、运行中或旧记录仍保留一行汇总数据，逐项字段留空，避免下载报告漏掉页面当前筛选结果。
- 下载范围继续严格等于页面当前服务端筛选结果，不额外导出未显示批次或未匹配记录。

### CSV 字段与数据流

每行包含两组字段：

1. 检测记录字段：记录 ID、渠道 ID、渠道、模型、协议、模式、记录状态、总分、总判定、摘要、错误、更新时间。
2. 检测项字段：检测项内部名称、显示名称、状态、分数、权重、加权贡献、耗时、错误、跳过原因、证据详情。

前端对当前结果逐条调用现有 `parseVeridropScoreReport(result_json)`：

- 可解析且包含检测项：对 `checks[]` 展平，每项生成一行。
- 空、无效或缺少检测项：生成一行父级汇总，检测项列为空。
- `evidence` 保留格式化后的完整 JSON；CSV 转义继续处理逗号、双引号和换行，避免证据内容破坏列结构。
- 分数 `0` 在已执行检测项中必须原样导出，不能因假值判断变成空白；跳过项的加权贡献继续为空。

### API、存储与错误处理

- 复用检测结果列表响应中的 `result_json`，不新增 API、数据库字段、迁移、配置、缓存或后台请求。
- 单条无效 JSON 不得中断整个下载；该记录退化为汇总行，其余记录继续正常导出。
- 下载按钮在当前筛选结果为空时保持禁用；浏览器生成 Blob 失败时沿用页面错误提示约定，不暴露原始凭据或内部异常。
- 证据来自服务端已经清理过的报告数据；导出逻辑不包含渠道 API Key、管理员令牌或请求认证头。

### Main Chain Impact

该功能仅在管理员点击下载时于浏览器内解析已加载的结果并生成 CSV。AI relay 每请求新增 DB、Redis、锁、连接池、协程和同步处理成本均为 0；管理后端也无新增调用。

### 测试与验收

1. 含 8 个检测项的记录导出 8 行，每行父级记录字段一致、检测项字段各自对应。
2. 通过、失败、错误和跳过项均导出状态、分数、权重、贡献、耗时、错误、跳过原因和完整证据；0 分不能丢失。
3. 无 `result_json`、无效 JSON 和旧记录各保留一行汇总，不影响其他明细。
4. 包含逗号、引号和多行 JSON 的证据在 Excel/CSV 解析后仍是单个单元格。
5. 通过前端 typecheck、目标文件 oxlint、Prettier、生产构建；部署后用真实含明细记录下载并核对行数和字段。

### 跳过原因说明

上游 Runner 会把未执行的检测器也写入 `results[]`，状态为 `skip`，并在 `details.skip_reason` 记录原因：

- `mode-excluded`：当前检测模式主动排除，未调用上游。例如 OpenAI 快速模式只执行基础请求、模型一致性和协议规范性；函数调用、结构化输出、流式一致性和 Token 计费不会发起请求。
- `model-excluded`、`unknown model`、`model lacks thinking support`：检测项不适用于当前模型，未调用上游。
- 长上下文未启用：可选探针未开启，未调用上游。
- `missing-usage`、`no observations` 等：相关调用或其他探针已经执行，但返回数据不足以评分；这类情况可能与中转响应缺字段有关，需要查看证据，不能显示成“模式主动跳过”。

评分弹窗为每个跳过项直接显示本地化说明，并明确标注“未发起调用”或“已调用但证据不足”；原始 `skip_reason` 仍保留在可展开证据中，未知原因不丢失。

## 批量检测与记录结果视觉层级优化

### 问题与目标

批量检测当前把搜索、三个筛选项和两个执行按钮强行压在同一行，中文和英文长文案均容易拥挤；按钮名称没有说明执行范围，筛选结果数量与已选数量又在下一行重复展示。检测记录的“状态徽标 + 分数详情按钮”视觉权重相近，且详情列再次显示相同结论，造成信息重复。截图中的英文泄漏并非语言切换失败，而是新增批量检测词条被错误写在 locale JSON 根节点，没有进入 `translation` 对象，运行时无法被 i18next 命中。

目标是让批量检测先完成“筛选与选择”，再清楚执行“当前结果”或“已选渠道”；让记录第一列一眼看出结论和分数，同时把“查看明细”降为次级操作；修复全部七种语言的词条位置和文案，不改变检测规则、筛选语义或任务接口。

### 批量检测布局与文案

- 工具栏改为两层：第一层是搜索和筛选，第二层左侧显示“共 {{total}} 个渠道，当前显示 {{visible}} 个 · 已选 {{selected}} 个”，右侧放置批量操作。
- 搜索框占主要宽度；状态、协议、可执行性使用相同宽度。`Detectability` 改为用户语义更直接的 `Availability`，中文“可执行性”；选项为“全部 / 可检测 / 不可检测”。
- “Detect filtered”改为“检测当前结果（{{count}}）”，明确只执行筛选后且可检测的渠道；“Detect selected”改为“检测已选（{{count}}）”。已选为 0 时主按钮禁用，当前结果按钮保持次级样式。
- 单行操作按钮使用“检测”，加载时显示“检测中”；不可检测渠道继续禁用，并在模型列说明不可检测原因。
- 中等宽度采用两列筛选布局，超宽屏再展开为搜索加三个筛选项；操作区单独成行，避免语言变化导致控件互相挤压。

### 检测记录层级

- 结果列合并为一个主状态徽标：有评分时显示“通过 88 分”“基本合格 63 分”“未达标 42 分”；任务错误仍只显示“失败”，跳过仍显示“已跳过”。
- “查看明细”改为紧邻状态的低强调文字按钮，不再使用与主状态相同尺寸的胶囊按钮；没有评分报告时不显示入口。
- 详情列优先展示摘要或错误原因；若内容仅等于结果判定（例如“基本合格”），显示短横线，避免同一结论在一行出现两次。
- 阈值保持现有规则：70 分及以上通过，50–69.9 分基本合格，低于 50 分未达标；不是 100 分才通过。

### i18n 修复

批量检测新增词条必须通过 `web/scripts/add-missing-keys.mjs` 写入七种语言的 `translation` 对象，并删除误写在 JSON 根节点的同名字段，随后运行 `bun run i18n:sync`。新增或调整的关键文案包括 `Availability`、`Detect current results ({{count}})`、`Detecting...`、`{{visible}} of {{total}} channels · {{selected}} selected`，以及带分数的结果标签。技术标识、渠道名、模型名和 API 地址保持原值。

### 数据流、接口与边界

不新增或修改 API、数据库、配置、缓存和任务参数。筛选仍在前端针对已加载目标计算；执行“当前结果”继续提交筛选后可检测渠道 ID，执行“已选”继续提交已选渠道 ID。筛选变化后清除已不可见或不可检测的选择，保持现有行为。空结果、加载失败、任务运行中和禁用原因继续复用现有状态组件。

### Main Chain Impact

本次仅修改管理员页面布局、展示计算和 locale 文件。AI relay 每请求新增 DB、Redis、锁、连接池、协程及同步计算均为 0；管理 API 调用次数和检测任务并发不变。

### 测试与验收

1. 中文环境不再出现截图中的 `Search channels`、`all`、`Detectability`、`Detect filtered`、`Detect selected` 或 `Detect`。
2. 在桌面、窄桌面和移动宽度下，筛选项与按钮不重叠、不截断，执行范围和数量可直接理解。
3. 状态、协议、可执行性和关键词筛选可组合使用；筛选后批量、勾选批量和单渠道检测提交的渠道集合正确。
4. 记录中的通过、基本合格、未达标、失败和跳过样式层级明确；50 分显示“基本合格”，70 分进入“通过”，不要求 100 分。
5. 七种语言词条均位于 `translation` 对象，根节点无误写字段；通过 i18n 同步、TypeScript、目标文件 oxlint、Prettier、生产构建和相关 Go 测试。

### 实现记录

批量检测已采用“筛选区 + 摘要与操作区”两层结构，三个下拉框显式渲染本地化选中值，避免内部值 `all` 泄漏到界面；当前结果和已选渠道分别显示实际可执行数量。记录结果已把判定和分数合并为主徽标，“查看明细”降为文字链接，详情等于判定时显示短横线，单渠道按钮在请求期间显示“检测中”。

## 下载报告改为可读的完整证据报告

### 问题与目标

当前下载功能虽然把每个检测项展开为 CSV 行，但仍把该检测项的整个 `details` 对象序列化到一个“证据”单元格。线上样本中 `protocol.details.issues` 有 25 项、`fingerprints` 有 10 项，这些数据实际都在单元格内；Excel 等表格软件默认只显示首行或截断高度，用户因此只能看到一项证据。渠道、模型、检测项和证据又全部铺在同一张长表中，不适合阅读、审查和打印。

本次将“下载报告”的默认产物从 CSV 长表改为自包含 HTML 详细报告。报告应完整列出每条记录、每个检测项及每个嵌套证据条目，提供清晰的阅读层级并可直接用浏览器打印或另存为 PDF。原始证据不得丢失或只展示首项。

### 报告信息架构

1. 报告首页显示生成时间、当前筛选范围、记录总数、已评分数，以及通过、基本合格、未达标、失败、跳过的数量摘要。
2. 每条检测记录独立成节，标题区优先展示结果、分数、渠道、模型和更新时间；协议、模式、记录 ID、渠道 ID、摘要和错误放在次级信息区。
3. 检测项不再使用横向宽表。每个检测项使用纵向卡片：标题、状态与分数在首行，权重、加权贡献、耗时、错误和跳过原因随后排列。
4. `details` 使用递归的键值区块展示：
   - 标量直接显示字段名和值；
   - 对象显示为带缩进的小节；
   - 数组显示数量，并把每个元素按 `1、2、3...` 独立列出；
   - `issues`、`fingerprints`、`tiers_tested`、token 序列等数组必须逐项完整输出，禁止只取第一项或拼成不可见的单元格内容；
   - 空对象、空数组和空字符串显示明确的空值符号，不伪造证据。
5. 每个检测项末尾保留“原始证据 JSON”折叠区作为无损兜底，确保未来 monitor 新增未知字段时仍可完整查看。
6. 打印样式避免在检测项卡片内部强制分页；长数组允许跨页，并重复必要的记录标题。报告不依赖网络、外部字体或脚本，下载后可离线打开。

### 数据流与实现边界

点击“下载报告”后，前端继续使用页面当前已经加载且符合服务端筛选条件的结果：`VeridropDetectionResult[]` → `parseVeridropScoreReport` → HTML 报告模型 → HTML 转义与递归证据渲染 → UTF-8 Blob → 下载 `.html` 文件。文件名包含生成时间。

`VeridropReportCheck` 需要同时保留结构化 `details` 和现有格式化 JSON，避免先转字符串再反向解析。报告生成必须对所有用户可控文本执行 HTML 转义，包括渠道名、模型名、摘要、错误、字段名和证据值；不得把证据内容作为 HTML 直接插入。单条无效 `result_json` 退化为记录汇总卡片，不中断整份报告。

本次不新增 API、数据库字段、配置、依赖、后台请求或服务端文件。下载范围仍等于页面当前结果；API Key、管理员令牌、认证头等凭据不进入报告。现有 CSV 构建函数从主下载路径移除，避免用户继续得到不可读的单元格报告。

### i18n 与交互文案

页面按钮改为“下载详细报告”，并补充七语言翻译。HTML 报告按当前界面语言生成，报告标题、摘要统计、字段标题、“完整证据”“原始证据 JSON”“无证据”等固定文案均通过现有翻译函数取得；渠道名、模型名、协议标识和原始证据字段保持原值。

### Main Chain Impact

报告仍只在管理员点击下载后于浏览器本地生成。AI relay 每请求新增 DB、Redis、锁、连接池、协程和同步处理成本均为 0；管理后端也不新增调用或存储。大报告的计算和内存仅发生在触发下载的当前浏览器标签页。

### 测试与验收

1. 使用包含 `issues=25`、`fingerprints=10`、`tiers_tested=3` 的样本生成报告，逐项文本和序号全部存在，首项和末项均可搜索到。
2. 一条含 8 个检测项的记录生成 8 个检测项卡片；多条记录之间层级清晰，不重复成百列父级字段。
3. 字符串中的 `<script>`、`&`、引号和换行只作为文本显示，不能执行或破坏报告结构。
4. 0 分、跳过项、错误项、无效 JSON、空数组、嵌套对象和未知字段均有稳定输出；任一坏记录不影响其他记录。
5. 下载文件可离线打开，中文不乱码，浏览器打印预览不横向溢出，检测项标题和内容不会无意义拆页。
6. 运行 TypeScript、目标文件 oxlint、Prettier、七语言同步、生产构建及前端样本生成断言；部署后用线上含 25 条问题的记录下载并核对完整证据。

### 实现记录

下载入口已改为生成自包含的 HTML 详细报告，报告按“记录 → 检测项 → 证据字段”纵向组织，不再把整段证据塞入 CSV 单元格。对象按字段展开，数组逐项编号；每个检测项同时保留可折叠的原始证据 JSON，因此新增字段和深层数组不会被截断。报告包含当前筛选条件、记录与结果摘要、分数、状态、权重、加权贡献、耗时、错误和跳过原因，可离线打开并通过浏览器打印为 PDF。

实现使用当前界面语言生成固定文案，七种 locale 均已补齐；所有动态内容在插入 HTML 前统一转义。样本断言覆盖 8 个检测项、25 条问题、10 个指纹、3 个层级、跳过原因、原始 JSON 与恶意 HTML 字符串，均完整输出且没有脚本注入。TypeScript、目标文件 oxlint、Prettier 和生产构建已通过。完整 Go 回归的非 `model` 包均通过；共享 MySQL `model` 测试集仍受历史测试数据影响，本次修改不涉及 Go、数据库或 relay 主链。

为避免下载后一次展开大量记录和证据，报告现在默认只展示总览和每条记录的结论摘要。记录摘要增加协议和模式标签，记录与检测项均使用明确的展开箭头和打开状态边框；点击记录可查看其检测项，点击检测项后再查看元数据；完整证据和原始 JSON 保持单独折叠。

证据字段不再在文件打开时递归转换为大量 DOM 节点。报告把每个检测项的原始结构化数据只保存一次，且不再在报告解析阶段预先格式化整段 JSON；打开“完整证据”或“原始证据 JSON”时才在本地渲染对应内容。打印前会渲染全部结构化证据但不重复输出原始 JSON。该内联脚本不访问网络、文件或外部来源，保留离线查看能力，并显著降低大报告打开时的布局和绘制成本。
