# 检测记录结果多选筛选

## 目标和范围

将“真伪检测 > 检测记录”页的单选“结果”筛选改为多选，使管理员可以组合查看多个结果类别，例如“通过 + 基本合格”或“未达标 + 失败”。筛选必须作用于数据库完整匹配集合，不能只过滤浏览器当前加载的最多 100 条记录。

本次修改检测结果查询、精确匹配数量和对应管理界面，不修改评分规则、检测任务、自动调度、报告内容、渠道状态或 AI 转发链路。旧的单值 `outcome` 查询参数继续兼容。

## 交互设计

- 继续使用当前紧凑筛选栏和 Base UI `Select`，启用原生 `multiple` 模式，不新增弹窗。
- 可选结果包括：检测中、通过、基本合格、未达标、失败、已跳过、已取消。
- 未选择任何结果时表示“全部”；选择 1 项时显示该结果名称；选择 2 项及以上时显示“已选 N 项”，避免长文案挤压筛选栏。
- 下拉菜单保持打开以便连续勾选，Base UI 负责勾选标记、键盘操作和焦点行为。
- “重置筛选”清空结果数组并恢复“全部”。
- 切换选择后立即生成新的 React Query 查询键并向服务端查询，不保留单选和多选两套前端状态。
- 结果统计继续展示忽略结果筛选后的完整分类分布；“匹配结果”数量按已选结果类别之和精确计算。

## 数据流

1. 用户勾选或取消一个结果类别。
2. React 状态保存去重后的结果数组；空数组表示不限制结果。
3. 前端将非空数组序列化为逗号分隔的 `outcomes` 参数。
4. Controller 校验所有枚举值、空片段、重复值以及新旧参数冲突。
5. Model 将所有合法类别条件组成一个括号包裹的 `OR` 条件，再与渠道、模型、批次、模式、时间等条件按 `AND` 组合。
6. API 返回完整筛选集的前 100 条、精确 `matching_count` 和不受结果筛选影响的统计分布。

## API 契约

沿用现有管理员接口：

`GET /api/channel/veridrop/results`

鉴权保持不变，仍由真伪检测管理资源对应的管理员权限控制。

新增可选参数：

- `outcomes`：逗号分隔的结果枚举，允许值为 `in_progress`、`passed`、`completed`、`low_score`、`failed`、`skipped`、`cancelled`。
- 示例：`outcomes=passed,completed,low_score`。
- 未提供 `outcomes` 和 `outcome` 时不限制结果。
- 旧的单值 `outcome` 保持兼容，并在服务端转为单元素结果集合。
- 同时提供 `outcome` 和 `outcomes`、包含空片段、未知值或重复值时，返回现有国际化“参数无效”业务错误。

响应结构不变；`matching_count` 表示所选类别的匹配数量之和，`summary` 仍忽略结果筛选。

## 数据模型和查询设计

不新增表、字段或迁移。`ChannelVeridropDetectionListOptions` 增加结果数组，同时保留旧单值字段供现有调用兼容。

结果分类继续使用后端统一定义：

- `in_progress`：`queued` 或 `running`；
- `passed`：`done` 且判定为 `passed`、`pass` 或 `success`；
- `completed`：普通完成记录，或 `marginal` 且分数不低于 50；
- `low_score`：`done`、`marginal` 且分数低于 50；
- `failed`：`error`、`timeout`，或 `done` 且判定为 `failed`、`fail` 或 `error`；
- `skipped`：`skipped`；
- `cancelled`：`cancelled`。

多项结果使用单个括号包裹的 `OR` 组，防止后续 `AND` 条件改变逻辑优先级。查询继续使用 GORM 参数绑定和兼容 SQLite、MySQL、PostgreSQL 的 SQL 表达式。

## 索引设计

不新增索引。结果查询继续复用现有批次、更新时间、状态与分数索引；结果枚举最多七个固定分支，管理员查询仍有 100 条返回上限。统计聚合复用现有筛选条件，不增加额外查询次数。

## 配置参数

不新增配置参数。

## 业务边界和错误处理

- 空数组等同“全部”，前端不发送空 `outcomes`。
- 服务端去重仅用于防御性处理；HTTP 输入中的重复值按无效参数拒绝，避免含糊请求。
- 多个结果类别之间按并集查询，每条记录最多返回一次。
- 无匹配数据继续使用现有空状态。
- 查询失败记录底层错误，并向前端返回现有可重试提示，不泄露 SQL 错误。
- 新增用户可见文案通过 `t(...)` 并同步全部七种语言。

## 与现有子系统的关系

筛选只读取 `channel_veridrop_detections`，不访问渠道密钥，不修改 `channels`，不触发检测任务、清理任务、计费、Redis 或渠道自动禁用逻辑。下载报告继续使用页面已取得的筛选结果，并在筛选摘要中列出全部已选结果名称。

## Main Chain Impact

AI relay 请求协程不执行任何新增代码。新增参数解析和数据库查询只发生在管理员检测记录页面，每个 relay 请求新增 DB、Redis、锁和 goroutine 成本均为 0。

## Shared Resource Audit

- `channel_veridrop_detections`：后台检测任务写入，管理员页面读取；AI relay 主链不访问。
- 数据库连接池：多选仍复用现有一条列表查询和一条统计查询，不新增连接池或后台任务。
- React Query 缓存：结果数组加入现有查询键；与 relay 无共享缓存命名空间。
- Redis、文件句柄、goroutine 池：无新增使用。

## 测试设计

实施前先补充以下测试：

1. Model 等价类：空数组不筛选；单元素与旧单值结果一致；`passed + completed` 返回两类并集。
2. Model 决策覆盖：`in_progress + failed + skipped + cancelled` 覆盖状态集合、完成判定和终态分支，且每条记录只返回一次。
3. Model 组合条件：多结果与渠道、模型、最新批次、时间和排序叠加后仍保持正确的括号优先级。
4. 统计：`matching_count` 等于所选类别之和，`summary` 不随结果多选变化。
5. Controller 合法输入：旧 `outcome` 与新 `outcomes` 分别成功。
6. Controller 非法输入：未知值、空片段、重复值、新旧参数同时提供均返回参数错误。
7. 前端静态验证：TypeScript、oxlint、Prettier、七语言 i18n 和生产构建通过。
8. 手工交互：连续勾选、取消、清空、重置、刷新、切换其它筛选和报告筛选摘要均正确。

- 数据库查询使用括号包裹的结果条件并集，`matching_count` 返回所选类别的精确合计，`summary` 继续返回忽略结果筛选后的完整分布。
- 已补充 Model 与 Controller 回归测试，并完成 Go、TypeScript、oxlint、i18n 和生产构建验证。
