# 请求日志多用户名筛选

状态：已按用户确认实施；沿用现有开关，不新增开关。

## 目标与范围

请求日志设置允许指定多个登录用户名，命中任意一个即记录请求和返回内容。例如 `十三,张三,李四`。复用现有文本输入框、`RequestLogUsername` 配置和日志存储流程，不增加用户选择接口，也不改变日志详情权限。

现有实现见 `middleware/request_logger.go` 的 `requestLogUsernameMatches`，当前对整个字符串执行去空白和大小写不敏感比较。存储架构沿用 [请求日志内存索引与磁盘存储](request-log-memory-index-disk-store.md)，本设计仅扩展用户名过滤语义。

## 匹配规则和边界

| 配置值 | 行为 |
| --- | --- |
| 空字符串或纯空白 | 保持原有全量记录行为 |
| `十三` | 仅匹配登录用户名十三 |
| `十三,张三` | 匹配十三或张三 |
| `十三，张三` | 中文逗号与英文逗号等效 |
| ` 十三 , , 张三， ` | 去掉每项首尾空白，忽略空项 |
| `Alice,bob` | 大小写不敏感，保持 `strings.EqualFold` 语义 |
| `十三,十三` | 重复项不影响结果，每个请求仍只记录一次 |
| `, ， ,` | 非空配置但无有效用户名，不匹配任何用户，避免意外全量记录 |

匹配必须是完整用户名，不支持子串、通配符、显示名、邮箱或用户 ID。未知用户名可以保存但不会匹配；不为校验名单查询用户表。名单非空时，无法解析用户名的请求不匹配。

逗号成为保留分隔符，不支持转义；原先包含逗号的完整用户名配置将改变含义。已核查 `model.User.Username` 仅声明 max=20 校验，注册入口去首尾空白并验证非空，没有禁止逗号，因此历史含逗号用户名确实存在兼容性边界。用户名内部空格保留，不把空格、分号当作分隔符。

## 数据流

1. 管理员填写用户名列表，沿用表单保存逻辑提交字符串。
2. 现有设置接口完成鉴权、保存 `options` 配置并更新运行时值；重启沿用原配置加载流程。
3. 请求日志开关开启时，仍按现有逻辑采集请求和返回内容；请求结束后使用 context 的登录用户名匹配列表。
4. 匹配成功才进入现有非阻塞队列；context 仅有用户 ID 的既有分支继续由后台 worker 解析用户名。
5. worker 使用同一匹配规则再次检查，然后沿用批量写盘和内存索引登记。
6. 日志列表、详情、清理、快照和客户端 AI 响应契约保持原状。

配置修改不会重新筛选历史日志。维持 worker 按处理时配置再次过滤的现状：修改名单时，排队中的请求可能按新名单丢弃；此前已过滤掉的请求不会补录。

## API 契约与权限

不新增端点。沿用 `GET /api/option/` 和 `PUT /api/option/`，受 `AdminAuth()` 和 `RequireSystemSettingsScope` 保护，请求日志设置域为 `operations.request-log`，读写分别要求 view/edit 权限。

保存示例：

```json
{"scope":"operations.request-log","key":"RequestLogUsername","value":"十三,张三"}
```

读取继续返回原有设置列表中的 key/value 字符串；保存继续使用现有 success/message 响应。失败沿用设置接口的日志、国际化错误和前端反馈，不增加响应结构或公共端点。

## 数据模型与配置

复用 `options` 中已有的 `RequestLogUsername` 字符串，不增加表、列、索引或迁移。SQLite、MySQL、PostgreSQL 均沿用既有配置持久化逻辑；不新增大表查询，无需 EXPLAIN。

不新增配置参数。现有 `RequestLogEnabled` 是功能开关，可即时关闭整个请求日志功能。现有请求体积、队列容量、保留数量和清理阈值继续生效；不迁移现有配置到另一套配置框架。

## 实现方式与页面说明

在现有匹配函数内按英文逗号和中文逗号扫描字符串，逐项取子串、TrimSpace、EqualFold，命中立即返回。优先采用单次扫描，避免每次请求创建名单切片、map 或 lowercase 字符串；不添加缓存和锁。

沿用当前输入框和按钮布局，提示支持中英文逗号分隔多个登录用户名，留空记录全部。补充示例占位文案，并说明仅分隔符不会记录任何用户。同步维护 en、zh、zh-TW、fr、ru、ja、vi 七种语言。实施前加载项目 i18n、shadcn-ui 和 React 技能，不改上游托管的认证与 API 基础文件。

## 错误处理与子系统交互

名单解析不产生 I/O 或业务错误；空项、重复项直接兼容，不使 AI 请求失败。保存失败继续使用既有设置接口和表单错误反馈。后台异常继续由现有日志 worker 的 recover 和系统日志处理。

不改变计费、配额、上游请求转换、流式返回、日志内容或日志查看权限。多个用户会增加相较单用户的命中量，但仍受原有队列与存储上限约束；队列满继续丢弃日志并限频告警。

## Main Chain Impact

同步新增工作仅为内存字符串扫描与比较；不开连接，不新增 DB/Redis 调用、文件操作、锁或 goroutine。原有正文采集仍在请求过程中执行，名单匹配仍在请求结束时执行，因此本改动不会减少未命中请求的既有采集开销。

后台继续由固定 worker 解析缺失用户名、二次过滤、写日志文件并登记索引。请求日志开关关闭时走原有直接放行分支。所有共享资源及其主链路关系列于下一节。

## Concurrency Analysis

30,000 RPM 约 500 请求/秒，100,000 RPM 约 1,667 请求/秒。设配置文本长度为 L，单次匹配时间复杂度 O(L)、辅助空间 O(1)，无列表构造；常规已知用户名路径每个请求同步匹配一次，命中后 worker 再匹配一次。

增量成本：每请求 DB 调用 0、Redis 调用 0、锁 0、goroutine 0。假设配置为 100 个用户名、总长约 3.2 KB，则 100k RPM 全命中情况下两次扫描的上界量级约为每秒 10.7 MB 文本；这是扫描规模估算，不是延迟实测。100k RPM 下总吞吐仍受原有正文大小与磁盘性能限制，不以这项估算宣称全量日志可持续写入。

实施时 benchmark 覆盖 1、10、100、1,000 项的首项命中、末项命中和未命中，并报告 ns/op、allocs/op。超长配置线性增加 CPU 成本，不引入无依据的硬上限；若测得常见规模无法满足亚毫秒筛选要求，再调整设计后实施。

实测（Windows amd64，Ryzen 7 8700G，`-benchtime=100ms`，8 字节 ASCII 用户名）：1/10/100/1,000 项末项命中分别为 18.55/147.5/1,387/16,659 ns/op；1,000 项未命中为 11,960 ns/op。所有场景均为 0 B/op、0 allocs/op。该结果是匹配函数微基准，不代表整个日志管线的负载能力。

服务器为 2 核、约 2 GB 内存。在服务器上启动独立的回环 HTTP 测试进程，使用本次源码的真实 `RequestResponseLogger`、有界队列、4 个 writer 和磁盘日志存储；处理器提供模拟响应并设置测试用户名。每请求约 1 KB 输入、2 KB 输出，64 个客户端 worker，队列容量 1,000。alice、bob、outsider 三个用户均匀轮流发送；单用户名单为 alice，多用户名单为 ` alice，bob,alice `。

分别以 500 和 1,667 请求/秒测试关闭日志、单用户、多用户三种模式，每档 20 秒。总请求数 130,020。HTTP 延迟从客户端发出请求到读完响应计算，不含生成器排队时间；本次生成器未丢弃请求。测试完成后排空日志队列，核对落盘数量、用户名及 request ID 唯一性。
