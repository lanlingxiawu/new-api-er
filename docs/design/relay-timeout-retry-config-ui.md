# 超时与重试的配置界面重构

状态：已实现（第 3/4/5 节）
日期：2026-09-23

## 1. 问题

### 1.1 配置入口成片缺失（实现遗漏）

[渠道重试的次数与时长控制](relay-retry-time-budget.md) 的后端已完成并在测试服验证通过，但管理界面上有三项配置**根本没有入口**，只能改数据库：

| 配置 | 后端 | 界面 |
|---|---|---|
| `relay_timeout_setting.retry_min_budget_seconds` | 已实现 | 缺失 |
| `relay_timeout_setting.max_total_attempts` | 已实现 | 缺失 |
| `GroupRetryTimes`（分组重试次数） | 已实现（OptionMap 路径 + 校验） | 缺失 |

前两项属于 `system-tuning` 页「AI Request Timeout」区块的字段清单（`hot-config-sections.tsx` 的 `relayTimeoutFields`）与默认值表（`defaults.ts`），漏加；第三项是分组 → 整数的映射，需要独立编辑器，完全未做。

该功能此前被报告为"前端完成"，实际只完成了用户抽屉内的字段。这是报告不准确，不是范围调整。

### 1.2 用户抽屉的超时区块过载

`users-mutate-drawer.tsx` 的「AI 请求超时」区块当前有 **7 个控件**，外加三句连排的说明文字：

```
流式响应超时模式（下拉）   流式响应超时（秒）   流式总时长超时（秒）
非流式响应超时（秒）       非流式总时长超时（秒）
重试次数                   非流式超时计费（下拉）
```

说明文字："每个请求同时受响应超时和总时长超时限制。四项全为 0 时沿用原有行为；否则 0 表示继承系统默认值，-1 表示关闭该项限制。10 分钟示例：流式响应 600、流式总时长 -1；非流式响应 -1、非流式总时长 600。"

两个具体问题：

- **对称重复**：`stream_response_timeout` / `non_stream_response_timeout`、`stream_total_timeout` / `non_stream_total_timeout` 是两两对称的。绝大多数场景下管理员对两种模式想要的是同一个值，却必须填四次、理解四个标签。
- **说明承担了过多解释**：`0` / `-1` 的三态语义、"四项全为 0"的接管前提、一个需要读两遍才能理解的示例，全压在一段文字里。

## 2. 目标与范围

让常见配置只需两个输入，同时不牺牲分别配置流式/非流式的能力；并把三项缺失的配置补上入口。

范围内：

- 用户抽屉超时区块按请求类型呈现：流式三个字段，非流式一个时长加超时计费；
- 系统设置补齐两个标量字段；
- 新增分组重试次数编辑器；
- 相应的七语言 i18n。

范围外：

- **后端语义与数据模型一律不动**。用户表仍是五个超时字段 + `retry_times` + `non_stream_timeout_billing`，`0` / `-1` 的三态语义不变，接管前提（四项全为 0 则不接管）不变。本方案纯粹是呈现层重构。
- 不改系统设置页的整体信息架构，只在既有 `system-tuning` 页内增删。

## 3. 用户抽屉：按请求类型呈现

> 2026-09-24 确认（替代先前的「统一 / 分别」两档方案）：流式、非流式按各自的实际行为给字段，不设开关；非流式只留一个时长；超时计费挪到非流式旁边。

### 3.1 依据：两种请求的超时行为不同

| | 流式 | 非流式 |
|---|---|---|
| 返回方式 | 先首包，再持续输出 | 上游生成完才一次性返回 |
| 响应计时器 | 等首包（或按静默间隔），之后另有阶段 | 首字节到达即生成完成，与总时长管的是同一件事 |
| 需要的字段 | 响应超时（含模式）+ 总时长，两个都有意义 | **一个时长** |
| 超时时的上游成本 | 已交付内容即结算依据 | 上游通常已完成计费；由「超时计费」决定平台还是用户承担 |

超时错误不重试（`SkipRetry`），所以非流式的「响应超时」与「总时长」只差在总时长还计入先前失败尝试的时间，实际没有区分价值。先前的「分别配置」开关只是为了在两组字段间切换，按请求类型固定呈现后不再需要。

### 3.2 形态

```
AI 请求超时
  0 继承系统默认值，-1 表示不限制。

  流式请求
    响应超时模式（下拉）
    响应超时（秒）          总时长超时（秒）

  非流式请求
    超时时长（秒）          超时计费（下拉）

重试
  重试次数
```

- 流式三个字段沿用原字段与文案（`stream_response_timeout_mode` / `stream_response_timeout` / `stream_total_timeout`）。
- 非流式「超时时长」：从发出请求到拿到完整结果的最长时间，含重试。
- 「超时计费」从原「重试与计费」分区移到非流式旁：它只对非流式超时起作用。描述按当前值说明谁承担上游成本。
- 原「重试与计费」分区改名「重试」，只含重试次数；左侧导航同步。

### 3.3 数据映射（后端与数据模型不变）

用户表仍是 `non_stream_response_timeout` 与 `non_stream_total_timeout` 两列，接口、缓存、校验、超时中间件都不动。

- **保存**：非流式超时时长同时写入这两列（相同值）。`0` 两列都继承系统默认，`-1` 两列都不限制，与原语义一致。
- **打开抽屉时的显示值**（两列可能是旧界面分别设置的）：
  - 两列相等 → 该值；
  - 否则取其中较小的正数（先到期的那个才是实际生效的限制）；
  - 没有正数时取响应超时一列的值：非流式要等生成完才有响应，且系统默认总时长不限，所以响应 `-1`、总时长 `0` 原本就不限制，显示 `-1`；响应 `0`、总时长 `-1` 原本受系统默认响应超时约束，显示 `0`。（曾经的规则"两列都是 `-1` 才显示 `-1`，否则 `0`"会把前一种显示成 `0`，一保存就套上系统默认的 300 秒，比原来更严。）
  - 核对用例（前端无测试框架，记录在此）：`(0,0)→0`、`(-1,-1)→-1`、`(-1,0)→-1`、`(0,-1)→0`、`(300,600)→300`、`(600,-1)→600`、`(-1,600)→600`、`(600,0)→600`。
- 两列不相等时，字段下方提示「此前分别设置为 响应 X 秒 / 总时长 Y 秒，保存后统一为 Z 秒」，避免静默改写。

现网数据（2026-09-24，香港测试服 134 个用户）：132 个四项全为 `0`，2 个测试账号设了 `1`，其中一个两列不等（`0` / `1`），按上面规则显示 `1` 并出提示。

### 3.4 文案

- 区块说明：「0 继承系统默认值，-1 表示不限制。」
- 非流式超时时长：「从发出请求到拿到完整结果的最长时间，含重试。非流式要等上游生成完才返回，所以只需要一个时长。」
- 超时计费：
  - `refund`：「超时不向用户计费。非流式超时时上游通常已完成计费，这部分成本由平台承担。」
  - `charge`：「超时按模型已产生的用量向用户计费，即使用户没有拿到结果；上游成本由用户承担。」

## 4. 分组重试次数编辑器

### 4.1 位置

放入 `system-tuning` 页，作为「AI Request Timeout」之后的独立 section（`section-registry.tsx` 新增一条），id `group-retry-times`，标题「分组重试次数」。

理由：它与重试闸门是同一主题，且 `system-tuning` 页的既有 section 都是「影响转发行为的运行参数」。放 `models/` 页（分组倍率所在）会与计费主题混淆。

### 4.2 形态

`GroupRatio` 的编辑器（`group-ratio-form.tsx` 852 行 + `group-ratio-visual-editor.tsx` 1370 行）承载了倍率特有的批量操作与价格联动，整体复用不合适。分组重试是「分组名 → 整数」的简单映射，新建一个轻量编辑器：

```
分组重试次数
  某个分组未配置时，使用系统默认重试次数。

  [分组下拉 ▾]  [次数输入]  [删除]
  [分组下拉 ▾]  [次数输入]  [删除]
  [+ 添加分组]

  [保存]
```

- 分组下拉的候选来自已有分组列表（与用户抽屉的 `GroupCombobox` 同源），避免手输错分组名产生永不生效的配置；
- 次数输入沿用用户抽屉里 `TimeoutOverrideField` 的数字输入语义（`-1` / `0` / 正整数），`min=-1`、`max=20`（与后端 `MaxGroupRetryTimes` 一致）。输入框内容按原始文本保存、保存时再解析：数字输入框在只键入 `-` 时上报空串，若立即转成数字会被改写成 `0`，`-1` 就无法手动输入；
- 每行下方一句取值说明：`-1` 不重试（该分组只尝试一次）、`0` 跟随系统默认。切组沿用 main 语义，配额为 0 时不会切到下一组（见 [relay-retry-time-budget.md](relay-retry-time-budget.md) 第 22 节），所以文案不提切组。

### 4.3 保存

复用既有单键保存：`useUpdateOption()` → `PUT /api/option`，key `GroupRetryTimes`，value 为 JSON 字符串。后端 `controller/option.go` 已有 `CheckGroupRetryTimes` 校验分支，`model/option.go` 已有 `UpdateGroupRetryTimesByJSONString` 落库分支——两者在上一轮已实现，本节不需要后端改动。

前端提交前本地做一次同样的校验（值必须是 `-1` 或 `0..20`），把错误在保存前就显示在对应行，而不是等后端返回一句整体错误。

### 4.4 空值处理

编辑器为空（没有任何一行）时提交 `{}`，语义是"所有分组都跟随系统默认"。不是删除该 option 键——保留空对象可以让管理员区分"从未配置过"与"显式清空"。

## 5. 系统设置的两个标量字段

补入 `relayTimeoutFields`（`hot-config-sections.tsx`）与 `systemTuningFallbackSettings`（`defaults.ts`）：

| key | 标签 | 范围 | 默认 |
|---|---|---:|---:|
| `retry_min_budget_seconds` | 剩余预算低于此值不再重试（秒）；说明文案注明「0 = 关闭（默认）」 | 0–604800 | 0 |
| `max_total_attempts` | 单请求最大尝试次数（0 = 不限制） | 0–100 | 0 |

这两项与既有三项同属一个配置组，走 `PUT /api/option/group` 整组保存，后端白名单 `relayTimeoutFields`（`model/config_group.go`）已在上一轮补齐。

界面上需要一行提示说明二者的依赖关系：**剩余预算检查仅在配置了总时长超时时生效**；总时长为 `0` 时只有最大尝试次数起作用。这是 [relay-retry-time-budget.md](relay-retry-time-budget.md) 第 4 节的前提，管理员必须能在设置页看到。

实现：`ConfigGroupField` 新增可选 `description`，渲染在输入框下方；只有 `retry_min_budget_seconds` 使用。

## 6. 数据模型与 API

无变更。不新增表、列、迁移、端点。用户表字段、`options` 键名、保存路径全部沿用。

### 6.1 设置作用域登记（三处必须同步）

系统设置页的读和写都带 `scope`，后端按作用域白名单过滤。新增字段或 section 时，只改 `model/config_group.go` 的存储白名单是不够的：

| 位置 | 作用 | 漏登记的后果 |
|---|---|---|
| `service/settingsaccess/scopes.go` | 作用域 → 可读写的 option 键 / 配置组字段 | 读：`GET /api/option/?scope=` 不返回该键，界面静默显示回退值；写：`AllowsGroup` 按整组校验，**任一字段不在白名单，整个 section 都保存失败** |
| `service/authz/resources_system_settings.go` | 权限目录（可授予非 root 管理员） | 中间件 `settingsaccess.Resolve` 之后的权限检查无从授予 |
| `model/config_group.go` | 配置组的存储白名单 | 保存被拒 |

本功能登记为：`system-tuning.relay-timeout` 追加 `retry_min_budget_seconds`、`max_total_attempts`；新增作用域 `system-tuning.group-retry-times`，只放行 `GroupRetryTimes` 一个键（不得顺带放行 `GroupRatio` / `RetryTimes`）。`service/settingsaccess/relay_retry_scope_test.go` 按界面实际提交的载荷锁定这三点，已验证在未登记的代码上失败。

## 7. 错误处理

- 分组重试编辑器：本地校验失败时在行内显示，不发请求；后端返回的业务错误由既有的全局拦截器提示（`useUpdateOption` 已处理，不重复弹提示）。
- 用户抽屉：沿用既有 `zodResolver` 校验与 `FormMessage` 呈现。

## 9. 验证方式

前端无测试框架（Rule 15.7），门禁为 `bun run typecheck` 与 `bun run lint`；改动过的文件另需保持 `oxfmt` 干净（`bun run format:check` 全仓有 138 个历史未格式化文件，不能整体作为门禁，只逐文件比对）。此外必须做渲染核验，不能只靠类型通过：

2. 打开用户编辑抽屉，确认流式三项、非流式一项加超时计费；两列不一致的老数据显示先到期的值并出提示；保存后两列统一；
3. 打开 `system-tuning` 页，确认两个新字段可保存、分组重试编辑器可增删行并保存；
4. 保存后重新打开，确认值正确回显（验证读写两侧都通）。

# 2026-09-29 审计修正：非流超时继续分别编辑

非流请求的两个计时器不能在管理界面合并：

- `non_stream_response_timeout` 是单次上游尝试的完整响应等待时间；普通重试开始时会重启。
- `non_stream_total_timeout` 是包含所有重试与内部回退的请求级总时长；不会重启。

界面继续分别展示、校验和提交这两列。打开或保存用户抽屉不得推导、合并或互相覆盖历史值；编辑其他用户字段时，两列必须原样往返。

布局复用流式超时区域的双列 `TimeoutOverrideField`：

- “Non-stream response timeout (seconds)”：说明其约束单次上游尝试。
- “Non-stream total timeout (seconds)”：说明其覆盖整个请求和全部重试。
- “Timeout billing” 保持在同一非流区域，继续独立控制超时后的退款或按已产生用量计费。
