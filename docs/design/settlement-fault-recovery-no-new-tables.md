# 数据库故障恢复修复：不新增表

用户已指定不新增表。本修订替代 [原方案](settlement-fault-recovery.md) 的两张新表设计，不增加模型、列、索引，不把 options 或任务租约表当资金流水。

## 目标与范围

修复真实双库复现的批量增量丢失、直接结算明确失败后不恢复、活动 fallback 无法直接回放及成本缺少日志关联。保留现有计价、usage、鉴权和上游返回。完全断连造成鉴权 500、容量瓶颈和历史未知账单追偿单独验收。

## 复用已有结构

仓库已有 BusinessStatsAppliedBatch，已在既有迁移列表中，具有唯一 batch_key 和 applied_at。核对当前代码未发现其他运行时代码使用或清除此表。复用其业务批次提交回执语义，采用独立 `quota_recovery:v1:` 前缀、随机批次 ID 和负载 SHA256，避免键冲突。

失败恢复数据使用独立目录中的带版本/校验和文件。成本/佣金沿用 log_id 唯一约束；fallback 保留已有 Accounting/QuotaData 字段，在真实日志 ID 产生后再写财务记录，不再先写无法关联的 NULL log_id 记录。不能猜测回填没有可靠映射的旧账单。

## 数据流与核心逻辑

- 批量：原有短锁交换快照 → 后台保存批次文件 → 主库事务检查批次回执，未提交时写回执并更新本批全部增量 → 提交 → 确认并删除文件。相同批次重试时，回执与额度更新同事务，已提交不再加减。
- 文件持久化失败时保留已取快照，新流量仍进入新 map。数据库或进程恢复后续做，不覆盖/丢弃失败批次。
- 非批量：只将服务器明确拒绝执行的失败更新（如 MySQL 1290、PG 25006）送入同一后台恢复机制。钱包成功而 token 失败时只补 token；缓存已调整的步骤不再次调整缓存。
- 预扣 db=true 失败仍返回失败，不延后扣一个没有执行上游的请求。网络超时/断连等旧式更新的提交结果不确定时，不假定没提交而再扣，保留需核对状态。
- 日志：后台持久化 fallback 中的待记账数据；回放插入日志后获得真实 ID，再执行财务 continuation。财务未完成不能先删恢复负载；重复处理使用既有 log_id 防重。
- 在既有文件锁内轮换活动 fallback，随后释放锁做回放，不要求重启；后台恢复与手动回放使用同一有界协调。旧 relay_log_only 格式不补造收费。

## API、模型与配置

不新增表、列、索引或公共接口。沿用管理 status/replay 接口及原权限。新恢复路径通过 setting/operation_setting 的配置快照开关控制；worker、文件/队列容量、批次大小、DB 超时有界。关闭不删除已保存恢复任务。不记录 API 密钥、密码、DSN。

现有回执的保留期必须覆盖所有可重放文件，不能短 TTL 删除后使旧文件重复扣费。旧部署若缺少仓库早已声明的回执表，由原迁移流程处理，恢复 worker 不临时建表；本次不增加迁移定义。

## Main Chain Impact

正常路径不增加同步 DB 查询、Redis 调用、文件写入或逐请求提交回执。新增的是已有错误后的分类和有界入队；持久化、事务、重试、回放、关联在后台。生产者锁内不做文件/DB I/O，不按每请求生成无界 goroutine，不等待恢复队列。

## Shared Resource Audit

users/tokens/channels/订阅表与主链共享：仅按主键执行已确定差额，短事务、超时，不跨上游调用持锁。回执复用已有唯一索引，使用独立前缀；不触及用户、token Redis 命名空间之外的新热路径键。缓存恢复不能重复 INCRBY。后台固定 worker，限制连接/队列，不挤占主链连接池。文件使用独立恢复目录和既有 fallback 锁；坏文件保留并告警。

## Concurrency Analysis

100000 RPM≈1667 请求/秒。正常主链新增 DB/Redis 调用目标为 0；回执随后台批次写，非每请求写。分批、有限并发、DB 超时和失败退避避免恢复任务抢占数据库；文件同步在后台按批进行，不持生产者锁。容量仍需重新实测，原容量失败不自动转绿。

## 完整生命周期与错误处理

先保存恢复文件，再提交带回执事务。事务提交后文件未删除，重启凭相同键跳过额度更新。启动仅有界恢复，不同步排空历史任务阻塞监听。磁盘满、坏行、任务满、worker panic 必须可观测，不伪报任务完成。

首次后台持久化前的内存增量被 kill -9 仍存在丢失窗口，本次不承诺消除。旧式同步操作提交结果不确定时不自动猜测重扣。资金失败与日志失败分别保留状态，不把响应交付当作钱包提交证明。

## 测试先行

1. 批量开/关各 4 JSON＋4 SSE，应收 1200，MySQL 只读恢复后钱包/token/计数/日志/成本一致。
2. 新旧增量并发、事务中途失败、同批次重复提交、提交回包丢失、文件删除前重启：只提交一次。
3. 预扣失败不延迟扣费；钱包/token 部分提交、退款、订阅、零差额、额度边界和未知提交分别断言。
4. PG 只读后活动文件无需重启可回放；成本关联齐全；第二次回放无重复收费、统计或记录。
5. 文件/容量/Redis/worker 故障不引入主链阻塞，缺口不能静默隐藏。
6. 仓库兼容检查覆盖真实 SQLite/MySQL/PostgreSQL；生产路径验收使用真实 MySQL 主库＋PG 日志库＋Redis，SQLite 不作替代。
7. 相关包测试、race、独立 relaykit 构建；重复启动无新增 DDL，容量和启停门槛单独核验。

## 2026-11-06 实施与验证

已按本方案实现，不新增 GORM 表模型、字段、索引或迁移定义。额度提交回执复用已存在且已纳入原迁移的 `business_stats_applied_batches`，键前缀为 `quota_recovery:v1:`。不是在启动时临时创建另一张恢复表。

实际恢复流程：

- `model/quota_recovery.go` 保存有 SHA256 校验的批次文件，再将每至多 500 项更新与对应回执放入同一事务；提交后才删除文件。每轮至多处理 16 个文件，DB 预算 3 秒，单个快照至多 10000 项，目录保留上限 1024 项。
- 已同步但未重命名的 `.json.tmp` 在后续轮次恢复；坏文件隔离保留，不不断占用前 16 个可执行文件的位置。保存失败时保留已取出的快照；原有生产者 map 继续聚合新增量，不承诺磁盘持续故障时内存无限可用。
- 钱包、令牌终结算及退款/已成功预扣的补偿，仅在服务器明确拒绝执行时排队恢复。预扣失败不延期扣款；网络中断、提交回包不明不猜测重扣。回放只补 DB，不重复调整缓存。
- 已完成请求的资金补记可更新尚保留的软删除用户/令牌行。渠道被管理员硬删除时，其无处写入的历史计数告警后跳过，不让这一项统计更新回滚同批有效的钱包/令牌补记；不会重建或启用已删除渠道。此边界已在真实 MySQL、PostgreSQL 与 SQLite 文件中验证。
- 日志兜底使用版本 2 的 `relay_log_pending_accounting` 保留 Accounting；`QuotaData` 与渠道每日上游限额仍在原后台续处理执行一次，财务恢复不重复执行这两项。
- 日志回放只在启动回放时封存活动文件，普通状态查询不轮换文件。原重试 worker 每 30 秒尝试恢复，手动回放仍可使用；版本 1 的历史记录不会被当作新待记账任务。
- 版本 2 回放先按已有 request_id 索引和请求身份找回已提交日志，再依据已有财务 log_id 唯一约束/清理回执防重。财务续处理返回不等于提交成功，必须检查成本记录已经提交，否则保留文件。

验证环境为独立测试容器中的 MySQL 8.0.46、PostgreSQL 17.11、Redis 7.4.11，运行 Linux amd64 程序、Nginx 和每秒检查一次的监控脚本。它们是真实数据库，并不是生产主机版本或硬件的已确认副本。补齐删除目标边界后的测试候选 SHA256 为 `125278c4de4d3211c8a376807925e444105a0b99d7b9bddea8211e9b29e45bc1`；此前候选和阶段证据另外保留。

### 仍不能据此签署生产验收

- 最低 100000 成功 AI 请求 RPM 的容量门槛未通过；本轮没有把少量功能请求、chunk 或内部重试当成容量证明。
- 没有实际生产硬件、精确版本或生产旧库 schema，未完成该旧 schema 的升级演练。既有启动/索引问题仍应按测试基线核验。
- 首次保存前的内存增量被 kill -9 仍有丢失窗口；磁盘满且兜底无法保存时，保留原最后续处理，可能产生没有日志关联的成本，不能宣称所有故障均已杜绝。
- 原始同步写提交结果不明、历史 NULL log_id 成本没有可靠映射时均需人工核对，不自动补扣或猜测关联。延迟财务处理沿用处理时的成本/佣金配置，不新增不可变费率快照。
- 本轮只确认测试过的真实渠道和场景；GPT/Gemini 所选渠道未通过，不能对外宣称全部厂商功能验收成功。
- 验证期间工作区其他缓存/定价实现及测试文件也发生过内容变化；按二进制 SHA 与各阶段源文件清单界定证据。未覆盖其他修改，不把已测候选的通过结果自动扩展到持续变化的整个工作区。
