# 慢客户端补测：内存、写入超时与资源回收

日期：2026-10-21。用户要求补测慢读、停止读取和中途断开。本轮只添加测试和记录，没有修改生产缓冲、写入期限、计费或诊断逻辑，也未部署。

## 方法与边界

测试 `relay/channel/claude/slow_client_load_test.go` 使用真实 TCP：本地 mock 上游 → 现有流式处理器 → 本地 HTTP 客户端。每组一半 Claude 原生、一半 OpenAI 转换；普通帧文本为 16 KiB，大帧用例为 256 KiB；每请求总文本 2 MiB，最后返回合法 refusal 和用量。上游、处理器和客户端同处一个测试进程，因此以下内存值包含三者，不能当作独立生产网关的内存预算。

客户端每次最多读取 4 KiB，慢读每次暂停 20 ms，名义上限约 200 KiB/s。停止读取用例取得响应头后保持 TCP 打开，完全不读取正文；断开用例读取至少 64 KiB，停顿 250 ms 后关闭响应体。快速对照不延迟读取。

测试监听器对 TCP 发送缓冲请求设置 4 KiB，客户端对接收缓冲请求设置 4 KiB，以确保回复不能全部提前进入内核缓冲。具体内核实际分配由 Windows 决定。生产的 30 秒写入期限保持原样，通过透明 writer 记录真实网络 timeout，未用假的错误替代阻塞。完整读取仍需保持用量和拒答诊断；纯客户端失败不能冒充上游异常诊断。

测试期间每 100 ms 采样 Go HeapAlloc、HeapInuse、StackInuse、goroutine、活跃处理器和上游数量；外部 Python/psutil 每 100 ms 采样测试进程工作集和 private bytes。峰值为采样峰值，不保证捕获瞬时最高点。退出后关闭连接，检查上下游活动请求归零、协程回落，再执行 GC 采样；没有调用 `debug.FreeOSMemory` 强制向操作系统归还内存。

环境与首次压测相同：Windows 11，Ryzen 7 8700G（8 核/16 线程），约 47.1 GiB 内存，Go 1.25.1。无真实 AI 请求、数据库或账单写入。实际网络为 HTTP/1.1 明文 loopback，没有模拟 TLS、HTTP/2、反向代理缓冲、200 MiB 极限帧或小时级长连接。

## 结果

7 组共 **416 个请求**全部通过，总测试时间约 73.62 秒。正常完成 288 个，预期客户端失败 128 个（64 个写入超时、64 个主动断开），没有非预期失败。每个用例均验证上游保留正文不超过 2048 字节、下游 base64 不超过 2732 字节，以及连接和工作者退出。

| 场景 | 并发 | 测试总时长（秒） | 采样 Go 堆峰值（MiB） | 结束并 GC 后堆（MiB） | 结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| 快速读取对照 | 64 | 0.68 | 170.84 | 6.85 | 全部完成 |
| 限速读取 | 16 | 10.55 | 51.06 | 7.25 | 全部完成 |
| 限速读取 | 64 | 10.92 | 169.10 | 8.06 | 全部完成 |
| 限速读取 | 128 | 10.64 | 335.00 | 8.06 | 全部完成 |
| 读取响应头后停止 | 64 | 30.04 | 40.05 | 9.02 | 64 个均发生真实写入超时 |
| 中途断开 | 64 | 0.32 | 42.21 | 8.96 | 64 个均按客户端离开结束 |
| 256 KiB 大帧限速读取 | 16 | 10.45 | 81.06 | 8.29 | 全部完成 |

停止读取组的处理器从开始到结束中位数约 30.016 秒，最大 30.029 秒，全部触发生产写入期限。第 5、10、15、20、25 秒仍有 64 个活跃流，堆分别约 39.99、40.00、40.01、40.01、40.01 MiB；在这个停读窗口内没有观察到正文持续堆积。断开组处理器最大总时长 0.281 秒，其中包含客户端人为停顿的 250 ms，不能把这 0.281 秒当成从断开时刻开始的纯清理耗时。

各组测试结束后的 goroutine 均为 3；测试服务器启动后的基线为 5。上下游活跃请求均回到零，没有观察到结束后的处理器、上游请求或连接工作者残留。此结论针对本轮负载和观察窗口，不是对所有长流场景的无泄漏证明。

## 对内存问题的解释

**慢读主要延长占用时间，并通过增加在途请求数抬高总内存。**同为 64 并发，快速对照与慢读的堆峰值接近（约 171 与 169 MiB），但慢读约 10.9 秒才完成，快速对照约 0.68 秒完成。慢读并发从 16 增至 128，堆峰值从约 51 增至 335 MiB；不能从这些混合测试进程数字推算生产每连接固定成本。

**Go 堆回落不等于任务管理器里的内存立即回落。**128 并发慢读期间测试进程采样工作集最高约 414.91 MiB；随后停读用例开始时还沿用之前已分配的堆和地址空间，到停读用例末尾工作集约 97.74 MiB。停读用例的 GC 后 HeapAlloc 约 9.02 MiB，但 HeapSys 约 383.84 MiB，其中 HeapReleased 约 318.25 MiB。Go 运行时可以保留地址空间、空闲页、栈及池化对象供复用，工作集还包含非 Go 堆内存；单看进程占用未立即降至基线，不能判定泄漏。

固定诊断采集上限在这些慢客户端场景中仍有效；本次没有发现诊断随回复全文增长的现象。大帧仍会增加处理缓冲压力：相同 16 并发，256 KiB 帧的堆峰值约 81 MiB，高于 16 KiB 帧的 51 MiB。生产上限为 200 MiB 不意味着预分配该大小，本次也没有验证 200 MiB 大帧叠加高并发时的容量。

## 复现与证据

```powershell
$env:STREAM_SLOW_CLIENT_LOAD='1'
go test ./relay/channel/claude -run '^TestClaudeSlowClientLoad$' -v -count=1 -timeout=8m
```

单独验证生产写入超时可将 `-run` 改为 `'^TestClaudeSlowClientLoad/stopped_64$'`。未设置环境变量时这些负载测试会跳过，不给日常单元测试增加约 30 秒的真实网络等待。

本次完整运行先用 `go test -c` 构建测试二进制，再用同样的测试参数执行，以便外部采样器直接监控测试进程 PID。原始日志、带 Go 时间序列及进程内存采样的 JSON、测试二进制保存在本地 `_local/stream-slow-client-validation-20261021/`；该目录不纳入版本控制。

压力测试后执行 `go test ./relay/channel/claude ./relay/common ./relay/helper -count=1`，三个包均通过；`gofmt`、`git diff --check` 和新增文件 UTF-8 检查通过。数据库整链路、长期稳定性和 race 检测的未覆盖项仍按[前次验证报告](stream-diagnostics-validation-20261021.md)记录。
