# 大规模混合日志导出：扫描窗口与超时恢复

日期：2026-11-24。状态：已按用户确认的方案实现；完整索引及缺少后续两个复合索引的 PostgreSQL 大表验收、全部筛选字段矩阵及相关回归通过。完全无可用索引的容量边界实测仍超时，详见补测结果。数据与证据已保留，尚未部署线上。

后续性能修正见 [分页与额外退让](usage-log-export-speed.md)：在本次超时恢复之上收紧分页 SQL 起点，并校正查询压力反馈。下文验收记录对应超时恢复阶段，后续修复的速度及回归结果单独记录。

## Goals and scope

修复使用日志导出在选择性很高的条件下，因自动扩大扫描窗口而触发单批超时、整项任务失败的问题。保留用户选定的时间范围、筛选语义和数据精度。

本轮用户明确要求：本地测试；每天 600 万条、30 天共 1.8 亿条混合日志；覆盖各种导出条件；测试库保留用于修复后回归；**不增加索引**。不访问或部署生产环境。

用户于本轮再次确认，线上本次导出使用 PostgreSQL。因此以 PostgreSQL 的真实大表、条件矩阵及超时恢复为主验收，MySQL 仅作项目兼容性补充，不替代 PostgreSQL 的结果。

用户随后补充：启用“logs 表缺少索引”启动警告之后，后续新增索引均未手工维护；具体缺失列表未知。此前完整 17 个索引的测试结果不能直接代表该生产结构。历史结构补测和完全无可用索引的容量边界需分别记录，不能把缩小时间窗口解释为可消除任意全表扫描。

## Existing Logic and Related-Path Findings

- `controller/log_export.go`：管理员创建任务接受用户名、类型、模型、令牌、渠道、分组、时间及数值/异常条件；`buildLogExportFilter` 保留指针字段的显式零值。自助及员工导出另行固定用户范围。
- `model/log_export_scan.go`：SQL 层应用类型、文本及数值条件，使用时间闭区间和 `(created_at,id)` 正序游标；ClickHouse 使用 `(created_at,request_id)`。JSON 异常条件在读取后由 `matchesRow` 判断。
- `model/log_export_scanner.go`：明细、汇总、原始日志、额度数据及审计数据共用 `runBatches`。额度正序，审计倒序，员工按授权客户依次扫描；重试不能绕过这些校验。
- 修复前的 `model/log_export_job.go:nextLogExportWindowSec` 仅按 SQL 返回行数判断密度。不到一批就扩大一倍，直至 24 小时。原来的 `window_sec=3600` 实际是起始值与下限，并非最大窗口。
- 修复前的 `runBatches` 在任何查询错误后立即退出。查询返回的部分结果尚未进入回调，失败后无需撤销已写数据；但恢复时必须丢弃失败批次并保持最后成功游标。
- `runLogExport` 的总超时包含资源等待；失败删除部分文件并将最终行数置零。汇总在完整扫描后才写文件。因此截图的零行不代表没有符合条件的数据。
- `service/auditexport/source.go` 的 `Read` 与额度 reader 均通过 `LogExportBatch.Position/Cursor` 表达扫描位置。审计候选行可能被进一步过滤，不能从最终输出行推算游标。
- `model/log_export_throttle.go` 已有 CPU/低峰闸门、按返回行数限速及查询耗时退让；继续复用，不增加并行查询。
- 旧设计 `usage-log-export-throttle-accounting.md` 将“匹配结果少”视为“底层数据稀疏”，在大量混合日志上不成立；其中“行限速限制数据库真实扫描压力”的描述也不成立，行限速只计返回行。
- `model/log_migrate.go:migrateLogTable` 对已有 `logs` 表只提示缺少索引并返回，不自动创建索引；`model/main.go` 的主库及独立日志库都使用这一入口。新建表另走创建逻辑，不能用新建测试库的完整索引推定旧生产表的结构。
- 用 `git blame` 和 `git show` 核对，警告策略首次出现在 `8410b980f8`；该版本已经声明 `(created_at,id)`、`(created_at,type)` 等时间索引。相对该版本，当前 `Log` 新增的是 `idx_log_export_user_time(user_id,created_at,id)` 与 `idx_cleanup_created_id(type,created_at,id)`。据此构造缺少这两个索引的历史结构副本；这是代码历史推导，不是生产索引清单。

## Key business logic and edge cases

### 1. 窗口调整同时看查询耗时

每个窗口记录最慢一次读取的耗时，不计写文件、限速和 CPU 等待。只有“返回不足一批”且查询耗时不超过 `min(1 秒, 单批超时/4)` 才允许翻倍；达到单批时限的一半则优先减半，最低 60 秒。多批密集窗口仍沿用现有收缩逻辑；普通密度收缩不主动低于配置值，因延迟缩小的窗口可保持更小。

### 2. 单批读取超时缩小未读区间后恢复

- 先区分父任务已取消/总超时、权限校验失败、普通 SQL 错误及本次读取超时。仅最后一种进入恢复；权限校验超时不能靠缩小日志窗口重试。
- 保持最后成功的游标和已写文件/汇总，不处理失败查询返回的部分结果，不计入 scanned_rows。
- 正序从最后成功的扫描秒（或窗口起点）到当前窗口末尾计算未读范围；倒序镜像处理。范围减半，最小 60 秒，保留该秒的游标次键，避免同秒多行丢失或重复。
- 实际查询窗口已经不超过 60 秒仍失败时停止。若宽查询在成功游标后只剩不足 60 秒，先收紧至这段自然尾段再尝试一次，不扩大到已完成区间或原窗口之外。后续正常窗口仍以 60 秒为下限。收缩必须严格减少查询范围，不能无限重试。
- 缩窗后限制本次扫描后续窗口的最大宽度，避免读完小窗口立刻再次扩回已失败的大窗口。员工下一客户使用独立扫描状态。
- 失败尝试仍计入总耗时，执行现有退让闸门；每次重试再次检查取消、CPU/低峰条件及适用权限。
- 成功完成子窗口后从其边界 ±1 秒继续；终段不足 60 秒本来就无需补足。空批次仍须推进范围。

### 3. 生命周期及错误处理

取消和总时限优先，不延长任务寿命。文件写入/磁盘不足、权限撤销、审计风险版本变更、重算错误均不重试。恢复日志只记录任务 ID、窗口和尝试耗时，不记录用户数据或凭据。终态错误沿用现有脱敏处理。

## Main Chain Impact
