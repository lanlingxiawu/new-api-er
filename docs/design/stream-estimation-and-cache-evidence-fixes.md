# 流式分片估算、缓存证据与 Realtime 输出修复

## 已确认目标与范围

按本轮审计推荐修复三项：分片逐次取整导致异常估算偏高；供应商缓存字段在异常确认用量中丢失；Realtime 有输入估算时覆盖已交付文本输出。仅调整新增受管流式流程，非流式、开关关闭、HTTP 非 200、未收到响应继续原流程。既有六行异常结算矩阵、资金预留/退款及诊断权限保持。

## 数据流与业务逻辑

1. 成功写出并刷新后提取已交付文本，使用请求尝试局部的增量估算器：保存词类和未取整权重，每批返回累计取整值的增量。同一文本按任意完整字符边界分片，最终与一次估算一致；不保存完整回答。首次交付时读取映射后的模型，每次渠道尝试重建估算器。
2. 上游原始 JSON 观察阶段按本次选中渠道识别已有兼容缓存别名：DeepSeek 的 prompt_cache_hit_tokens；Moonshot 的 choices[].usage.cached_tokens；Moonshot/智谱 v4 的 usage.cached_tokens、prompt_cache_hit_tokens；OpenAI/llama.cpp 的 timings.cache_n。标准缓存字段优先且显式零有效；重复累计报告覆盖而非求和。别名与同帧其他证据一起校验后原子提交，异常结算仍只采用确认字段，不从旧适配器混入估算。私有 usage_evidence.cached_tokens 保存归一化值，原字段位置保留在现有原始响应中。
3. Realtime 每轮独立增量估算已交付文本，结束选择估算用量时分别构建输入、文本输出和音频输出，移除旧 local 总量覆盖。文本和工具参数只采用交付观察器结果，不再另加旧逐 delta 文本计数；音频维持原音频算法，兼容 output_audio 事件名。转写属于既有文本估算口径，仅记录一次，不与旧文本估算重复累加；不推断或改动供应商的音频/转写定价。确认用量（包括显式零）始终优先，客户端无确认用量继续零结算。每轮结束重置文本估算器，已完成轮次账本不变。

## API、存储、配置与错误处理

不新增端点、表、索引、配置、依赖或对外字段。沿用 stream_error_setting、实际成功响应门控与 RootAuth 诊断接口；不采集请求。别名数值须为 0 至 10 亿的整数，非法证据复用 upstream_json_error；不影响原生上游 error 的转发规则。费用仍由既有统一结算执行一次。

## Main Chain Impact

同步：已交付字符一次线性扫描、固定数量 JSON 字段查询、每轮内存用量合并。估算状态只保留固定大小计数，不延迟发送，不等待后续帧，无网络/DB 调用。异步：仍使用既有日志和统计队列，未新增任务。

## Shared Resource Audit

仅使用尝试/轮次局部估算器、原会话短锁和既有模型权重只读快照。权重表与旧估算共用，但每个估算器仅首次初始化读取一次，不更改全局配置。新增 Redis、DB、连接池、文件句柄、工作池及跨请求锁为 0；资金会话调用次数不变。

## Concurrency Analysis

30k/100k RPM 下新增 DB/Redis 调用与 goroutine 均为 0。估算时间 O(交付字符数)、状态 O(1)，不存在重扫完整输出的平方复杂度；缓存候选遍历受已有 8 MiB 帧上限约束。记录本地验证，不用单机微基准代替生产负载结果。

## 实施步骤、验证与风险

先加入失败回归，再实现并补中文方法/参数注释：
- SSE 同一文本整体/逐字符/不同刷新批次，模型映射延后、重试清零、无有效交付不收费。
- 各渠道缓存别名、标准字段优先、显式零、重复累计、非法值原子性；验证最终确认用量保留缓存及透传开关不改变路径。
- Realtime 有/无输入、有/无音频、确认正数/零、异常/客户端取消、分片和多轮隔离；本地 WS 夹具验证实际写出与错误补发。
- relay 全包及相关测试、选定 DB 无关 service/model/controller/middleware 测试、根构建、格式和差异检查。

风险：估算仍是近似算法，不等于官方 tokenizer；仅消除分片方式带来的系统性差异。缓存别名按既有渠道白名单，不把其他渠道同名业务字段当作费用证据。不修改旧非流式估算器或音频时长算法。
