# 流式诊断标记与拒绝原因展示

用户于 2026-09-13 确认实施；本方案替代既有文档中把策略原因纳入 Root 私有展示的约定。

## 目标与范围

`reject_reason` 恢复到 `bb6317462`：非空上下文原因写入 `logs.other.reject_reason`，日志详情直接向管理员展示。普通用户接口保留该字段、前端不展示，与指定版本一致。原始响应、底层错误、用量证据仍仅 Root 查询。

公开标记更名为 `stream_diagnostic_available`，只表示已确认的新流式流程上游异常。按钮要求布尔 true 和 Root 身份，不依据响应采集、旧标记、拒绝原因、结算失败或泛化的 error 状态推断。

## 数据流与业务边界

每次尝试创建独立诊断状态 → 上游传输边界记录实际交换结果，协议读取记录明确错误来源 → 终止时固定诊断资格 → 日志生成写公开标记与原私有 envelope → 普通查询剥离 envelope、保留独立原因和新标记 → Root 按需查询原诊断接口。

按 2026-09-13 [成功响应门控](stream-success-response-gate.md)，只纳入真实 HTTP 200 / WS 成功 101 后的 EOF 不完整、响应 JSON/协议错误、上游错误事件、读取失败及受管上游超时。HTTP 非 200、未收到响应的连接失败或响应头前超时不生成诊断字段；正常完成、仅下游取消/写失败、本地转换/预扣/结算错误、非流式和开关关闭不生成诊断标记。首个明确上游异常不被后续下游关闭覆盖；SDK 内部失败后成功的交换不污染正常终态；渠道重试不继承前次标记。成功响应之后，即使 body 为空或响应采集关闭，明确上游异常仍有诊断资格。

通用流式、请求体透传、Claude 专用解析和 Realtime 均覆盖。来源记录只影响日志资格，不改变现有终止原因、错误补发或费用选择。

## API contracts 与存储

无新接口。使用日志 `other.stream_diagnostic_available?: boolean` 仅在有资格时写 true。使用 `stream_diagnostic` 存储、`stream_diagnostic_attempt` 定位及 `stream_result` 结算摘要（旧字段仅读取兼容）及 RootAuth GET `/api/log/claude-diagnostic` 的 request_id/created_at/attempt 合同；success/data、no-store、超时及权限不变。

日志读取钩子不再合成可用标记。旧标记移除，不转成新标记，不批量迁移历史数据。历史嵌套原因只投影字符串 reject_reason，顶层已有值优先；其余证据仍剥离。普通用户字段过滤按指定提交恢复，不把整个诊断对象暴露给用户。旧日志无新标记时不显示按钮，原因仍独立展示。

下游实际正文采集与通用命名的后续扩展见 [下游正文方案](stream-diagnostic-body.md)。无新表、列、索引或配置；复用已冻结的 stream_error_setting 开关与既有查询索引。响应采集范围、计费、预扣、退款均不变。

## 实施结果与审计

- 已恢复独立原因：写日志时保存上下文原因，普通读取只投影历史嵌套字符串原因，前端使用 bb6317462 原 DetailSection；普通用户接口保留原因但前端隐藏。
- 通用会话首因与诊断资格分离；控制器未知错误保留原终止/计费标签但不误标上游。采集关闭仍分配独立尝试编号和无 body 错误诊断。
- HTTP/SDK/WS 在真实交换处记录来源；SDK 内部后续成功清除暂时传输失败。补充 SDK 响应解码及 Nova 缺失内容来源，避免它们落入未分类本地错误。Realtime 轮次之间的异常关闭、Claude 专用循环和透传均纳入。
- 本地转换 panic、请求编码错误、结算预留错误与客户端关闭不生成上游资格。已确认上游失败不被下游后续关闭覆盖。
- 本阶段不改计费矩阵、预扣/退款资金操作和原错误事件；后续通用命名、下游正文及翻译扩展见 `stream-diagnostic-body.md`。
