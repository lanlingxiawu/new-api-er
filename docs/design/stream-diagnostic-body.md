# 通用流式诊断命名与下游响应正文

2026-09-13 用户确认实施。本文补充并优先于既有诊断文档中仅采集上游响应的说明。

同日新增 [成功响应门控](stream-success-response-gate.md)：响应采集器只在真实 HTTP 200 / 成功 WS 101 后工作；非 200 或未收到响应时，上下游正文均不采集，不保存新诊断字段，不显示按钮。

同日用户再次确认：新流程中的上游原始响应也只在明确上游异常时保存。以下“异常响应保存规则”优先于前期正常请求也保存上游快照的实现；既有历史日志和非流式原流程不变。

## 异常响应保存规则

- 目标：新流程正常完成、仅客户端断开、本地错误或尚未确定上游异常时，不把上游响应头和 body 写入日志；明确上游异常且采集开启时才保存，和下游正文、诊断按钮使用同一异常资格。
- 数据流：保持真实成功响应后的有界内存采集，在消费日志和错误日志序列化/入队前，分别使用已固定的 `StreamResult.DiagnosticAvailable` 或会话的 `DiagnosticAvailable` 过滤日志副本。过滤涵盖最后一次响应与 SDK `previous_responses`，不修改采集器、已固定结果或已入队快照，避免影响后续 Realtime 轮次和终止错误补发。
- 仅过滤原始响应内容：响应头、body 首尾和下游正文；状态码、读取状态/错误、用量证据、结算摘要、尝试编号和独立 `reject_reason` 保持原逻辑。无原始响应的字段可以为 null，表示没有保存内容，而非零字节响应。SDK 历史条目的读取元数据仍保留，但不携带头或 body。
- 成功响应门控之前的 HTTP 非 200、连接失败仍由原流程处理；新流程由每次尝试的非空 `StreamResponseGate` 识别，不更改未安装该门控的旧采集路径。采集关闭时即便有上游异常，也只保留现有无 body 诊断。先发生明确上游异常、再下游断开仍按已有资格保存。
- API、Root 权限、前端按钮及 JSON 字段结构不变；无新增配置、表、列、索引或数据迁移。沿用冻结的 `stream_error_setting` 开关，不清理历史日志，不改普通请求日志、错误分类、补发、收费、退款和渠道重试。
- 实施顺序：先补充双日志入口与序列化回归，再加入共享的响应内容过滤逻辑，最后运行协议/透传/SDK/Realtime、权限和结算回归，并审计全部私有诊断写入点。
- 验证：正常、取消、本地错误、未终止、EOF 不完整、读取/JSON/协议错误、上游 error、采集关闭、非流式和成功响应门控；检查 SDK 历史响应无遗漏、原内存快照不变、上游异常后能保存此前的响应和追加的下游 error。

## 目标与范围

新日志改用 `stream_diagnostic_attempt`、`stream_result`、`stream_diagnostic`；`stream_diagnostic_available` 资格不变。通用类型、上下文键、日志方法和前端组件去除 Claude 命名；Claude 协议解析和配置兼容项保持原名。

下游只新增 `stream_diagnostic.downstream_body_base64` 一个字段，不增加计数、写入/刷新错误或下游头等字段。不采集请求头、请求 body。非流式、费用选择和转发协议不变。

## 数据流与边界

每次尝试冻结既有开关 → 开启响应采集时安装位于 StreamWriter 之下的有界写出观察器 → 原 writer 返回后只复制其接受的 `p[:n]`（部分写入也保留）→ 补发终止错误沿同一边界写出 → 入日志队列前取最新下游快照。StreamWriter 尚未提交的帧及被过滤的成功结束帧不纳入。WebSocket 在成功的下游 WriteMessage 后记录原载荷，包含终止错误，连接内各轮共用采集器，不采集上行载荷或 WS 帧头。

仅新流程确认上游异常且响应采集开启时持久化下游字段。正常完成、仅客户端断开、非流式均不新增该字段。缺失表示未采集/历史日志，空字符串表示已采集但零字节写出。

最多保存 2048 字节：未超限保存全文，超限拼接前后各 1024 字节，再整体 base64。为满足单字段和实际字节要求，不插入伪造的省略标记；UI 固定说明超过 2 KiB 时省略中间，满 2048 字节时不能区分恰好 2 KiB 与截断，不声称它是完整正文。Write 成功仅代表服务端 writer 接受，不代表客户端应用已消费；Flush 失败不抹除已接受的字节，也不改变有效交付/计费规则。

## API contracts 与数据模型

RootAuth GET `/api/log/claude-diagnostic` URL、请求参数、success/data、no-store 和查询超时不变。诊断增加可选 base64 字符串，其余私有字段保持含义。

新写入只用新键；读取旧日志时投影旧摘要和尝试编号至新键，新键存在时优先。Root 查询兼容两个 envelope，新者优先；普通读取同时剥离两者。若同秒同尝试既有早期渠道错误日志又有终止结算日志，优先返回含 `stream_result` 的终止快照，避免命中补发前的空正文。没有终止快照时仍返回原尝试证据。`reject_reason` 保持 bb6317462 的独立展示规则，不从旧标记合成资格。无历史数据批量迁移，无新表、列、索引或查询。

## 配置、错误处理与子系统交互

沿用 `stream_error_setting.enabled/capture_response` 冻结值和原 Claude 配置兼容，无新增配置。观察器不主动读取/刷新/关闭连接，不修改 Write 返回值，诊断不参与额度结算。每次渠道尝试移除旧包装器并重建缓冲，避免重试串数据；SDK 内部交换共享当前尝试下游正文。

## Main Chain Impact

同步仅在底层 Write 返回后复制有界首尾字节、短锁保存，入队前编码不超过 2 KiB；不持锁执行网络 I/O。持久化沿用既有异步日志队列。无新增网络、数据库、Redis 调用或每请求 goroutine。

异常响应保存收紧只在日志生成时同步过滤值副本；SDK 历史最多复制三份响应元数据，不复制正文，不修改共享底层数组。没有新增锁或等待，失败不会新增任何中转响应分支。

## Shared Resource Audit

复用 logs.other 与原日志队列；不访问资金表，不创建 Redis key、全局 map、连接池或工作池。新增缓冲属于当前尝试，与共享连接池/其他请求隔离；同请求 WS 与 HTTP 观察使用采集器短锁，无跨 I/O 持锁。

## Concurrency Analysis

30k/100k RPM（约 500/1667 请求每秒）新增 DB/Redis 调用及 goroutine 均为 0。采集开启后首次实际写出才分配约 2 KiB 缓冲，终止编码约 2.7 KiB，仅异常时入库；按长连接并发核算内存。非流式、零写出不分配正文缓冲，普通流不做下游 base64 快照。没有新索引访问或大表扫描；容量验证需覆盖慢客户端、长流、错误风暴。

新增过滤对每份日志做常数次字段清空，SDK 历史最多三条；不增加采集内存上限、连接池/工作池占用或 logs 写入次数。与主链共享的仍仅是原 logs.other 和既有异步日志队列；普通流日志不再序列化原始上游头/body，降低队列字节负载。30k/100k RPM 的实际压测另行进行。

## 实施结果与审计

- 完成通用 Go 类型/方法/上下文键、JSON 字段和前端组件命名更新；旧 JSON 只在读取与历史兼容夹具中保留。Claude 专用协议/设置及 Root API URL 保持兼容。

- 首次实际写出才创建 2 KiB 有界缓冲；仅有确认上游异常的诊断写入一个 `downstream_body_base64`，普通完成、仅客户端错误、关闭采集及非流式均不新增该字段。普通日志同时过滤两种私有 envelope。
