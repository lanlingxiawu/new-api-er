# 真伪检测结果统计

## 目标和范围

在“真伪检测 > 检测记录”页增加结果统计区，让管理员无需逐行浏览即可看到当前查询范围内的记录总数及各结果类别数量。

统计必须基于数据库中的完整匹配集合，不能只统计前端当前加载的最多 100 条记录。统计与渠道、模型、批次、模式和更新时间筛选联动；“结果”筛选只负责筛选下方列表，不参与各类别分布统计，避免选择某一结果后其它类别全部显示为 0。

本次范围包括：

- 服务端返回完整匹配集合的结果分类统计；
- 前端展示总计、检测中、通过、基本合格、未达标、失败、已跳过和已取消；
- 用服务端精确数量替换当前基于 `results.length` 的“匹配结果”数量；
- 统计区随现有自动刷新和筛选变化更新；
- 七种前端语言同步。

本次不修改检测评分规则、任务调度、检测结果写入、报告内容、渠道状态或 AI 转发链路。

## 交互设计

统计区位于筛选栏下方、结果表格上方，复用当前页面的紧凑布局、Badge、边框和语义色，不新增独立大卡片或额外弹窗。

统计项按以下顺序展示：

1. 总计
2. 检测中
3. 通过
4. 基本合格
5. 未达标
6. 失败
7. 已跳过
8. 已取消

窄屏时允许自然换行。数量使用等宽数字样式；类别颜色复用结果表格现有状态颜色，不能硬编码新的颜色值。

统计项同时作为结果类别的快捷筛选入口，并与现有“结果”多选下拉框共用同一个筛选状态，不引入第二套状态：

- 点击“总计”清空结果类别筛选，但不重置渠道、模型、批次、模式和更新时间等其它条件；
- 点击某个结果类别时切换该类别的选中状态，可连续点击叠加多个类别；
- 再次点击已选类别时取消该类别；取消最后一个类别后等价于选择“全部”；
- 通过统计项或下拉框修改筛选后，两处选中状态立即同步，查询参数、缓存键和列表刷新行为完全一致；
- 计数为 0 的类别仍可点击，语义与下拉框中的对应选项一致；
- 统计项使用原生按钮语义和 `aria-pressed` 表达选中状态，并复用项目现有焦点环、语义色和键盘操作样式。

加载时保留区域高度并显示现有加载样式，骨架状态不可点击；统计请求失败时由结果查询统一展示可重试错误，不显示伪造的 0。

### 筛选过程的页面稳定性

首次进入页面且没有任何缓存数据时继续显示统计和表格骨架。已有结果后，无论通过统计项、结果下拉框或其它筛选控件修改条件，查询切换期间都保留上一份完整响应，不能把统计项和表格替换成骨架或空状态，避免整块内容高度变化造成页面闪烁。

实现使用项目现有 TanStack Query `keepPreviousData` 占位策略，与价格巡检页面保持一致。筛选控件立即显示新状态，旧结果仅在新请求进行期间短暂保留；请求成功后统计、精确匹配数量和表格一次性切换到新响应。`isFetching` 继续驱动区域 `aria-busy` 和刷新按钮状态，但不能触发初始骨架。请求失败仍进入现有可重试错误状态，不长期展示旧结果冒充新筛选结果。

“显示 N 条匹配结果”中的 `N` 改为服务端返回的精确 `matching_count`，即应用包括结果类别在内的全部当前筛选后得到的记录数。表格仍最多返回 100 条，文案调整为“共 N 条匹配结果，当前显示 M 条”，避免把加载条数误认为总数。

## 数据流

1. 管理员进入检测记录页或修改筛选条件。
2. React 根据渠道、模型、批次、结果、模式和更新时间生成现有查询参数。
3. `GET /api/channel/veridrop/results` 解析并校验参数；`batch=latest` 继续先固定到明确的 `batch_task_id`。
4. Model 使用同一套基础筛选条件执行：
   - 一次结果列表查询，应用全部筛选、排序和 100 条上限；
   - 一次条件聚合查询，应用渠道、模型、批次、模式和更新时间，但不应用结果类别、分页和排序。
5. 聚合查询按后端唯一的 outcome 判定规则计算各类别数量，并由所选结果类别推导 `matching_count`；未选择结果类别时 `matching_count = summary.total`。
6. API 在现有响应中同时返回 `items`、`summary`、`matching_count`、游标和批次标识。
7. React Query 缓存完整响应；现有 8 秒轮询触发时，列表和统计一起刷新。

## API 契约

沿用现有管理员接口：

`GET /api/channel/veridrop/results`

鉴权保持不变，继续由真伪检测管理资源对应的管理员权限控制。

请求参数保持不变。响应 `data` 增加：

```json
{
  "items": [],
  "next_before_id": 0,
  "latest_batch_id": "task_xxx",
  "matching_count": 73,
  "summary": {
    "total": 73,
    "in_progress": 2,
    "passed": 18,
    "completed": 9,
    "low_score": 5,
    "failed": 34,
    "skipped": 4,
    "cancelled": 1
  }
}
```

字段含义：

- `summary`：忽略 `outcome` 筛选、应用其余当前筛选后的完整类别分布；所有类别之和必须等于 `total`。
- `matching_count`：应用包括 `outcome` 在内的全部当前筛选后的精确数量。
- 旧客户端忽略新增字段即可，接口保持向后兼容。

当 `batch=latest` 且不存在任何批次时，继续返回成功空响应，同时 `matching_count` 和全部统计字段均为 0。

## 数据模型和查询设计

不新增表、字段或迁移。新增一个只用于响应的统计结构体，字段对应七个 outcome 和总数。

聚合 SQL 使用跨 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+ 兼容的 `COUNT(*)` 与 `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`，不使用数据库专有函数。分类条件必须与 `ClassifyChannelVeridropDetectionOutcome` 和列表 outcome 筛选完全一致：

- `in_progress`：`queued` 或 `running`；
- `passed`：`done` 且 verdict 为 `passed`、`pass` 或 `success`；
- `completed`：不属于其它类别的完成记录，包括 `marginal` 且分数不低于 50，以及兼容历史数据的普通 `done`；
- `low_score`：`done`、verdict 为 `marginal` 且分数低于 50；
- `failed`：`error`、`timeout`，或 `done` 且 verdict 为 `failed`、`fail` 或 `error`；
- `skipped`：`skipped`；
- `cancelled`：`cancelled`。

为避免列表和统计条件漂移，渠道、模型、批次、模式、时间等公共条件由一个可复用的 Model 查询构造逻辑统一应用；结果条件只在列表查询和 `matching_count` 推导中使用。

## 索引设计和大数据约束

统计查询复用现有访问路径：

- `idx_veridrop_batch_id(batch_task_id, id)`：最新批次统计；
- `idx_veridrop_updated_id_v2(updated_at, id)`：时间范围统计；
- 现有渠道名称、模型、状态和分数索引：对应筛选和分类条件。

不新增只能覆盖单一筛选组合的宽索引，避免持续写入检测结果时增加额外索引维护成本。聚合只由管理员页面触发，单次页面刷新固定为一条列表查询和一条聚合查询；8 秒轮询仅在最新批次或存在运行中记录时启用。渠道名和模型的包含匹配可能无法完整利用普通索引，这是现有筛选行为，本次不扩大返回行数或轮询频率。

## 配置参数

不新增配置参数。统计刷新沿用检测记录现有刷新策略。

## 关键业务逻辑和边界

- 空表、无最新批次或筛选无匹配时，所有统计为 0，列表为空。
- outcome 分类互斥且穷尽当前所有状态，类别之和必须等于总计。
- `score = 50` 属于“基本合格”，`score < 50` 且 verdict 为 `marginal` 才属于“未达标”。
- `error` 和 `timeout` 统一计入“失败”；`cancelled` 单独统计，不能混入“已跳过”。
- `done` 但 verdict 为空或来自历史未知值的记录按现有分类规则计入“基本合格”，保持前后端口径一致。
- 排序、`limit` 和游标不影响统计。
- 最新批次游标继续固定到同一 `batch_task_id`，统计不会在翻页过程中切换到新批次。

## 错误处理策略

- 参数无效继续使用现有国际化“参数无效”业务错误。
- 列表查询或聚合查询任一失败，记录底层错误并返回现有可重试错误，不返回部分列表配合错误统计。
- 前端复用当前结果加载错误提示，不把缺失的统计响应当作全 0。
- 新增用户可见文案全部通过 `t(...)`，并按项目脚本写入 `en`、`zh`、`zh-TW`、`fr`、`ja`、`ru`、`vi`。

## 与现有子系统的关系

- 检测任务：只读取已写入结果，不改变任务执行。
- 清理任务：清理完成后现有查询失效机制会重新加载列表和统计。
- 下载报告：仍只导出当前已加载的明细，不把统计区混入 HTML 报告。
- 渠道：不读取密钥、不修改渠道状态。
- 配置、计费、Redis：不新增访问。

## Main Chain Impact

AI relay 请求协程不执行任何新增代码。统计只在管理员主动打开检测记录页或页面轮询时执行；每个 relay 请求新增 DB、Redis、锁和 goroutine 成本均为 0。

## Shared Resource Audit

- `channel_veridrop_detections`：检测后台任务写入，管理员页面读取；AI relay 主链不访问。新增一条有界频率的聚合读取，不增加写锁或事务。
- 数据库连接池：每次检测记录刷新由一条列表查询增加为一条列表查询加一条聚合查询；不创建独立连接池，不持有跨查询事务。
- React Query 缓存：复用现有检测结果查询键和刷新周期；与 relay 无共享内存或缓存命名空间。
- Redis、文件句柄、goroutine 池：无新增使用。

## 测试设计

实施前先补充能够暴露缺口的测试：

1. Model 边界值：`49.9` 计入未达标，`50` 计入基本合格；空 verdict 的 `done` 记录计入基本合格。
2. Model 等价类：queued/running、passed 别名、marginal、failed 别名、error/timeout、skipped、cancelled 各至少一条，验证类别互斥且总和一致。
3. Model 组合筛选：渠道、模型、最新批次、模式和更新时间同时作用于列表与统计；outcome 只限制列表和 `matching_count`，不改变 `summary` 分布。
4. Model 空数据与无匹配：所有字段为 0，不产生 NULL 扫描问题。
5. Controller 正常响应：新增字段结构和数值正确，旧字段保持不变。
6. Controller 错误路径：聚合失败时返回统一可重试错误，不泄露数据库错误。
7. 前端静态验证：TypeScript 类型、oxlint、七语言 i18n 同步和生产构建通过。
8. 手工交互：依次验证点击单个统计类别、叠加多个类别、取消部分和全部类别、点击“总计”清空结果筛选，以及从下拉框反向修改筛选；两处状态、请求参数和表格结果必须始终一致。
9. 手工可访问性：统计项可通过 Tab 聚焦并用 Enter、Space 切换，`aria-pressed` 与视觉选中态一致；计数为 0 的类别仍可操作，加载骨架不可操作。
10. 布局回归：筛选、重置、最新批次、自动刷新、运行中状态和空状态下的统计均与表格一致；窄屏不溢出。
11. 防闪烁回归：首次加载仍显示骨架；已有数据后分别点击统计项、修改结果下拉框、切换其它筛选和排序，统计区与表格在请求期间保持原有高度且不切换骨架，新响应到达后一次性更新。
12. 错误回归：保留上一份响应期间若新查询失败，仍显示现有错误和重试入口，不能继续把旧数据呈现为新筛选结果。

## 实施状态

已按本设计实施：

- 检测结果接口返回完整分类统计和精确匹配数量；
- 统计复用列表基础筛选条件，但不受 outcome、排序、分页和 100 条列表上限影响；
- 修正历史普通 `done` 记录在 SQL 结果筛选中的分类，使其与后端统一 outcome 判定一致；
- 检测记录页增加八项紧凑统计，并明确区分匹配总数和当前显示数量；
- 新增文案已同步至七种前端语言。

- 统计项已改为与“结果”多选下拉框共用状态的快捷筛选按钮：类别支持切换和多选叠加，“总计”只清空结果类别筛选；两处选中状态和查询参数保持同步。
- 快捷筛选补充了原生按钮语义、`aria-pressed`、键盘焦点样式和明确的视觉选中态；不修改 API、数据模型、配置、国际化文案或 relay 主链。

- 检测结果查询已采用与价格巡检一致的 `keepPreviousData` 策略，只在首次加载时显示骨架，消除筛选与排序造成的统计区、计数和表格闪烁；未修改服务端接口和查询频率。
