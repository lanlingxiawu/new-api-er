## Goals and scope

减少分页过程中重复读取已完成范围，以及查询耗时反馈造成的不必要等待。保持导出内容、顺序、筛选、权限和任务生命周期；保留现有批查询与任务总时限、窗口恢复、CPU/低峰保护、实际行数限速和并发上限。

仅修改 `model/log_export_scan.go`、`model/log_export_scanner.go`、`model/log_export_throttle.go` 及直接相关测试。不增加索引、迁移、连接池、worker、配置项或前端功能。测试继续使用已保留的 1.8 亿混合日志及 2,400 条控制样本。

### 已确认的两个问题

1. `logExportBatchQuery` 每页仍以整个窗口起点构造 `created_at >= windowStart`，另加游标 OR 条件。在实际 PostgreSQL 计划中，游标成为 Filter：最后一页先读取并过滤已导出的 249,000 行，才返回剩余 1,000 行。
2. `exportGate.Observe` 把整个任务观察到的最小耗时当成全局基线，不区分窗口宽度、批大小、空批或客户。1 小时窗口扩为 8 小时后的正常耗时增长也会触发退让；原查询重复读取前缀造成的几毫秒到几十毫秒增长，同样会触发每批最多 800 毫秒的额外休眠。`Charge` 的实际行数限速与这个 penalty 相加，导致后者明显超过查询本身耗时。

## Data flow

现有请求/授权 → Redis 任务与并发槽位 → 后台扫描器 → 查询前 CPU/低峰检查 → 收紧到最后成功游标所在秒的 SQL → 查询耗时观察 → 现有逐行过滤、明细写入或汇总 → 按候选行和实际压力退让 → 保存进度 → 成功发布文件。

超时仍仅缩小未读区间，保存最后成功次级游标；失败查询的部分行不写出。权限变化、普通 SQL 错误、写入错误、任务取消和总超时继续按现有路径结束。

无表、列、ORM 标签、迁移、索引或驱动变化。SQL 仅增加现有下界的精确约束，使用 SQLite/MySQL/PostgreSQL 均支持的普通比较与 OR；ClickHouse 保留 `(created_at, request_id)` 次级游标。

## Key business logic and edge cases

### 1. SQL 从未读范围开始

在 `logExportBatchQuery` 内，存在游标时用 `max(windowStart, cursor.CreatedAt)` 作为时间下界。保留原闭区间上界及整个 OR 游标条件：

```text
created_at >= max(windowStart, cursor.CreatedAt)
AND created_at <= windowEnd
AND (created_at > cursor.CreatedAt
     OR (created_at = cursor.CreatedAt AND id > cursor.Id))
```

不能改成 `cursor.CreatedAt + 1`，否则同秒未读行会丢失；不能改变扫描器的逻辑窗口起点、进度或下一个窗口边界。ClickHouse 同样收紧时间下界，但次键仍是 request_id。raw 和普通投影复用这一处修正。

### 2. 仅比较同类读取的查询耗时

扫描器向闸门提供该次读取的窗口秒数、实际请求批大小、候选行数、是否读取超时及耗时。窗口秒数在执行读取前取得，不能把超时后的缩小窗口算到失败读取上。

闸门保留三个固定大小的基线槽：空批、非空未满批、满批，以 `Scanned` 而非输出/汇总行数分类。每个槽记录最近的窗口宽度、请求批大小和该组合观察到的最小成功耗时；宽度或批大小变化时建立新基线，不直接与之前不同工作量比较。无动态 map，无每行采样。

同类读取继续使用现有超过基线 2 倍增长、低于 1.2 倍衰减的规则及 8 倍基础休眠上限。进入一次新的 `runBatches` 时清除这些查询基线，避免员工上一客户影响下一客户；累计等待、未兑现休眠、已有 penalty 和 CPU/低峰状态不因此清空。

读取超时直接按现有倍率增加 penalty，不更新成功基线。父任务已结束、授权/风险校验失败及普通错误不进入读取超时恢复，不新增重试。

窗口宽度只是工作量的近似分类，不能直接测量数据库真实负荷；下一条限制用来防止短查询的相对波动放大成很长的休眠。

### 3. 查询退让与本批查询耗时相称

保留内部 penalty 的增长、衰减及最大值。在 `Charge` 计算本批**查询反馈部分**的等待时，仅采用 `min(penalty, lastQueryCost)`；CPU 软限等待单独全额保留。基础休眠、行速率时间、空批最小计费与微休眠累积保持原样。

例如一次 20 毫秒的成功读取即使触发内部 800 毫秒 penalty，本批查询反馈休眠最多 20 毫秒，而实际行速率休眠和 CPU 软限仍照常叠加。内部 800 毫秒压力状态保留，下一次较慢查询仍可承担完整退让。读取超时的查询成本很高，不会被这个上限削弱现有退让。

该规则改变了查询反馈限速语义，已由用户随本文方案明确批准；它不属于前置方案中“继续执行现有闸门”的实现细节。

## Error handling strategy

沿用已有任务错误映射与脱敏响应，不增加用户文案。取消在查询、休眠和写入期间仍有效；查询失败不推进游标。输出文件先完整结束再发布；错误仍清理本次未完成输出，不能为保留测试数据而改变生产任务失败清理语义。测试夹具、历史报告和成功输出由本地脚本保留。

## Concurrency Analysis

每个 AI 请求新增 DB 调用、Redis 调用、锁、goroutine 均为零，100k RPM 下不引入额外每请求工作。每个导出仍串行读取一批，最多占用一个正在执行该读取的连接；不会通过并行查询获取速度收益。
