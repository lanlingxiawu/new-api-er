# 价格巡检：上游分组倍率与成本系数核对 + 模型改价便捷化

> 状态：**已实现**（2026-09-28）。本文描述实现后的实际逻辑。

关联文档：`price-monitor-loss-detection-and-price-repair.md`（亏损判定与改价）、`price-monitor-inline-repair-floor.md`（保本下限）、`channel-upstream-log-query.md`（上游日志查询）、`channel-limit-upstream-basis-and-timed-recovery.md`（"上游倍率即成本系数"）。

## 0. 已确认的口径

| # | 问题 | 结论 |
|---|---|---|
| D1 | 上游分组倍率从哪里取 | 官方 new-api（main 分支）接口为主（§3.1），上游日志补充（§3.2） |

## 1. 目标与范围

### 1.1 问题

**成本系数没有核对。** 成本系数 `ChannelCostConfig.cost_ratio`（`model/employee.go`）决定成本账（`成本 = 平台价 × 成本系数`，`service/employee_commission.go` `calcCostQuota`），也用于渠道每日限额的上游口径，本意就是"上游对我们的实际倍率"，但全靠人工填写。巡检抓上游 `/api/pricing` 是匿名请求，拿不到我们密钥所在的分组与倍率；亏损判定的"实测成本"只看上游列表价，不含上游分组倍率——上游把给我们的倍率从 0.8 调到 1.2，巡检不会发现。

**模型改价不方便。** 改价入口原先只在"亏损风险"视图里、只对"实测亏损"的行开放；弹窗只有"最高价（原始渠道价）"和"手动"，有分组折扣时按最高价改会被后端保本下限拒绝；改完这一行要等下一轮巡检才能看到结果；阶梯价的行只有一句"请在模型定价中修改"。

### 1.2 目标

| # | 目标 |
|---|---|
| G1 | 每轮巡检为每个渠道取得上游分组与上游分组倍率，并标明来源（官方接口 / 日志 / 取不到的原因） |
| G2 | 核对成本系数 vs 上游分组倍率：一致 / 偏低 / 偏高 / 无法核对 / 免费分组，可在巡检页一键采用上游倍率或手动修改 |
| G3 | 亏损判定的"实测成本"与保本下限乘上上游分组倍率 |
| G4 | 巡检页任意视图、任意按量/按次计价的行都能直接改价，可选参考价，支持批量，改完立即重算 |

### 1.3 范围外

- 不自动改价、不自动改成本系数；所有写操作由管理员显式触发。
- OpenRouter 渠道不取上游分组倍率（标"该渠道类型不支持"）；非 new-api 上游的接口会 404，标"上游不是 new-api"。
- 阶梯表达式（`billing_expr`）不支持行内改价，只提供跳转到模型定价页并定位到该模型。
- 用户专属倍率的缺口沿用原设计。

## 2. 数据流

```text
[巡检任务 · master 节点 · 后台 goroutine，不在 relay 链路]
  抓取平台/官方/渠道价格（不变）→ 构建矩阵
  → assignPriceMonitorHeaderChannelIds（渠道表头带上渠道 ID）
  → resolvePriceMonitorUpstreamRatios（G1，与取价是否成功无关）
  → applyPriceMonitorChannelCostStatus（G2，用当前成本系数）
  → 亏损判定与改价数据（G3、G4）
  → 保存 snapshot.json（ChannelCosts、表头 channel_id、统计 cost_ratio_mismatch）

[管理员改价 / 改成本系数]
  → 写入（复用现有写入路径）
  → refreshPriceMonitorSnapshotInPlace：用当前定价与快照里已存的来源价格重算整份快照，
    不发上游请求；只在主节点执行
  → 响应 refreshed，页面重新查询
```

## 3. 上游分组倍率的获取（`controller/price_monitor_channel_cost.go`）

### 3.1 官方接口（主）

渠道同时配置了上游账号访问令牌与用户 ID（渠道设置 `account_balance_token` / `account_balance_user_id`，与余额查询的判断一致）时使用。地址取 `account_balance_url`，没填用渠道地址；请求头 `Authorization: Bearer <访问令牌>`、`New-Api-User: <用户 ID>`。

每个上游账号（地址 + 用户 ID + 访问令牌）在一轮巡检里只取一次数据，账号下的渠道共用；账号级失败（令牌被拒、限流、不是 new-api）也缓存，不对同一账号重复请求：

1. **令牌列表**：`GET /api/token/?p=N&page_size=100`（最多 10 页）。官方返回脱敏密钥（前 4 位 + 10 个 `*` + 后 4 位，同 `model.MaskTokenKey`）与完整的 `group`，按渠道密钥的脱敏形式匹配分组。
   - 2026-03 之前的官方版本在列表里返回完整密钥：列表里的密钥一律先去掉 `sk-` 再脱敏后索引（已脱敏的形式再脱敏结果不变），新旧版本都能匹配，不必逐把搜索。
   - 读全的判断：有正数 `total` 时按已读条数是否达到 `total`（上游的每页上限可能小于 100，本页不满不代表读完）；`total` 为 0 可能是上游计数失败，这时以"本页不满 100 条"为准。判断错了，后面几页的密钥会被误判为"不在账号下"。
   - 不用逐把 `/api/token/search` 做主路径：它挂 SearchRateLimit（默认每用户每分钟 10 次），同一账号下渠道一多就被限流、部分渠道永远取不到。
   - 只在脱敏形式对上多个分组，或列表超过 10 页没读全时，才用 `/api/token/search?token=<密钥去掉 sk->` 精确查（不带通配符即精确匹配）。
2. 令牌 `group` 为空表示跟随账号分组，取 `GET /api/user/self` 的 `group`（每账号一次）。
3. **分组倍率**：`GET /api/user/self/groups`（每账号一次），官方 `GetUserGroupRatio` 的结果，已含分组间特殊倍率；`auto` 的 ratio 是说明文字，不进倍率表。
4. 多密钥渠道逐把匹配未禁用的密钥（最多 5 把；与 relay 选密钥同一口径，状态表里没有记录即启用），分组不同时记下全部分组（`upstream_groups`），核对取倍率最高的一个（按最坏情况估成本）。不在账号下的密钥（已在上游删除）跳过，全部查不到才算失败；限流、接口不可用等账号级原因直接返回。
5. 分组为 `auto`（倍率不固定）、密钥不在账号下、分组不在可用分组里、401/403/429/404/其他失败：各自记原因，转日志。

每个上游请求（含读响应体）受巡检设置的"来源超时"约束，整个取倍率步骤另有 15 分钟总预算（用完时进行中的请求被取消，其结果丢弃；没轮到的与被取消的渠道都沿用上次结果、不计为已尝试，下一轮优先）；没配代理时用独立的 HTTP 客户端，不与 relay 共用连接池，配了代理沿用渠道代理。

### 3.2 上游日志（补充）

没配账号令牌、官方接口失败或分组为 auto 时，用渠道第一把未禁用的密钥查 `GET /api/log/token`（复用 `service.QueryUpstreamLogs`），取最近一条带倍率的消费日志：分组取 `group`，倍率取 `other.user_group_ratio`（≥ 0 时生效，官方默认 −1 表示无专属倍率）否则 `other.group_ratio`。

官方把该接口挂在 CriticalRateLimit（同一 IP 默认 20 分钟 20 次），因此：

- 按上游主机分组，每个主机每轮最多查 `upstream_log_queries_per_host` 次（默认 8，0 = 关闭日志补充）；
- 同一主机内按"上次尝试最早"优先（排序在并发开始前完成），配额不够的渠道标"排队中"、不计为已尝试，下一轮优先；
- 收到 429 本轮停止对该主机的日志查询；
- 最多 4 个主机并行，同一主机内顺序请求；每个请求受"来源超时"约束。

被上游限流（官方接口或日志）的渠道同样不计为已尝试，下一轮优先重试，而不是等一个刷新间隔。

### 3.3 刷新与沿用

- `upstream_ratio_refresh_hours`（默认 6）内不重新获取，沿用快照里的结果。
- 获取失败时沿用上一次取到的倍率（附本次失败原因），超过 `upstream_ratio_max_age_days`（默认 7）则丢弃。
- 沿用以渠道的取数配置不变为前提：每条结果记下 `source_fingerprint`（渠道类型、上游地址、全部密钥、上游账号令牌与用户 ID 的 SHA-256 摘要前 16 位，不存原文）。渠道 ID 不变但换了上游或密钥时摘要不同，旧倍率、网关类型与失败原因一并作废并立即重取，不等刷新间隔；重取失败也不回落到旧倍率（那是另一个上游的）。否则换上游后最长 `upstream_ratio_max_age_days` 内都拿旧倍率判亏损、算保本价。摘要取原始密钥配置而非启用中的密钥：多密钥渠道自动禁用某把密钥是常态，不应因此作废倍率。升级前的快照没有摘要，直接记下当前配置。摘要只存在快照里，渠道核对接口不返回。
- 原因枚举：`no_source`（没配令牌且日志没有可用记录，或日志补充已关闭）、`key_not_in_account`、`auto_group`、`group_missing`、`credential_rejected`、`rate_limited`、`unavailable`、`not_supported`、`no_consume_log`、`waiting`、`unsupported_channel`。页面按枚举翻译，不透传上游错误原文。

## 4. 成本系数核对

```text
r    = 成本系数（没有配置行时按 1.0，并标"未配置"）
g_up = 上游分组倍率
dev  = r / g_up − 1
  unknown     取不到 g_up
  free        g_up == 0（上游免费分组），不核对
  match       |dev| ≤ 1e-9（只吸收浮点运算误差，如 (0.1+0.2)/0.3−1 ≈ 2e-16）
  cost_low    dev < 0       成本账低估，利润与提成虚高，每日限额按低估的上游消耗计算
  cost_high   dev > 0       成本账高估
```

不设业务容差：两边都是手填的倍率（上游管理员配的分组倍率、我们配的成本系数），一致时就是完全相等；差 1% 也意味着成本账与上游实际扣费差 1%，应当报出。

成本系数是整个渠道一个数，隐含"上游模型价 = 平台模型价"；两边模型价不同的部分由逐模型的亏损判定覆盖（§6）。状态在每次查询时用当前成本系数重算，所以在任何节点改了成本系数，核对列表都立即反映。

界面（`web/src/features/system-settings/models/price-monitor-channel-costs.tsx`）：

- 比对筛选里新增「成本系数核对」视图（代替矩阵显示），列：渠道、上游分组、上游倍率（来源与获取时间，或取不到的原因）、成本系数、核对结果、操作。需要处理的排在前面（偏低、偏高、无法核对、一致、免费）。
- 统计卡新增"成本系数不一致的渠道"（按实时核对列表计数），点击进入该视图。
- 矩阵的渠道列头补一行"成本系数 r · 上游倍率 g"，不一致时标红，点击进入该视图并高亮该渠道。
- 矩阵中命中"配置成本风险"的行，操作列给「调整成本系数」，进入该视图并高亮对应渠道（改价解决不了这类风险）。
- 不一致的渠道提供「采用上游倍率」（确认后把 r 改成 g_up）；所有渠道都可「修改成本系数」（0–100）。需要巡检编辑权与渠道编辑权。
- 核对列表另起查询、每 30 秒刷新；保存巡检设置与一轮巡检结束时立即重新拉取，不等轮询。

## 5. 模型改价便捷化

### 5.1 所有视图、所有按量/按次计价的行都能改价

- 操作列在所有视图显示；每行有「改价」与复选框，工具栏「批量改价」。矩阵查询在任何视图都带上平台单元格（改价要读平台现价），只是不比对平台的视图不显示平台列。
- 阶梯价的行给「去模型定价修改」链接（新窗口打开 `/system-settings/billing/model-pricing?model=<模型>`，模型定价页据 `?model=` 预填搜索框）。
- 后端为每个按量/按次计价的行产出改价数据 `repair_floor`，没有可比渠道时保本下限 `fields` 为空；`current` 覆盖平台已配置的所有改价字段（按官方价改一个没有下限的字段时，改价请求同样需要它做并发校验）。

### 5.2 改价弹窗（`price-monitor-apply-dialog.tsx`）

每个模型一张卡片，每个价格字段一行：当前价、保本价、官方价、渠道价（最低–最高）、新价格。字段取平台已有的与任一参考价涉及的。

| 模式 | 新价格 |
|---|---|
| 保本价（默认） | 低于保本价的项抬到保本价，已高于的保持现价——只抬不降，不会把利润压到零 |
| 官方价 | 有官方价的项改成官方价（可升可降），没有的保持现价 |
| 最高价 | 现价与渠道最高价取大（原有语义） |
| 手动 | 逐项输入 |

- 默认模式取第一个可用的：保本价 → 官方价 → 最高价 → 手动；所选模型都没有某种参考价时该模式置灰。
- 新价格低于保本价时标黄并要求二次确认；服务端仍按保本下限复核，突破需 force（行为不变）。
- 批量改价时每个模型卡片有复选框，可以去掉个别模型。

### 5.3 改完立即重算（`controller/price_monitor_refresh.go`）

改价、改成本系数成功后调用 `refreshPriceMonitorSnapshotInPlace`：

- 用当前定价重建每一行的平台单元格（快照文件不存平台的原始 option 值，而且其他页面改过的价格也应反映）。其他来源单元格清掉比对标记、亏损字段与无价格的占位分项（那是上一次标记补的"平台有、来源没有"行，留着会被再次标记当成不一致）后重新标记；缺失、占位价、来源失败三类单元格原样保留。双方都是表达式且任一方为动态价时只能比表达式原文，而原文不写进快照文件，从磁盘加载的快照里没有，这类单元格沿用巡检时的比对结果。
- 用当前成本系数重算核对状态、亏损判定、改价数据与统计。不发任何上游请求。
- 串行执行；写回用 `SaveIfCheckedAt`，期间若新一轮巡检已替换快照则放弃写回。
- 巡检进行中发生的改动：那一轮读的是改动前的定价或成本系数，保存后会覆盖重算结果，所以记下"待补算"，巡检保存后再重算一次（补算直接执行重算，不经过登记待补算的入口，否则会把自己又登记一遍）。巡检把取上游倍率（可能较慢）放在读平台定价之前，缩小这个窗口。
- 只在主节点执行（快照由主节点维护、存在主节点本地）；升级前的旧版本快照不重算（缺表头渠道 ID，重算会清掉所有渠道判定）。非主节点、重算失败或被新一轮取代时返回 `refreshed=false`，页面把这些行锁成"下一轮刷新"，与原行为一致。
- 已知限制：重算只处理快照里已有的行。改价后不再有差异的行留在列表里（便于确认结果），改价后新出现差异的模型要等下一轮巡检才进入列表；旧版的逐字段差异列表 `Items` 也等下一轮更新。
- 在渠道编辑抽屉等其他地方改成本系数不触发重算：核对列表与"不一致渠道"统计卡按当前成本系数实时计算，矩阵里的配置成本判定在下一轮巡检更新。

## 6. 对亏损判定的影响（G3）

- `measured = 上游价 ÷ 平台价 × g_up`（g_up 已知时）；单元格记 `upstream_factor`。未知时维持原算法，`upstream_factor` 为空。
- 保本下限：`floor = max over 渠道 (上游价 × g_up ÷ 售价系数)`；g_up = 0 的渠道没有成本，不构成下限。改价弹窗的"最高价""渠道价"仍是原始列表价。
- "配置成本"取核对结果里的同一个成本系数值，判定与核对不会各读一次、读到不同的值。
- **页面显示价格对比，不显示系数**。系数是按最坏情况估的中间量（逐项取最大、售价取最低分组倍率），作为数字给人看容易被误读成真实亏损幅度。命中实测亏损的单元格带 `loss_lines`：逐项列出"上游实际成本（列表价 × g_up）/ 我们最低售价（平台价 × 最低分组倍率）"，只列前者更高的项，阶梯价带阶梯下标；g_up 未知时注明按列表价计算。明细与实测亏损判定走同一套可比维度（`priceMonitorComparableDimensions`）和同一个比较条件，有标记就一定有明细。配置成本亏损与具体价格无关，显示一句"成本系数 r 高于最低分组倍率 g"。
- 快照版本 18 → 20（19 加上游倍率与渠道 ID，20 加 `loss_lines`），升级后自动全量重算一次；旧版本快照不做就地重算，等这一轮巡检。
- 公开分享页不暴露内部定价信息（与 `repair_floor` 同理）：亏损判定的四个系数 `sell_factor` / `measured_factor` / `configured_factor` / `upstream_factor` 与价格对比 `loss_lines` 全部剥掉，只保留亏损类型徽标（分享页 `controller/price_monitor_page.go` 只显示徽标，不再画系数行）。成本系数与上游倍率是采购成本与上游折扣；实测系数与明细里的上游成本都乘了上游倍率，结合页面上的来源价即可反推。表头渠道 ID 也去掉。

## 7. API

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/price_monitor/channels` | 巡检查看 | `{checked_at, items}`，items 为核对行，状态按当前成本系数重算 |
| PUT | `/api/price_monitor/channels/:id/cost_ratio` | 巡检编辑 **且** `channel` write | `{cost_ratio}`（0–100）；渠道须存在且启用；写入 `model.UpsertChannelCostConfig`（含缓存失效），保留已有备注；记审计 `price_monitor.cost_ratio.update`；返回 `{refreshed, item}` |

| PUT | `/api/price_monitor/settings`（已有） | 不变 | 新增三个可选字段（§8），省略的不写入 |

错误用 `ApiErrorI18n`：`price_monitor.cost_ratio_invalid`、`price_monitor.channel_unavailable`（en / zh-CN / zh-TW）。

## 8. 数据模型与配置

- **无新表、无迁移**。快照新增 `ChannelCosts map[渠道 ID]PriceMonitorChannelCost`；表头新增 `channel_id`；统计新增 `cost_ratio_mismatch`；`repair_floor` 新增 `lowest`、`official`，且对所有按量/按次计价的行产出。
- `price_monitor_setting` 新增（Rule 12，在巡检设置弹窗里编辑）：

| 键 | 默认 | 范围 |
|---|---|---|
| `upstream_ratio_refresh_hours` | 6 | 1–168 |
| `upstream_log_queries_per_host` | 8 | 0–20，0 = 不用日志 |
| `upstream_ratio_max_age_days` | 7 | 1–30 |

三个键都在 `model/config_group.go` 的 `priceMonitorFields` 里（设置弹窗每次保存都会带上它们），`SaveConfigGroup` 先按整数解析、再用 `PriceMonitorSetting.IsNormalized` 校验范围，越界或非整数拒绝保存，不会静默保留旧值。

## 9. 与主链路的关系（Rule 0）

- 全部在巡检后台任务与管理接口中执行，不进入 relay 链路。
- 共享资源：
  - `channel_cost_configs` 及其内存/Redis 缓存：relay 路径的每日限额会读成本系数。写入复用 `UpsertChannelCostConfig`，与渠道抽屉同一路径、同样的缓存失效。
  - 模型价格：改价复用现有 `apply_price` 的事务与版本校验，不变。
  - 上游 HTTP 调用：巡检后台 goroutine 内执行，每个请求受"来源超时"与响应体大小（1 MB）约束；没配代理时用独立客户端，不占 relay 连接池（配了代理沿用渠道代理客户端，与余额查询相同）。日志补充复用 `service.QueryUpstreamLogs`（自有客户端与并发上限）。上游账号访问令牌只在请求头中使用，不写日志、不进快照。
