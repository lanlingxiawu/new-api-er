## 规则 0：主链路绝对不可干扰

**任何代码改动——无论是新增功能还是修改现有功能——都不得影响 AI 主链路的执行。**

主链路关键路径：`客户端请求 → 中间件 → relay 处理器 → 上游 AI → 流式响应 → 客户端`

### 具体要求

| 要求 | 说明 |
|---|---|
| 禁止阻塞调用注入 relay | 日志、统计、计费钩子必须异步（goroutine/channel），不能在 relay goroutine 上内联执行 |
| 新中间件必须亚毫秒级 | 重逻辑（DB 查询、外部调用）移到后台 goroutine，中间件只做快速判断 |
| 新功能失败必须静默 | 内部 `recover()` + 记录日志，错误不得传播到 relay 响应 |
| 热路径禁止新增同步 DB 读 | relay 需要的数据只能读缓存，DB 仅作限时的 cache miss 兜底 |
| relay 相邻变更必须有开关 | 任何触及 relay 执行流程的修改都必须有 feature flag，可即时关闭 |

### 共享资源冲突检查（所有代码改动必须执行，包括新增和修改）

改动涉及以下资源时，**必须检查主链路是否也访问同一资源**，冲突用隔离解决，不用热路径加锁：

| 资源 | 冲突风险 | 解决方式 |
|---|---|---|
| **Redis key** | 缓存污染、key 碰撞、意外驱逐 | 使用独立 key namespace |
| **DB 表** | 行锁竞争、拖慢 relay 读、全表扫描膨胀 | 提前加索引，避免写操作锁到 relay 读的行 |
| **内存缓存 / map** | 并发写 race、GC 压力影响 relay 延迟 | 加同步保护，评估 GC 影响 |
| **连接池** | 新功能占满连接，relay 拿不到连接 | 评估池容量，连接不是免费的 |
| **goroutine / worker pool** | 新功能抢占，relay worker 被饿死 | 为 relay 预留容量 |

## 规则 1：JSON 序列化统一使用 `common/json.go`

所有 JSON marshal/unmarshal 必须使用 `common/json.go` 中的封装函数：

```go
common.Marshal(v any) ([]byte, error)
common.Unmarshal(data []byte, v any) error
common.UnmarshalJsonStr(data string, v any) error
common.DecodeJson(reader io.Reader, v any) error
common.GetJsonType(data json.RawMessage) string
```

**禁止**在业务代码中直接 `import "encoding/json"` 并调用其函数。  
`json.RawMessage`、`json.Number` 等**类型定义**可以引用，但序列化操作必须走 `common.*`。

## 规则 2：数据库兼容性

必须同时兼容 **SQLite / MySQL >= 5.7.8 / PostgreSQL >= 9.6** 三种数据库。

### 优先使用 GORM 抽象

- 优先使用 `Create`、`Find`、`Where`、`Updates` 等 GORM 方法，避免裸 SQL。
- 主键生成交给 GORM，不要手写 `AUTO_INCREMENT` 或 `SERIAL`。

### 裸 SQL 的注意事项

| 差异点 | PostgreSQL | MySQL / SQLite |
|---|---|---|
| 列名引号 | `"column"` | `` `column` `` |
| 保留字列（group/key）| 用 `commonGroupCol`、`commonKeyCol`（`model/main.go`）| 同左 |
| 布尔值 | `true` / `false` | `1` / `0`，用 `commonTrueVal`/`commonFalseVal` |
| 数据库判断 | `common.UsingPostgreSQL` | `common.UsingSQLite`、`common.UsingMySQL` |

### 禁止（无跨库兜底时）

- MySQL 专用函数（`GROUP_CONCAT` 等）
- PostgreSQL 专用操作符（`@>`、`?`、JSONB 操作符）
- SQLite 不支持 `ALTER COLUMN`，只能 `ADD COLUMN`
- 数据库专有列类型，JSON 存储统一用 `TEXT`

## 规则 3：前端包管理器使用 Bun

两套前端（`web/default/` 和 `web/classic/`）均使用 `bun`：

```bash
bun install          # 安装依赖
bun run dev          # 启动开发服务器
bun run build        # 生产构建
bun run i18n:sync    # 同步翻译
```

## 规则 5：上游中继请求 DTO 零值保留

在 relay/convert 路径中，解析客户端 JSON 后再转发给上游的请求结构体：

- 可选的标量字段**必须**使用指针类型加 `omitempty`（如 `*int`、`*float64`、`*bool`）。
- 语义：
  - 客户端未传该字段 → `nil` → marshal 时省略 ✓
  - 客户端显式传 `0` / `false` → 非 nil 指针 → 必须发给上游 ✓
- **禁止**用非指针标量加 `omitempty`，零值（`0`、`false`）会被静默丢弃。

## 规则 6：前端修改必须同时更新两套 UI

任何前端页面/组件的改动都必须同时应用到两套 UI：

| UI | 目录 | 技术栈 | 开发端口 |
|---|---|---|---|
| Default | `web/default/` | React 19, TypeScript, Base UI, Tailwind CSS | 3002 |
| Classic | `web/classic/` | React 19, JavaScript (JSX), Semi Design | 5173 |

### 样式规范

- **Default**：使用 Tailwind 工具类和 Base UI 设计 token，禁止硬编码颜色，使用响应深浅模式的 `bg-*`、`text-*`、`border-*` 类。
- **Classic**：使用 Semi Design 组件 props 和 CSS 变量（`var(--semi-color-*)`），禁止在 Semi token 体系外写死颜色值。
- **优先复用现有样式**：实现同一功能模块的新内容前，先查看同页面/同模块已有组件的样式写法，直接复用相同的 class 组合、组件变体和布局模式，不要为相同的 UI 模式另起一套平行实现。**按钮区域同样适用此原则**：添加按钮前，先找同模块最近的同类按钮组，照搬其结构。
- **Classic UI 次要危险操作**：若某操作是表单中的次要功能（如清除数据），用一个带文字的 danger 按钮即可，不需要添加粗体标题或说明段落。确认弹窗使用 `Modal.confirm`（`@douyinfe/semi-ui`），设置 `okType: 'danger'`。

### i18n 规范

- Default 翻译文件：`web/default/src/i18n/locales/{lang}.json`，key 为英文原文，用 `t('English key')`
- Classic 翻译文件：`web/classic/src/i18n/locales/{lang}.json`，zh-CN / zh-TW 为独立文件，同样用 `t('English key')`
- 修改后执行：`bun run i18n:sync`（在各自 UI 目录下）

### 交互设计原则

- 所有 UI 交互（加载态、错误提示、空态、确认弹窗、操作反馈）必须**以用户视角**设计，而非以实现视角。
- 错误提示必须告诉用户下一步能做什么，不得暴露内部错误码或 Go error 原文。
- 加载中、禁用态等过渡状态必须明确处理，不能让用户陷入「不知道操作是否在进行」的困惑。

### 发现后端缺失实现时

- 不要在前端静默 stub 或伪造后端行为。
- 将缺口记录为设计文档（`docs/design/`）中的 TODO，**先与用户确认再决定如何处理**——缺失的后端实现可能是有意取舍、延迟范围，或尚未做出的设计决策。

### 编码规范（Windows / UTF-8）

- 所有源文件（`.tsx`、`.jsx`、`.ts`、`.js`、`.json`）必须保存为 **UTF-8 无 BOM**。
- 禁止用 PowerShell 的 `Out-File`、`Set-Content`、`echo >` 写含中文的文件（默认 UTF-16，会乱码）。
- 含中文内容的文件必须用 `Write` 或 `Edit` 工具写入。

## 规则 7：新功能必须先写设计文档

**新增功能或对现有功能进行较大改动前**，必须：

1. 在 `docs/design/` 下写设计文档（文件名：`<功能名>.md`）。
2. **等待确认**后才能写实现代码，未经确认不得开始编码。

### 设计文档必填章节

**所有功能**：

- 目标与范围
- 数据流（请求 → 处理 → 存储 → 响应）
- API 契约（端点、请求/响应结构、鉴权级别，参考规则 12）
- 数据模型变更（新表、新字段、迁移；大表需有索引设计，参考规则 9）
- 新增配置项（若有，参考规则 13）
- 关键业务逻辑与边界情况
- 错误处理策略（参考规则 10）
- 与现有子系统的交互（计费、relay、缓存等）

**如果功能涉及 AI relay 链路，额外必填**：

- **主链路影响**：哪些在 relay goroutine 上同步执行，哪些异步/延迟执行
- **共享资源审计**：功能访问的每个 Redis key/DB 表/内存结构/连接池，以及主链路是否访问同一资源（参考规则 0）
- **并发分析**：100k RPM 下每请求的 DB 调用次数、Redis 调用次数、锁使用、goroutine 开销（参考规则 9）

### 实现完成后

更新设计文档以反映实际代码逻辑，去除分歧，记录实现决策。

### 修改现有代码时

- 查阅 `docs/design/` 下的相关设计文档作为上下文参考。
- **代码逻辑优先于文档**——若代码与文档冲突，以代码为准（文档可能过期）。
- 发现重大出入时主动更新文档。

## 规则 8：高并发与大数据量设计约束

### 8.1 适用范围

**仅 AI relay 链路需要严格的高并发设计**，包括：

- `relay/` — 请求路由、上游分发、流式响应
- relay 路径上的计费/配额预扣与结算
- relay 路径上的 token/限流检查
- 每次 AI 请求都会执行的中间件

管理后台、设置页、管理 API、报表等**非 relay 路径不需要满足同等要求**，直接写普通同步 DB 查询即可。

当前 AI relay 链路峰值 **30,000 RPM**，设计必须支撑 **100,000+ RPM** 无需架构改动。

### 8.2 AI relay 链路强制原则

| 原则 | 要求 |
|---|---|
| 热路径禁止每请求 DB 写 | 写操作（计费、日志、统计）必须批量、异步队列，或先写 Redis 再由后台 worker 落库 |
| 读优先命中缓存 | relay 每次请求读取的数据必须来自 Redis 或内存缓存，缓存 TTL 必须显式声明 |
| 热路径禁止分布式锁 | 确实需要锁时范围要窄、超时要短，绝不能跨上游 AI 调用持锁 |
| goroutine 必须走 worker pool | 不能每请求无限创建 goroutine，使用 worker pool 或 channel dispatcher |
| 请求处理无状态 | relay handler 不能跨请求在内存中积累状态，共享状态放 Redis |
| 非关键子系统故障不阻塞 | 统计、台账、通知等失败/超时不得阻塞或错误化主链路响应 |

### 8.3 大数据量（全系统适用）

系统会持续积累大量数据（请求日志、账单、统计等）。对持续增长的表：

| 要求 | 说明 |
|---|---|
| 索引先于查询 | `WHERE`、`ORDER BY`、`JOIN` 列必须有覆盖索引，在设计文档中提出，迁移中添加 |
| 禁止 `SELECT *` 和全表扫描 | 显式列出查询字段，设计阶段验证 `EXPLAIN` 输出 |
| 列表分页用 keyset | `WHERE id < last_id` 替代 `LIMIT n OFFSET m`，offset 在大数据量下极慢 |
| 时间范围查询必须有时间过滤 | 日志/统计表查询必须带时间条件，禁止无界扫描 |
| 聚合走预聚合表 | 不在实时 API 响应中跑重 `GROUP BY`，由定时任务写入汇总表 |
| 软删除列纳入复合索引 | 有 `deleted_at` 时，将其加入复合索引，避免扫描已删除行 |

## 规则 9：错误处理规范

### Controller 层统一使用 `common/gin.go` 封装

```go
ApiError(c, err)          // 业务错误，包装 err.Error() 作为消息
ApiErrorMsg(c, msg)       // 业务错误，直接传消息字符串
ApiErrorI18n(c, msgKey)   // 业务错误，用 i18n key（用户可见错误首选）
```

三者均返回 **HTTP 200**，响应体：`{"success": false, "message": "..."}`，禁止发明其他响应结构。

### 非 200 的 HTTP 状态码

| 状态码 | 场景 |
|---|---|
| `401` | 未认证（由鉴权中间件处理，业务代码不要手动返回） |
| `403` | 权限不足 |
| `500` | 不可恢复的服务端错误（DB 故障、panic 恢复） |

### 其他要求

- 禁止将原始 Go error 字符串返回给客户端（可能暴露内部细节），必须包装为用户可读消息。
- relay 链路错误**不用** `ApiError`，走 `controller/relay.go` 的专用错误路径，不要混用。
- 返回给客户端清洁消息前，必须先记录底层错误日志。
- 非 relay 路径不要静默吞掉错误，最少调用 `logger.LogError`。

## 规则 10：日志规范

使用 `logger` 包（`logger/logger.go`），**所有调用必须传 request context 作为第一个参数**（用于捕获 requestId）：

```go
logger.LogInfo(c, "消息")
logger.LogWarn(c, "消息")
logger.LogError(c, "消息")
logger.LogDebug(c, "消息", args...)  // 仅 common.DebugEnabled=true 时输出
```

### 日志级别使用原则

| 级别 | 适用场景 |
|---|---|
| `LogDebug` | 开发/诊断细节，生产默认不开启 |
| `LogInfo` | 关键业务流程事件（模型已选、配额跳过、缓存命中） |
| `LogWarn` | 可恢复的异常（限流即将触发、触发重试、使用了 fallback） |
| `LogError` | 需要关注的故障（relay 错误、DB 故障、外部调用失败） |

**非请求上下文的系统级事件**（启动、配置加载、后台 worker 错误）：  
使用 `common.SysLog(msg)` / `common.SysError(msg)`，不用 `logger.Log*`。

### 禁止

- 禁止记录 API key、bearer token、用户密码等凭证信息。
- 禁止在业务代码中使用 `fmt.Println` 或 `log.Printf`，统一走 logger 包。

## 规则 11：新接口鉴权与路由

每个新接口必须放在 `router/api-router.go` 中正确的路由分组里，并挂载对应中间件。

### 鉴权中间件参考

| 中间件 | 所需角色 | 适用场景 |
|---|---|---|
| `middleware.AdminAuth()` | `>= RoleAdminUser` | 管理员 API |
| `middleware.UserAuth()` | `>= RoleCommonUser` | 已登录用户 API |
| `middleware.RootAuth()` | Root 角色 | 系统级操作 |
| `middleware.TryUserAuth()` | 无要求（可选） | 有无登录都能用的接口 |

### 其他要求

- **公开接口（无鉴权）必须显式说明原因**，在代码注释和设计文档中记录。
- Admin 接口放在已有 `AdminAuth()` 的路由组下，不要在单个接口上单独挂中间件。
- 禁止把需要权限的逻辑放在公开路由组里绕过鉴权。
- 处理 AI 请求的 relay 相邻接口走 relay router，不走 API router。

## 规则 12：配置项管理

所有用户可配置的设置必须走 `setting/` 包，禁止引入新的全局变量、纯环境变量配置或临时 DB 查询来管理设置。

### 添加新配置项的四步骤

**1. 定义结构体**（在 `setting/{module}_setting/{module}_setting.go`）：
```go
type MyFeatureSetting struct {
    Enabled  bool `json:"enabled"`
    MaxItems int  `json:"max_items"`
}
var myFeatureSetting = MyFeatureSetting{Enabled: false, MaxItems: 100}
```

**2. 在 `init()` 中注册**（ConfigManager 自动持久化到 DB）：
```go
func init() {
    config.GlobalConfig.Register("my_feature_setting", &myFeatureSetting)
}
```

**3. 提供 getter**（调用方不要跨请求缓存返回的指针）：
```go
func GetMyFeatureSetting() *MyFeatureSetting { return &myFeatureSetting }
```

**4. DB 持久化自动完成**，key 格式为 `{模块}.{字段}`（如 `my_feature_setting.enabled`）。

### 其他要求

- 用户可配置的值禁止直接读 `os.Getenv`，env var 仅用于部署/基础设施配置。
- 线程安全由 ConfigManager 保证，调用 getter 即可，不要在 goroutine 间直接传结构体指针。
- 配置的保存通过现有管理员设置 API 暴露，不要另建自定义保存接口。

## 规则 13：后端 i18n 双语同步

新代码产生**任何用户可见字符串**（错误消息、通知文本、UI 显示的提示）时，必须同步添加到两个语言文件：

- `i18n/locales/en.json` — 英文（作为 source of truth）
- `i18n/locales/zh.json` — 中文

Controller 错误使用 `ApiErrorI18n(c, msgKey)`（规则 10），运行时按用户语言查找 key，不要在 controller/service 代码中硬编码中文或英文字符串。

**不在 UI 中显示的内部日志消息**（纯服务器日志）不需要 i18n，统一用英文即可。

## 规则 14：计费表达式系统

涉及分层/动态计费（表达式计价）时，**必须先阅读 `pkg/billingexpr/expr.md`**。

## 规则 15：测试规范

### 15.1 Go 后端——测试文件位置与框架

- 测试文件与被测源文件**放在同一目录**（`foo.go` → `foo_test.go`），使用同包或 `foo_test` 黑盒包。
- 断言统一使用 **`testify`**（`require` / `assert`），不要用裸 `t.Fatal` / `t.Error` 做断言。
- Controller / 中间件测试使用 **`net/http/httptest`** + **`gin.CreateTestContext`**。

### 15.2 先写测试用例，再写实现

**在编写任何实现代码前**，先设计测试用例，运用以下方法：

| 测试方法 | 说明 |
|---|---|
| **边界值分析** | 在每个边界及其内外侧各取值（如 `limit=0`、`1`、`200`、`201`） |
| **等价类划分** | 将输入分为有效/无效等价类，各取一个代表值 |
| **语句覆盖** | 确保每行代码至少被一个测试执行到 |
| **判定覆盖** | 确保每个分支（if/else、switch）的真假路径都被覆盖 |
| **条件覆盖** | 复合条件（`a && b`）中每个子条件独立取真/假 |
| **路径覆盖** | 覆盖函数中所有独立执行路径，尤其是循环和嵌套分支 |

步骤：先设计测试用例并写入测试文件 → 再编写实现代码 → 所有测试通过后功能才算完成。

### 15.3 各层测试重点

| 层次 | 测试重点 |
|---|---|
| `dto/` | JSON 序列化往返、零值保留、指针语义（参考规则 5） |
| `model/` | 查询正确性、迁移兼容性 |
| `service/` | 业务逻辑、边界情况、错误路径 |
| `relay/channel/` | 上游请求/响应转换；用 `httptest.NewServer` 模拟上游 |
| `relay/helper/` | 计费表达式、价格计算、流解析 |
| `middleware/` | Header 解析、鉴权逻辑（使用 `gin.CreateTestContext`） |
| `common/`、`pkg/` | 工具函数正确性 |

### 15.4 relay 链路——禁止调用真实上游 AI

- **禁止**在测试中向 OpenAI、Claude、Gemini 等上游 AI API 发起真实网络请求。
- 用 `httptest.NewServer` 返回 fixture JSON 来模拟上游响应（项目 `relay/channel/` 已有此模式）。
- relay 测试必须快速（< 1s）且确定性，不依赖外部 I/O。

### 15.5 数据库测试——使用真实项目 env，SQLite 仅作兜底

- **优先**使用项目 `.env` / 环境配置中的真实数据库进行集成测试，能捕获 SQLite 默默接受而 MySQL/PostgreSQL 会报错的 SQL 问题。
- SQLite 内存库（`:memory:`）仅作**兜底**，用于没有真实 DB 服务的环境（如 CI），不作默认选项。
- **禁止 mock GORM**——mock 曾导致本项目生产/测试分歧（迁移失败被掩盖）。
- 使用 SQLite 兜底时，必须在注释中标注与 MySQL/PostgreSQL 行为不同的 SQL。

### 15.6 不需要写测试的情况

- 不要复现完整的 relay 热路径端到端测试——那属于 staging/压测范畴。
- 不要测试框架本身行为（Gin 路由、GORM 自动迁移），只测建立在框架上的项目逻辑。
- 不要为覆盖率指标而写空洞的测试，测试应针对真正可能出错的逻辑。

### 15.7 前端——当前无测试框架

- 两套前端均未配置测试运行器，TypeScript 类型检查（`bun run typecheck`）和 ESLint（`bun run lint`）是当前主要的正确性保障。
- 未经确认不要自行引入测试框架。需要回归覆盖的 bug，记录在 `docs/design/` 的 TODO 中。

### 15.8 实现完成后必须运行测试

- **代码写完必须运行全部测试并通过**，才能标记任务完成。运行命令：`go test ./...`（从项目根目录）。
- 有失败测试时必须先修复，不得带着已知失败测试提交。
- `service/` 或 `model/` 新增含分支或边界情况的业务逻辑，**必须**有覆盖所有分支的测试。
- 修复 bug **必须**补一个能复现原始 bug 的测试。
- relay channel 适配器改动**必须**包含用 fixture 测试变更转换逻辑的测试用例。
